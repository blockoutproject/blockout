# Backend rebuild: capability baseline

## Scope and authority

The replacement starts with an **empty business database**. Old matches, favorites, live links, notifications, local profiles and histories may all be deleted. Preserve the **ability to deliver the same capabilities with new data**, not the old records. The mandatory continuity is **existing Auth0 accounts and RevenueCat paid subscriptions**: a paying user must recover paid access when their local business account is recreated.

This is evidence for future specifications and plans, not a target architecture, a migration implementation or authorization to execute a production purge. The [constitution](../../.specify/memory/constitution.md), [domain model](../architecture/blockout-domain-model-v1.md), [identity architecture](../architecture/mobile-and-identity-architecture-v1.md) and [mobile redesign specification](../../specs/001-mobile-ui-redesign/spec.md) remain the relevant authorities. Changes to current observable behavior must be decided explicitly in the future specifications.

The observed `origin/main` was `f4ebe2393ec2fe85b2b6f58b9e1201742ac04bb5`. **Neither a matching production deployment nor the installed mobile build was established.** “Current” below means this source revision, not a claim of verified production behavior. No live provider, production database, Auth0 customer or RevenueCat customer was queried.

The evidence is split into a readable baseline and two reference appendices:

- [Data inputs](backend-preservation/data.md): all **18 application tables / 198 columns**, lineage, classifications and fresh-bootstrap dependencies. This is not a list of rows to retain or a required new schema.

- [Reference scenarios](#reference-scenarios): semantic comparisons and tests to reuse; unresolved runtime proof remains explicit.

## Fresh data flow and rebuild boundaries

Current sports writes cross clubs, teams, pools, matches, competition associations and configuration owners. The competition scraper discovers provider competitions, resolves curated mappings, reconciles pool/team identities and associations, stages match writes, and updates ranking totals. Club discovery depends on IDs already referenced by teams. The gateway then composes mobile views with separate owner calls and local caches; search and notifications use additional projections.

The [field inventory](backend-preservation/data.md#provider-to-screen-lineage) traces the full provider → parse/normalize → reconcile → owner write → database → composition → mobile chain. The fresh installation needs deliberate division/mapping/config/legal inputs before representative imports can populate usable screens. It does **not** need old sporting records, old media, moderation history or notification recovery.

Current database identifiers and constraints are implementation evidence. Preserve identity consistency **within the new system**, including provider codes, season boundaries, ordered match opponents and participation. Service consolidation, transaction boundaries, batch imports, normalized names and future REST names remain Plan decisions. No new endpoint or physical schema is selected here.

Rankings currently sort by points descending, penalty ascending, wins descending, set coefficient descending, then point coefficient descending in multiple gateway services. Scraper coefficient calculation uses three-decimal ratios and 1000 for a zero divisor. Match-derived totals and official provider standings can differ, particularly penalties. Comparing only the final rank number would miss useful statistical information and incorrect source precedence.

## Auth0 and RevenueCat continuity

The current [RevenueCat client](../../apps/frontend/mobile/src/modules/subscription/providers/revenuecat-client.ts) configures the SDK, and the [purchases provider](../../apps/frontend/mobile/src/modules/subscription/providers/purchases-provider.tsx) identifies an authenticated customer using **`auth0User.sub`**, not the local database user ID. Entitlement is read from the configured RevenueCat entitlement. The provider serializes identity transitions and discards stale responses; paywall purchase/restore results trigger a customer-info refresh.

The [user service](../../apps/backend/users-service/src/main/java/com/blockout/users/user/application/UserApplicationService.java) can create a business user through `ensureCurrentUser` after Auth0 login. Therefore an empty local user table is compatible with the observed identity design **if the same Auth0 subject and RevenueCat project/entitlement association are used**. This is a source-based inference, not proof about existing subscribers.

The current user bootstrap also attempts Auth0 identity linking when a local profile has the same email. That behavior is not proof that linked logins keep the same canonical subject or RevenueCat aliases; the controlled linked-account case must establish it. Email must not be treated as the subscription identity.

The real continuity check must use controlled accounts representing existing paid users, without changing their subscription identity: record the expected entitlement, start with no business profile in the isolated replacement, log in with the same Auth0 account, verify the new local user, then verify paid access. Cover both platforms, linked identities, restore and account switching. SDK mocks cannot establish the actual RevenueCat aliases, store transfer behavior, configured entitlement or installed-client settings.

The technical purge must never invoke `deleteUser` / the account-deletion endpoint: that path also deletes the Auth0 identity. All local histories may disappear. A recreated profile will have a fresh pseudonym and creation timestamp under current code; the seven-day live publishing rule then applies to the fresh account unless future product specifications change it. No old profile/age migration is required by this baseline.
