# MRG-347 Expo Relay Client Migration

- Status: implemented in the monorepo shadow baseline
- Owner: Expo mobile application
- Active BFF operations: twelve user, search, notification, and report calls
- Production effect: none

## Purpose

MRG-347 migrates every active Expo consumer formerly backed by handwritten `UserApi`, `SearchApi`, `NotificationApi`,
and `ReportApi` methods to canonical mobile-gateway v2 operations generated by Orval. Generated wire schemas validate
paths, queries, commands, and responses, while handwritten projections keep transport models out of screens, caches,
forms, and session state.

The migration does not redesign authentication, account deletion, favorites, search, the notification inbox, push
registration, or reporting. Existing TanStack cache identities, freshness, retry, infinite-page continuation,
optimistic rollback, feedback, haptics, image preparation, multipart behavior, and navigation remain application
policy.

## Migrated Operation Set

| Operation ID | Mobile workflow       | Consumer boundary                |
| ------------ | --------------------- | -------------------------------- |
| `BFF-P-11`   | submit report         | deferred editable report form    |
| `BFF-P-12`   | search clubs          | public search                    |
| `BFF-P-13`   | search teams          | public filtered search           |
| `BFF-P-14`   | search pools          | public filtered search           |
| `BFF-S-21`   | list notifications    | current-user infinite inbox      |
| `BFF-S-25`   | delete notification   | optimistic inbox deletion        |
| `BFF-S-26`   | register push token   | onboarding and session bootstrap |
| `BFF-S-29`   | update user profile   | deferred editable profile form   |
| `BFF-S-30`   | ensure current user   | authenticated session bootstrap  |
| `BFF-S-31`   | delete current user   | profile account action           |
| `BFF-S-32`   | follow team or pool   | optimistic entity detail state   |
| `BFF-S-33`   | unfollow team or pool | optimistic entity detail state   |

`BFF-S-22` through `BFF-S-24` expose unread-count, read, and opened workflows but have no active Expo callers. Their
generated code remains available without adding a new query, mutation, cache, or screen behavior. The four handwritten
resource clients disappear. The legacy API provider remains only as an empty compatibility shell until the separately
owned generated-only provider and case-conversion cleanup.

## Query, Cache, And Projection Ownership

- Session ensure retains the `current-user` cache key, disabled-by-default execution, five-minute freshness, and
  no-retry behavior.
- Search retains the existing club, team, and pool query keys, empty-query enablement choices, five-minute freshness,
  no-retry policy, request filters, and BFF item order. Cancellation signals now reach every generated search read.
- Canonical nullable search values remain explicit. Cards omit absent chips, use empty identity text only where their
  existing primitive requires a string, and use the neutral theme color because canonical search projections do not
  expose division colors.
- The notification inbox retains its page-size cache identity, five-minute freshness, no-retry behavior, infinite
  continuation, item order, and complete flattening. The handwritten page adapter derives the existing `nextPage`
  value from canonical `pageInfo` and forwards cancellation.
- Notification views contain only fields rendered by the inbox. Session users contain only active session/profile and
  favorite fields. Provider, persistence, audit, and delivery state absent from canonical projections are not recreated.

## Optimistic, Push, Multipart, And Form Policy

Team and pool follow state retains its existing local flag, follower-count cache update, session refetch, rollback,
and final invalidation order. Notification deletion retains cancellation, complete infinite-page snapshot, optimistic
removal, error rollback, and settled invalidation.

Both onboarding and authenticated-session push flows share one generated registration function. The audited
caller-selected user identifier remains unchanged. Registration validates a physical-device build identifier before
calling canonical v2, which requires a non-blank device identifier; no installation-identity redesign, retry,
unregister, or logout behavior is introduced.

Profile and report image selection and manipulation remain owned by their existing Formik forms. The established React
Native adapter passes URI, filename, and MIME-type objects behind Orval's browser-oriented `Blob` signatures, while
generated FormData assembly owns canonical JSON and file parts. Profile mutation uses explicit picture-removal intent;
report submission uses a numeric local user identity and projects the provider-independent result.

`ProfileForm` and `ReportForm` retain their current Formik/Yup fields, touched state, validation text, image controls,
external submit registration, loading, feedback, and haptics. MRG-514 and MRG-515 remain the only owners of their React
Hook Form/Zod migrations.

## Compatibility And Rollback

Shared v1 case conversion and released-server v1 routes remain available until their approved retirement gates.
Before a production Expo v2 release, rollback may use the preceding Expo build and standalone v1 server images. After
such a release, the last-known-good dual-route mobile-gateway and owner-service images remain the server rollback
baseline. This task authorizes no store release, OTA update, EAS build, deployment, provider write, or traffic switch.

## Verification Evidence

- Mobile typecheck proves all twelve generated operations, wire schemas, projections, cache types, optimistic updates,
  and multipart adapters compose without exposing generated models to screen or session state.
- The existing form-boundary guard still reports exactly eight transition-only Formik/Yup forms; MRG-347 migrates
  profile and report transport only.
- Existing form contract tests, the complete REST contract suite, and OpenAPI source lint remain green.
- Two direct Orval generations leave generated output clean, and a fresh Expo export builds both Android and iOS
  Hermes bundles.
- Documentation, Nx project inspection, Maaatch comparison, source confinement, targeted formatting, and whitespace
  checks remain publication gates.

## Closed Scope

- No unused notification workflow is activated.
- No profile or report form is converted, redesigned, or extended.
- The active goal stops before Phase MRG-900.
