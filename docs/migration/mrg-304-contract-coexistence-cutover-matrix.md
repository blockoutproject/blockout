# MRG-304 — Contract Coexistence And Cutover Matrix

- Status: approved cutover specification
- Decision date: 2026-07-17
- Runtime effect: none
- Production effect: none
- Evidence baseline: MRG-268 and MRG-301 through MRG-303

## Purpose And Authority

This document fixes how Blockout REST and RabbitMQ contracts coexist while services and callers migrate to generated
camelCase boundaries. It is normative for later pre-production migration tasks, but it does not activate a route,
contract, generator, broker declaration, deployment, or production cutover.

The canonical target is `/api/v2/**` for REST and `<legacy-routing-key>.v2` for RabbitMQ. Existing `/api/v1/**` REST
routes and unversioned RabbitMQ routes remain legacy-only compatibility surfaces. Standalone repositories and current
production images remain authoritative until the later production phase receives separate authorization.

MRG-313, MRG-314, and MRG-315 select generation tooling only. They cannot reopen the coexistence topology, version
names, legacy isolation, provider-first order, rollback rules, or removal gates fixed here.

## 1. REST Coexistence Contract

### 1.1 Canonical v2

Every generated canonical REST operation:

- is exposed only below `/api/v2/**`;
- emits and accepts Blockout-owned JSON, query, and multipart JSON names in `camelCase`;
- uses generated transport DTOs at the API adapter and maps them to application-owned contracts;
- adopts Problem Details progressively, with stable `code`, HTTP status, and safe request identifier;
- preserves current authentication intent, success status, null, ordering, pagination, empty-result, fallback,
  partial-failure, and multipart behavior until a later behavior correction is explicitly approved.

No generated v2 model accepts legacy snake_case. No header, media type, or query switch negotiates v1 versus v2.

### 1.2 Isolated v1 adapter

Every existing `/api/v1/**` route remains a service-local legacy adapter. It delegates to the same application use case
as v2 but owns the complete legacy transport behavior:

- a dedicated adapter-local snake_case `ObjectMapper` for legacy JSON and multipart `data` parsing;
- legacy transport records or `JsonNode` when exact legacy shape preservation is required;
- explicit conversion at the adapter edge only;
- current v1 auth, status, error body, null, array/page wrapper, ordering, binary and multipart part behavior.

The legacy mapper is never a global Spring mapper and is never injected into generated APIs, application services,
domain code, persistence, outbound generated clients, or event serialization. Permanent `SNAKE_CASE` configuration,
`@JsonProperty`, `@JsonAlias`, generated-model conversion, and Expo-wide case conversion are forbidden as coexistence
mechanisms.

### 1.3 Provider-first deployment order

The order codes in the REST matrix are normative:

| Code        | Required order                                                                                                                                                                                     |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `O-INT`     | Deploy the owner service dual-route; validate v1 parity and v2 shadow calls; migrate generated backend consumers; migrate the BFF; then migrate Expo, worker, or scraper callers named in the row. |
| `O-BFF`     | Validate every required downstream v2 provider first; deploy a dual-route BFF; retain it as the rollback baseline; validate v2 facade calls; only then release an Expo v2 consumer.                |
| `O-UNKNOWN` | Deploy no consumer and remove nothing until the read-only production snapshot identifies or closes external callers; then follow `O-INT`.                                                          |

A consumer never ships before its provider's dual-route image is validated. A v1 adapter and v2 API must invoke the same
application behavior; duplicated business logic is not a compatibility mechanism.

### 1.4 Rollback states

| Code                        | Current rollback artifact                                                                      | Rollback after the first v2 consumer                                                                                                                             |
| --------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `R-OWNER:<service>`         | The last known-good standalone v1 image for the named owner service.                           | The retained last known-good dual-route image. Returning to v1-only first requires every consumer to be reverted to v1.                                          |
| `R-BFF:mobile-gateway+Expo` | The last known-good standalone mobile-gateway image and the currently supported store release. | The retained dual-route BFF image. It must continue serving every supported mobile version; a v1-only BFF is forbidden while any active mobile release calls v2. |

Rollback changes route selection before changing providers: stop or revert the newest consumer, confirm v1 traffic,
then roll back the provider only if necessary. Database, queue, cache, and vendor behavior remain unchanged by a REST
route rollback.

### 1.5 Telemetry and removal codes

| Code        | Required evidence                                                                                                                                                                                             |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `T-REST`    | Per operation and caller cohort: v1/v2 request count, status class, latency, compatibility parse failure, Problem Details code, and safe request ID. Never log tokens, multipart bytes, or personal payloads. |
| `T-MOBILE`  | `T-REST` plus app version, platform, supported-release cohort, and store-availability evidence.                                                                                                               |
| `T-UNKNOWN` | `T-REST` plus a completed production caller/base-URL inventory proving whether any external integration exists.                                                                                               |
| `G-REST`    | Every production caller is on v2 and the operation records 30 consecutive days with zero v1 traffic.                                                                                                          |
| `G-MOBILE`  | `G-REST` plus both minimum supported mobile versions are at least the first v2-compatible release and that release is confirmed available in both stores.                                                     |
| `G-UNKNOWN` | The caller unknown is closed, every discovered caller is migrated, and 30 consecutive zero-v1 days are recorded.                                                                                              |

Pre-MRG-900 cleanup may remove global and annotation-based conversions after canonical callers migrate, but it must
retain the isolated v1 adapters. Actual production v1 retirement belongs only to the separately authorized future
retirement task after its evidence gates close.

## 3. REST Release And Removal Gates

A vertical slice is releasable only after:

1. v2 source, generated server/client artifacts, application mapping, and deterministic generation pass;
2. the owner dual-route image proves v1 byte/behavior parity and v2 camelCase behavior;
3. every row-specific provider precedes every row-specific consumer;
4. the rollback image is retained and its route-selection procedure is exercised;
5. compatibility telemetry is live before the first consumer switches;
6. unused-looking and unknown-caller operations remain available until MRG-267/MRG-417 and the row's removal code close.

Internal v1 removal requires `G-REST` or `G-UNKNOWN` for every row on the route. BFF v1 removal requires `G-MOBILE`.
Removing a global naming strategy, annotation, copied DTO, or Expo converter does not imply that its isolated v1
adapter can be removed.

## 4. RabbitMQ Coexistence Contract

### 4.1 Names and ownership

- Existing unversioned exchanges, routing keys, queues, DLQs, and bindings are v1 and remain unchanged.
- v2 reuses `entity.lifecycle.exchange` and `user.follow.exchange`.
- A v2 producer routing key is the exact legacy key plus `.v2`.
- A v2 primary queue is the exact legacy primary queue name plus `.v2`.
- A v2 dead-letter routing key is the exact legacy DLQ routing key plus `.v2`.
- A v2 DLQ is the exact legacy DLQ name plus `.v2`.
- Q-11 through Q-13 and Q-16 through Q-17 receive no v2 queue.
- `teambypool.deactivation` receives no v2 channel or publication while it is orphan-only.
- No migration activates a listener that is absent from current source.
- `notification-service` exclusively declares the new v2 notification queues and bindings, including successors to
  Q-14 and Q-15; `matches-service` declares neither v2 notification queue. This removes the current declaration
  conflict from the new topology without mutating v1.

### 4.2 Publication and switching

Dual publication is allowed only from the completed transactional outbox path. One stored outbox event creates the v1
and v2 publications with the same event UUID:

- v1 body and properties remain unchanged except additive AMQP header `x-blockout-event-id`;
- v2 uses the approved envelope and properties selected by MRG-315;
- publication state is idempotent per event ID and route version;
- direct service dual-publish outside the outbox is forbidden.

A shadow v2 queue may validate schema, headers, ordering evidence, and deserialization only; it performs no business,
notification, counter, or Elasticsearch side effect. Live switching follows this exact sequence:

1. pause the outbox publisher for the route family;
2. wait until v1 primary deliveries are drained and no message is unacknowledged;
3. stop the v1 side-effect listener;
4. bind/start the v2 side-effect listener and verify readiness;
5. resume the outbox publisher;
6. observe v2 acknowledgements, DLQ flow, deduplication, and projections.

v1 and v2 side-effect consumers never run concurrently. Rollback pauses the publisher, drains v2, stops the v2
listener, restores the retained v1 binding/listener, and resumes publication. A schema-validation shadow consumer may
coexist because it has no side effects.

is reviewed in the future production-retirement task.
