# MRG-345 Expo Catalog Client Migration

- Status: implemented in the monorepo shadow baseline
- Owner: Expo mobile application
- Active BFF operations: nine club, team, and pool reads and mutations
- Production effect: none

## Purpose

MRG-345 migrates every active Expo consumer formerly backed by handwritten `ClubApi`, `TeamApi`, and `PoolApi`
methods to the canonical mobile-gateway v2 operations generated by Orval. Generated wire schemas validate every path,
query, command, and response, while handwritten projections keep transport models out of screens, caches, forms, and
navigation state.

The migration does not redesign the club, team, pool, ranking, map, or followed-item workflows. Existing TanStack
cache identities, freshness, retry, enablement, optimistic follower updates, explicit refetches, feedback, haptics,
ordering, and navigation remain application policy.

## Migrated Operation Set

| Operation ID | Mobile workflow     | Consumer boundary                        |
| ------------ | ------------------- | ---------------------------------------- |
| `BFF-P-01`   | read club profile   | public club detail                       |
| `BFF-P-09`   | read pool profile   | public pool detail, ranking, and map     |
| `BFF-P-10`   | list selected pools | followed-pool cards                      |
| `BFF-P-15`   | read team profile   | public team detail and embedded rankings |
| `BFF-P-16`   | list teams for club | club tabs and team-list screen           |
| `BFF-P-17`   | list selected teams | followed-team cards                      |
| `BFF-S-01`   | update club profile | deferred Club form transport             |
| `BFF-S-27`   | update pool profile | deferred Pool form transport             |
| `BFF-S-28`   | update team profile | deferred Team form transport             |

No generated catalog operation lacks an existing caller, so the full active handwritten method set is replaced. The
three handwritten clients and their `MobileGatewayApi` authentication propagation disappear; generated secure calls
continue to receive the existing Auth0 token supplier and single unauthorized-session callback through the shared
Orval mutator.

## Query, Cache, And Projection Ownership

- Detail queries retain `clubs`, `enrichedTeams`, and `enrichedPools` cache keys, zero freshness, initial cached data,
  and disabled/missing identifier behavior.
- Club team lists retain the `teamList` key and active-club response order.
- Followed lists retain their sorted identifier cache-key identity, five-minute freshness, empty-list disablement,
  no-retry behavior, and the BFF's set-derived result order and omission policy.
- Query cancellation signals now reach the generated transport.
- Generated list wrappers, enums, nullable enrichment, ranking rows, and narrow edit results are projected immediately
  into named handwritten mobile views.
- Ranking array position remains authoritative. No client sort, missing-row synthesis, or partial-result marker is
  introduced.
- Nullable division enrichment in team and pool lists remains explicit. Cards use a neutral fallback and omit the
  division chip/image when enrichment is absent instead of failing the whole view.

The club projection intentionally sets the legacy phone view to null because the canonical public BFF response excludes
phone data. Persistence state, audit timestamps, unused postal data, and ranking coefficients absent from canonical
consumer projections are not recreated.

## Multipart And Form Boundaries

Club and team image selection and manipulation remain owned by their existing Formik forms. The established React
Native adapter passes the URI, filename, and MIME-type object behind Orval's browser-oriented `Blob` signature, and
generated multipart assembly owns canonical JSON plus the optional image part. The generated commands make keep,
replace, and remove-logo intent explicit. Pool updates use the generated JSON command directly.

`ClubForm`, `TeamForm`, and `PoolForm` retain their current Formik/Yup fields, touched state, validation text, image
controls, external submit registration, loading, feedback, haptics, and explicit detail refetch after success. MRG-507,
MRG-508, and MRG-509 remain the only owners of their React Hook Form/Zod migrations.

## Compatibility And Rollback

The remaining handwritten Match, User, Search, Notification, and Report clients stay available for MRG-346 and
MRG-347. Shared v1 case conversion and released-server v1 routes remain available until their approved retirement
gates. Before a production Expo v2 release, rollback may use the preceding Expo build and standalone v1 server images.
After such a release, the last-known-good dual-route mobile-gateway and owner-service images remain the server rollback
baseline. This task authorizes no store release, OTA update, EAS build, deployment, or traffic switch.

## Verification Evidence

- Mobile typecheck proves the nine generated operations, wire schemas, projections, cache types, and multipart adapter
  compose without exposing generated models to the screen layer.
- The existing form-boundary guard still reports exactly eight transition-only Formik/Yup forms; MRG-345 migrates no
  form state or dependency.
- Existing legal form contract tests, the complete REST contract suite, and source lint remain green.
- Two direct Orval generations leave generated output clean, and a fresh Expo export builds both Android and iOS Hermes
  bundles.
- Documentation, Maaatch comparison, source confinement, targeted formatting, and whitespace checks remain publication
  gates.

## Closed Scope

- No OpenAPI source, generated artifact, Orval configuration, dependency, environment value, route, native plugin,
  backend, database, event, scraper, standalone repository, production, or Maaatch change.
- Search results remain assigned to MRG-347 even when they render club, team, or pool cards.
- Competition and match callers remain assigned to MRG-346.
- No catalog form is converted, redesigned, or extended.
- The active goal stops before Phase MRG-900.
