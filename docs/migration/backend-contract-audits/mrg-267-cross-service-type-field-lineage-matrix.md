- Scope roots: `docs/migration/backend-contract-audits/mrg-252-*.md` through

- Audited deployables and workflows: all twelve Spring Boot modules, both Python scrapers, the Expo transport and

- Runtime mutation: none
- Evidence limitations: this matrix consolidates the checked-out source and caller evidence. Production telemetry,

## Purpose and Decision Boundary

This document consolidates the atomic audits into one cross-service register. It answers three questions without
changing code:

1. which current types duplicate the same concept across services, the BFF, Expo, scrapers, workers, events, stores,
   and vendors;
2. where each duplicated or unused-looking field is actually required, derived, compatibility-only, vendor-owned,
   persistence-only, event-only, or removable; and
3. which evidence must exist before a copied type, field, casing bridge, or annotation can be retired.

The atomic field rows in the source audits remain authoritative. A grouped row below is exhaustive for the fields it
names and inherits the cited audit's evidence status. A slash-separated or comma-separated field list does not weaken
the classification: every named field receives that row's primary classification at that specific boundary.

Classification is boundary-local. The same field name may legitimately have different classifications. For example,
`createdAt` is `REQUIRED` for the users-service live-link age policy, `PERSISTENCE_ONLY` for several other entities,
and `COMPATIBILITY_ONLY` when copied into a BFF response with no proven mobile read. No classification authorizes a
runtime deletion.

This task does not approve records, MapStruct, package layouts, batching, target pagination, compatibility duration,
event tooling, Orval options, Python generation, or service migration order. MRG-268 owns those architecture decisions.

The desired end state contains no global Blockout case converter and no Jackson property annotation whose sole purpose
is permanent snake_case compatibility. Temporary reads are allowed only when MRG-304 records the exact boundary,
supported caller, rollback window and removal task.

## 7. Removal and Migration Gates

A field or type classified `REMOVABLE` above still waits for the following gates in its owning implementation slice:

1. the atomic source audit and this matrix identify the exact boundary, not merely a same-named field elsewhere;
2. MRG-301 through MRG-303 inventory the deployed REST, event, client and casing surfaces;
3. MRG-268 approves the target role and MRG-304 approves coexistence, rollout and rollback;
4. the source contract and generated consumer model exclude the field intentionally;
5. all known backend, BFF, Expo, scraper, worker, event and external callers have migrated or are proven absent;
6. compatibility fixtures preserve status, error, null, ordering, pagination, multipart and partial-failure behavior;
7. the old and new paths run with parity evidence for the supported version window;
8. production data is checked before a database or store field is removed;
9. the owning compilation/build, generated no-diff checks and relevant existing tests pass; and
10. the rollback path no longer requires the legacy field.

`COMPATIBILITY_ONLY` is stricter: it cannot become `REMOVABLE` until caller/version evidence closes its compatibility
purpose. A repository search is insufficient. `PERSISTENCE_ONLY`, `EVENT_ONLY`, and `VENDOR_OWNED` fields must not be
copied into public OpenAPI just because they exist, but they also must not be deleted from their owning boundary by a
REST cleanup.
