# Blockout V1 functional inventory

## Purpose and authority

This inventory records the functional baseline for the V2 rebuild scoped by [#252](https://github.com/blockoutproject/blockout/issues/252). It is discovery evidence, not an accepted feature specification or a V2 architecture. The [constitution](../../.specify/memory/constitution.md) governs future intent. The [roadmap](https://github.com/blockoutproject/blockout/issues/245) owns sequencing; all functional specifications must be accepted before technical planning and implementation.

Read the capability register first, then the ingestion rules and discrepancies. The coverage appendices connect the register to mobile routes, every source-contract operation, automatic jobs and Figma journeys. Capability identifiers below are document references, not Spec Kit task identifiers.

### Baseline and evidence limits

- Repository snapshot examined: `a67b615cc293b757fd71d8a055b6b4b7cc7cacaa` on `develop`. Relative source links describe that snapshot; subsequent code may change.
- Owner confirmation during the September 2026 framing: the repository was reorganized from multiple repositories into a monorepo without changing functional logic. The owner accepts this checkout as the functional reference for discovery. This is an owner assertion, not an independently verified production deployment match.
- The mobile manifest declares version `1.3.5`. Exact installed store build identifiers, deployed backend/scraper image digests and effective production configuration were not independently established. No live production transactions or destructive provider operations were performed.
- Selected production Auth0 and RevenueCat settings and account samples were subsequently inspected read-only on 2026-09-15; see [identity and Pro continuity](identity-and-pro-continuity.md#production-settings-and-sample-observations) for the exact coverage and limits. Complete store configuration, Grafana and hosting remain unaudited. Source defaults are not proof of effective production values. The owner reports predominantly manual monitoring with Grafana.
- Figma evidence is structural inspection of current pages, named screens and representative states, not an exhaustive visual/prototype interaction audit. Pro purchase/restoration and the followed-entities list remain to be designed, as confirmed by the owner.
- Tests cited here were inspected as evidence; this documentation change does not claim that the entire application test suite or production behavior was exercised.
- No archived or external repository was consulted. Production acceptance and document review belong in the issue/PR, not a duplicated status ledger here.

### How to interpret statements

**Observed** means source, contract or test evidence. **Owner-confirmed** means an explicit statement from the product owner during framing. **V2 addition** means an explicitly requested behavior absent from the V1 baseline. **Gap** means a discrepancy, unverified boundary or decision for later specifications. An existing implementation or characterization test does not by itself authorize reproducing an undesirable behavior.

## Ingestion and lifecycle rules

### Acquisition and classification

FFVB pool discovery handles departmental, regional and national source structures; regional/departmental discovery explicitly excludes league codes `LIGU`, `LIGY`, `LIMART`, `LIMY` and `LIRE`. At the inventory baseline, the reason and desired V2 inclusion were not owner-confirmed. The subsequent owner decision retains all five exclusions; see the [source acquisition specification](../../specs/001-source-acquisition/spec.md#coverage-and-discovery), FR-001 and A01. This does not establish the historical reason for those exclusions. This is not an inventory of every French competition. Ingestion deduplicates league/pool links and skips pool links missing a usable season or code; the professional path enriches AALNV data. Calendars are obtained by POSTing season/league/pool parameters to the CSV export endpoint, decoding Windows-1252 semicolon-separated content. This CSV acquisition method is an explicit retained constraint. It does not mean that every datum comes from CSV: rankings, discovery, club contacts and professional enrichment also use HTML/XML.

A raw division mapping belongs to a source league, season and raw label. The operator supplies division, format and gender. A newly discovered/unmapped pack is registered but not ingested as a guessed division. The owner manually prepares each season and standardizes presentation. A pack can exceptionally contain pools from different divisions; the current shared mapping is then imprecise. No automatic pack splitting is selected here.

Evidence: [FFVB discovery][discovery], [CSV parser][csv], [league ingestion][league-ingestion], [mapping service][mappings].

### Values, precedence and standings

For ordinary CSV ingestion, source candidates update date, score, set result, team/pool association, venue and referees through the change accumulator. The professional path enables field-specific priorities: XML updates date/score/set result; HTML updates the live code; FFVB supplies association, venue and referees subject to existing priority/null checks. Initial creation also supplies candidate values. Enum priority numbers alone are not a complete precedence specification.

LNV loads match and ranking XML before its enrichment, and an empty required dataset can stop that processing. HTML live enrichment uses names/aliases and date matching. Owner-confirmed incident: occasional professional rescheduling appears on the official LNV page before XML/CSV, with propagation latency reported up to roughly two hours. This is not a time-zone offset, a measured service-level objective, or proof that HTML scores are currently ingested.

The current calendar path always requests official ranking statistics. Numerical parsing can replace invalid/missing values with zero; the ranking `MAX` coefficient sentinel is represented as `1000.0`. Compact tables lack some win/loss breakdown columns and fill them with zero. The parser does not preserve an explicit official position, and current CSV association updates set `points_penalty` to zero. The gateway then sorts the statistics. Owner intent is the official standing, with no discrepancy observed. The separate local match-statistics helper must not be mistaken for the active authority for standings merely because its code/tests exist.

Match creation determines upcoming/finished from absence/presence of a set result. Updates publish the finished event on an upcoming-to-finished transition. Removing the result does not explicitly reverse status. This behavior needs a fixture and a later product decision; it is not declared an observed production incident.

Evidence: [match merge][match-changes], [LNV][lnv], [ranking parser][ranking], [pool composition][pool-gateway], [match application][matches].

### Dates, seasons and displayed live state

These rules refine V1-04–V1-13; listing the enclosing screen or API is not sufficient evidence for them.

- **Provider timestamps:** CSV dates are parsed as `YYYY-MM-DD HH:mm`, interpreted in Europe/Paris and converted to UTC, except literal `00:00`, which is directly attached to UTC. Invalid values produce no parsed date. The meaning of the midnight exception (real kickoff versus unknown-time sentinel) is not confirmed. This is separate from the owner-reported LNV propagation latency.
- **Calendar pagination:** page size selects distinct match days, not a fixed number of matches. Upcoming days ascend and finished days descend. Application date windows use Europe/Paris; database date extraction and mobile formatting are separate boundaries. Their behavior around midnight/daylight-saving changes or a device in another zone was not exercised.
- **Mobile date labels:** match timestamps use device-local formatting, while relative day headers compare date-only values against the current UTC date. This can differ from the backend's Paris-day boundary; no production incident is claimed.
- **Season choices:** search hardcodes `2026/2027`, `2025/2026`, `2024/2025` and starts with no season filter. The shared season selector used for the club-team list derives available seasons from returned items, sorts descending and defaults to the latest available; it retains a selection while it remains available. There is no established central season-discovery contract in these paths.
- **Live versus replay:** the mobile match row shows `Live` when a live URL exists and the match is not finished, and `Rediffusion` once it is finished. Elapsed kickoff time also produces a presentation flag, but these computations do not query a streaming provider or prove that a broadcast is currently running.

Evidence: [timestamp normalization][normalization], [match application][matches], [match queries][match-repo], [mobile dates][match-date], [search filters][search-filters], [season selection][season-filter], [score/status presentation][score-presentation].

### Source fields versus manual presentation

Owner-confirmed rule: a manually corrected display name takes precedence without overwriting the original source name. Club logo is the default inherited by its teams, with an optional team override.

Observed implementation is weaker: team/pool writers compare a subset of source fields to decide whether to update, but their HTTP adapters serialize display names as well. Team update also serializes the candidate logo URL; the Java update can clear a missing logo. Thus an unchanged scrape can leave an override untouched while a later source change/reactivation can overwrite it. The club merge directly replaces the display name from its provider record while preserving logo in the writer. Team aliases can also canonicalize `raw_name`, so that field is not necessarily a verbatim copy of the original CSV label. Do not infer protection from the writer's comparison list alone.

Evidence: [team writer][team-writer], [team adapter][team-adapter], [team owner][teams], [pool writer][pool-writer], [pool adapter][pool-adapter], [club merge][club-ingestion], [club writer][club-writer].

### Client refresh and report submission details

- **Match refresh (V1-09/V1-10):** the match screen refreshes when focused, on explicit pull-to-refresh, and when the app returns from inactive/background to active while that screen is focused. Its entity query can start from cached data, treats that data as stale immediately, and disables automatic query retries. These triggers do not establish a continuous live-score stream or a guaranteed freshness interval. Evidence: [match refresh][match-refresh], [entity query][entity-query].
- **Report submission (V1-15):** category, trimmed title and description are required in the mobile form. The request includes screen context, app version, device model and OS, plus business user ID/pseudo when available (otherwise guest identity). Images are selected from the image library and resized to width 1280, then encoded as JPEG before upload. These are existing diagnostics/attachment behaviors, not a new telemetry requirement. Backend image-type/size checks remain separate. Evidence: [report form][report-form], [report service][reports].

### Advertising, legal content and support privacy evidence

V1-17 has separate navigation and external-link interstitial counters; its controller resets on actual presentation and releases pending navigation on failures. Consent preparation and subscription hydration are separate state boundaries: a hydrated/degraded client is not proof of free entitlement. [F11](../../specs/004-advertising-privacy-legal/spec.md) owns the common ten-action rule and advertising/privacy requirements; those requirements are not a claim that the V1 implementation already satisfies them.

V1-21 includes the [mobile legal editor][legal-screen], not only a backend operation. Stored document version is a free-form string, distinct from the actual update timestamp. Seed texts do not establish production legal content or an acceptance ledger.

V1-15 reports currently have no reply-email field or structured target context. Some screen contexts depend on a successfully loaded entity, and the match report entry point is unavailable in its failed-load branch. The [report service][reports] creates GitHub issues and links separately stored images; repository and object visibility in production have not been inspected. Neither issue creation nor deleting a business user proves coordinated erasure of those files. F10 owns the reporting journey; F11 FR-028–FR-034 and A20–A24 specify its accepted contact, context, privacy and operator-workflow constraints.

## Confirmed V2 constraints and additions

These statements come from owner decisions during framing, not reverse-engineering:

- Rebuild the backend for complete functional parity, with freedom to replace implementation radically where beneficial. KISS means an appropriate, reliable and optimal system, not minimal structure at any cost. Potential future fantasy/pronostics/social functionality is context only, not present scope.
- The established mobile journeys/content remain the product constraint. Figma determines the redesign; missing Pro/followed-list designs must be completed without silently dropping V1 capabilities.
- All functional specs must be completed and accepted before architecture/technical plans or implementation. Use the installed official Spec Kit procedures when those steps are reached; this inventory adds no alternative workflow.
- One-time business-data/account reset is allowed for migration. Auth0 identities remain. This is distinct from ordinary user-requested account deletion and from retaining history after V2 starts operating. Irrecoverable old V1 sporting history need not be migrated; this exception does not weaken preservation of V2-acquired history, valid paid access or manually associated club logos. F14 must preserve club references, logo URLs and files before reset, apply only certain identity matches and retain unresolved associations. Other manual V1 presentation customizations are not included in this migration requirement.
- Existing paid Pro users must keep access. Use Liquibase rather than Flyway for the future schema; no schema or migration is implemented here.
- **V2 addition:** the owner must be able to grant Pro manually through RevenueCat in the first V2 release. [F09 FR-027–FR-030](../../specs/006-pro-subscriptions/spec.md) defines immediate temporary/non-expiring grants, changes, revocation, private traceability and independence from paid billing. No Blockout grant screen or moderator authorization is introduced; later delegation requires an explicit decision.
- **V2 addition:** users must be able to submit feature suggestions in the first V2 release. The exact form/category and processing behavior remain specification decisions.
- [F13](../../specs/003-shared-quality/spec.md) defines the approved quality and operations requirements, including 1,000 active users at about 100 user actions per second for one hour, useful consultation within two seconds in 95% of cases, propagation within one minute after acceptance and 99.5% monthly availability. These are V2 objectives, not measured V1 results or a selected monitoring vendor.
