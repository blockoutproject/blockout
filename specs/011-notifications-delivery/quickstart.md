# Quickstart: Qualify notifications, inbox and push

Follow the [local development setup](../../README.md#local-development) and use the [repository verification commands](../../README.md#verification). The [model](data-model.md), [contracts](contracts/README.md) and [plan](plan.md) define the states and selected mechanisms.

## Prerequisites

Use migrated isolated PostgreSQL, fictional usable/deleted accounts, overlapping follows and accepted sporting transitions. Use F13's generated Java/mobile consumers with JUnit/Spring MVC/Testcontainers and Jest Expo/React Native Testing Library. Controlled provider I/O permits local qualification; it does not establish physical delivery.

Physical push checks require development/release binaries on physical iOS and Android, isolated nonproduction credentials/destinations and known test accounts. Do not use real user payloads or Expo Go as delivery evidence. Restoration additionally requires an authorized source/destination, a qualified backup and masking under [F13](../003-shared-quality/quickstart.md#initial-restore-and-activation-condition).

## Inbox traversal qualification (T025)

After contract generation, run the actual generated HTTP/SQL and mobile navigation boundaries:

```sh
./mvnw -B -ntp -pl apps/backend verify -Dtest=NotificationsWebMvcTest,NotificationAccessWebMvcTest,NotificationContractWebMvcTest -Dit.test=InboxTraversalIntegrationTest,ReadInboxIntegrationTest,MarkNotificationReadIntegrationTest
NX_LOAD_DOT_ENV_FILES=false EXPO_NO_DOTENV=1 npm run test --workspace=@blockout/mobile -- --runInBand --reporters=default
```

Exercise the inbox rows in the scenario table through the actual F03 destination. Expect stable continuation after anchor removal, whole-inbox counts independent of loaded pages, true-only read intent, independent read/navigation outcomes and strict active/offline expiry. Native system badges and provider receipt require the physical cases below; synthetic HTTP/native SDK inputs cannot establish them.

## Retention and isolated restore

Run age-boundary and failure cases with a controlled clock and migrated PostgreSQL. Expect one atomic fixed-cutoff pass, no confirmed count after an uncertain commit, strict age-29 exclusion despite physical cleanup failure and another attempt at the next ordinary daily pass. ## After-commit push

Run the selected SDK, current-eligibility, HTTP and transaction boundaries with controlled external I/O:

```sh
./mvnw -B -ntp -pl apps/backend verify -Dtest='PushDeliveryTest,ExpoPushClientTest,PushDeliveryConfigurationTest' -Dit.test=PushDeliveryIntegrationTest,ExpoPushTransportIntegrationTest
```

Exercise the push and destination rows above. Expect no handoff before commit, current F12 admission before each batch, exact association invalidation only for `DeviceNotRegistered`, one ordinary send and one delayed receipt observation. Refusal, timeout, restart or maintenance must create no resend/catch-up work. The [operations guide](../../infra/operations/README.md#sporting-push-inputs-and-failure-limits) owns activation inputs, bounds and safe diagnostics.

## Physical push preparation

Execute T041 only with authorization for the exact isolated Expo/Apple/Firebase environments, test accounts, physical devices and matching native binaries. Use the [credential procedure](../../infra/operations/README.md#sporting-push-inputs-and-failure-limits). The notifications config plugin requires a compatible native binary. Simulator/emulator support does not replace physical iOS/Android qualification.
