# Validation guide: acquisition and source operations

The executable F13 workspace and F01 admission/transport foundations are available. Use the [README verification commands](../../README.md#verification) for implemented boundaries and [tasks.md](tasks.md) for completion state. The scenarios below define end-to-end qualification as their owning implementations become available; passing foundation checks does not establish provider coverage or complete acquisition/integration.

## Prerequisites

Use an isolated environment with the F13 backend, PostgreSQL and single collector instance, generated consumers from the same [canonical contracts](contracts/README.md), a collection-authorized operator and accounts without that right. Prepare deterministic sanitized/synthetic FFVB, LNV and IGN fixtures, controlled transport responses and a controllable test clock. No personal provider payload belongs in Git. Live-source qualification requires its own authorized scope and is not a CI dependency.

Verify the actual F01 → F02 → F03 handoff for a published empty standings table, qualified `not-published`, and unreadable/unavailable acquisition. Start both with and without a usable retained table; retain its own freshness on failure or non-publication, reject stale or contradictory absence input, and never turn a failed read into qualified absence. Carry a supplied `providerPublishedAt` through JSON observations and image metadata; verify unknown publication time is not inferred and a later publication timestamp cannot override an older logical observation token.

## Boundary evidence

Use JUnit for source interpretation and clock-driven eligibility, Spring MVC for contract/authorization behavior, and Testcontainers PostgreSQL for real transaction ordering, incarnation replacement and constraints. Generate and compile Java server/client and mobile outputs; check enums, date/absence/null semantics, unknown request fields, additive response fields, deterministic regeneration and no generated files in Git.

On physical iOS/Android builds, verify the approved collection journeys with existing Expo testing tools: pending versus running, explicit retry after reread, preserved selection/input, permissions, light/dark, narrow widths, text enlargement and screen-reader actions. Prototype/Figma approval proves the reviewed experience, not these native behaviors. Use provider qualification on representative supported current/historical formats before treating their coverage as operationally available; sampled fixtures do not prove exhaustive reconstruction.
