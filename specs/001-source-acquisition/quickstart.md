# Validation guide: acquisition and source operations

Follow the [local development setup](../../README.md#local-development) and run the [repository verification commands](../../README.md#verification). Use the prerequisites and scenarios below to qualify acquisition end-to-end; shared checks alone do not establish provider coverage or complete acquisition/integration.

Native accessibility verification follows [F13 FR-030](../003-shared-quality/spec.md#platforms-accessibility-and-bounded-continuity).

## Prerequisites

Use an isolated environment with the backend, PostgreSQL and single collector instance, generated consumers from the same [canonical contracts](contracts/README.md), a collection-authorized operator and accounts without that right. Prepare deterministic sanitized/synthetic FFVB, LNV and IGN fixtures, controlled transport responses and a controllable test clock. No personal provider payload belongs in Git. Live-source qualification requires its own authorized scope and is not a CI dependency.

## Discovery and professional adapter checks

Run the backend and collector targets from [repository verification](../../README.md#verification). Use controlled source/HTTP responses for refusal, partial-result, clock and cache cases; run provider qualification separately with authorized current and historical sources.

Verify seasonal attribution before consuming a shared catalog. Reject isolated rounds used as seasonal roots, contradictory seasons and unrelated championship contexts. Shared indexes are read once per passage and retain their original timestamp/ordinal; failures remain failures for every affected pool until the next passage. Preserve exact document-team associations scoped to season, championship and native team. Empty configuration supplies no auxiliary XML code or historical association.

Confirm admission before provider work and allocate ordinals before reads. A lost admission response starts no provider work or confirmation read; later polling follows backend eligibility. Conflict inspection preserves the original refusal when unavailable and stops confirmed supersession.

### Source preparation and seasons

Use the existing preparation/validation/launch commands and generated consumers in an isolated backend, collector and PostgreSQL environment. Select supported official seasonal roots through the [source policy](research.md#ffvb-source-patterns); do not infer missing seasons or classifications from a successful launch.

1. Prepare current and historical sources independently. Open the seasonal provider destination with a successful empty control list; expect source preparation without creating a control from GET. Failed or denied lists remain failures.
2. Edit/save a candidate and validate it. Expect previous qualification to disappear and pending validation to be readable through the same binding. Reject a wrong organizer, season, host or format.
3. Launch only qualified selected roots, including a newly prepared source in an already ACTIVE season. Expect used references to become locked, without enabling a paused family or assigning classifications.
4. Classify an individual discovered pool using the existing F02 flow while its parent pack remains unclassified. Request only that source/scope; expect no neighboring unclassified calendar import or automatic second passage.
5. Repeat across simultaneous active seasons. Expect independent references, controls, classifications and current results.

Use the real native operator journey with current F05/F12 admission and collection grants; sporting-classification rights alone must not supply collection powers. Qualify the F01 → F02 → F03 handoff through generated HTTP and actual owner transactions. Provider content, native operator interaction and collector service authentication require their own actual boundaries.

### Professional sources

Select current championship roots from the [official LNV entries](research.md#lnv-coverage-time-and-images) and historical roots from their published archive links. Follow each root's published regular/playoff phases without guessing identifiers. Exact-season confirmation may supply missing seasonal attribution only after structure/scope checks; it cannot establish parser compatibility or unknown phases.

Run the ordinary collector and F02 acceptance with periodic controls disabled for the isolated reconstruction. Read every F03 calendar page and compare exact match/team/pool/season identities, participant links and official standings. Expect no duplicate traversal identity or cross-season association. A bracket without a published standings table remains `not-published`; its calendar and participants remain usable.

Verify scoresheet/statistics references and the document-only information-sheet associations separately. Historical facts never come from current XML. Unavailable-file notices supply no replacement locator; unknown missing links remain structural refusals. Public F03 actions expose Blockout subresources without supplier locators, and collection fetches no PDF body.

Compare pinned-offset calendar/detail clocks, date-specific Europe/Paris conversion, partial dates, unknown-time flags and UTC date changes. A later supplier correction remains authoritative under the accepted logical ordering. Use the [F03 document boundary](../007-sporting-consultation/plan.md#maps-and-documents) for native relay/reader behavior. Representative sources establish only their supported formats and scopes, not exhaustive archives or cutover readiness.

## Club and geocoding

Run `npx nx run backend:test` and `npx nx run collector:test` from the [verification setup](../../README.md#verification). For focused scheduling/integration checks, use:

```sh
./mvnw -B -ntp -pl apps/backend verify \
  -Dtest=CollectionCadenceTest -Dit.test=ClubAcquisitionIntegrationTest
```

Use a controlled clock to verify immediate first club reads, the exact 24-hour deadline including after failure, independent seasonless controls and new permitted needs at the next minute opportunity. Geocoding technical failures retain hourly eligibility; unchanged final empty/ambiguous contexts are suppressed except for explicit unresolved-only reruns. A newer accepted F02 result remains authoritative even when its F01 acquisition acknowledgement is lost.

Follow the [FFVB club-sheet grammar](research.md#ffvb-source-patterns) with synthetic multiline/omitted address and postcode examples. Expect exact textual club identity, per-field unknown/empty/invalid outcomes and no league or named-person contact substitution. Ambiguous unmarked lines must not become guessed municipalities.

Exercise a unique full-address result, absent address and qualified empty/ambiguous address followed by municipality lookup. Expect no fallback after transport/malformed-response failure, no provider call without a permitted city and the same current locality revision in the result. Effective address/city/postcode changes invalidate old responses; masked source changes do not. A unique municipality fallback is a valid located result without normal-rerun recalculation. Address remains absent from cycle snapshots and diagnostics.

Check the supported IGN singular `detail` and plural `details` error envelopes, rejecting conflicting/additional errors as technical failures. Keep acquisition outcomes separate from F02 secondary-field refusals and uncertain writes; response loss permits no mutation replay. Qualify representative FFVB/IGN source compatibility under the [selected provider policy](research.md#club-geocoding) with separately authorized inputs; keep personal provider fixtures out of Git.

## Ordered uncertainty cases

Run these cases in an authorized isolated collector/backend environment. Do not inject faults against FFVB, LNV, IGN or a shared environment. Use the generated collector client, a local HTTP fault peer and the actual migrated PostgreSQL/F02 owner. Control the response **after** the indicated commit, and count writes independently of received responses. Keep accepted business facts and source locks throughout.

Use the [disposable runtime command](../../README.md#collector-to-sporting-qualification) with `-Dit.test='CollectorUncertaintyIntegrationTest,CollectorSportingBoundaryIntegrationTest'`. The uncertainty peer closes before forwarding or after the backend's committed response; the fencing cases separately hold actual SQL transactions.

1. **Admission response lost:** let the backend commit RUNNING, then drop its response. The collector exposes no provider capability and sends no confirmation GET. Current backend RUNNING excludes further admission until explicit restart. Repeat with failure before commit: a later ordinary poll may allocate a fresh UUID. Backend atomic admission still rejects stale concurrent polls.
2. **Sporting write response lost:** commit one F02 match transaction, then drop the response. Keep that accepted match and independently successful matches. Record unconfirmed integration; never resubmit the mutation or replay the passage. Attempt ordinary completion for the passage. A later ordinary eligible cycle may recover facts still published, subject to newer observation/visibility guards; it cannot reconstruct lost user corrections or custom image bytes.
3. **Completion response lost:** commit completion and drop its response. Report ordinary failure without a confirmation GET or repeated write. The next ordinary poll may admit eligible work because backend completion is authoritative. Repeat with failure before commit: backend RUNNING continues to require inspection/restart.
4. **Validation-result response lost:** commit qualification and completion together, then drop the response. Report failure without same-cycle confirmation or control-completion substitution. Current backend state owns eligibility on later polling; unfinished validation needs inspection/restart and a fresh explicit validation intent.
5. **Replacement during a held transaction:** hold a real F02 transaction after its shared runtime fence and before domain commit. Start registration of a different startup UUID with the current runtime revision. Observe its PostgreSQL lock wait, release and commit the first transaction, then confirm replacement. The committed fact survives; subsequent old-incarnation results, details and terminal writes are refused. Repeat admission versus exact-label closure in both lock orders: closure first prevents admission; admission first permits only that running selected work to finish once.

For every case, retain the original cycle/candidate identity privately, check actual SQL effects and HTTP call counts, and separate confirmed acceptance, refused acceptance and unresolved outcome. Availability evidence does not identify an instant crash: no heartbeat, watchdog, retry worker, sweep, checkpoint or broad reset is involved. An empty/unexecuted selection supplies no failure or recovery observation.

Use the [operations guide](../../infra/operations/README.md#collection-inspection-and-explicit-recovery) for inspection and explicit restart after the integrated fault cases; keep accepted facts and uncertain outcomes distinct.

## Bounded initial reconstruction

The backend's `initial-reconstruction` profile runs one Spring `ApplicationRunner` action with native configuration binding, then closes its context. It starts no HTTP server, F04 projection scheduler, notification-retention pass or link-announcement schedule. It has no provider client, bootstrap account, import endpoint, archive crawler or automatic follow-up. The existing collector alone reads the explicitly admitted references with its ordinary adapters and limits. The serving backend remains the sole search-index writer.

Use an explicitly authorized isolated destination, its migrated PostgreSQL 18.6 database, one collector and an existing account currently granted `collection.manage`. Export the backend environment as documented in [local development](../../README.md#local-development); Spring does not load dotenv. Keep the operator UUID, connection settings and command output in ignored private runtime files. Override isolation settings only in the process or a private runtime copy. No command below authorizes actual provider access, restoration, reset, logo reassociation, production reconstruction or transition.

After building the backend through the [existing verification target](../../README.md#verification), invoke the same executable for each action:

```sh
java -jar apps/backend/target/backend-0.0.0-SNAPSHOT.jar \
  --spring.profiles.active=initial-reconstruction \
  --blockout.reconstruction.operator="$OPERATOR_UUID" \
  --blockout.reconstruction.action=prepare \
  --blockout.reconstruction.start-year=2023 \
  --blockout.reconstruction.provider=FFVB \
  --blockout.reconstruction.organizer-reference="$OFFICIAL_ORGANIZER" \
  --blockout.reconstruction.candidate-url="$VERIFIED_ARCHIVE_CANDIDATE"
```

Supply each sporting start year explicitly; for example, 2023, 2024, 2025 and 2026 for a 2026/2027 four-season scope. Do not derive a year from today's date or a provider ID. Preparation reuses canonical seasons and their exact labels, creates only missing PREPARING bindings and requests ordinary asynchronous validation. Reusing the same qualified/locked reference preserves its evidence; a conflicting locked reference or closed season is refused. Wrong-host, unsupported-format and wrong-season evidence remains refused by the existing collector validation. Where compatible structure lacks seasonal attribution, use `action=confirm` with `source-id`, the current source `revision` and exact canonical `label`; confirmation cannot override invalid evidence.

Read the returned/current source and season state before continuing. A missing archive remains a coverage gap, never a current-feed substitute. Missing classification uses the [existing F02 flow](../002-sporting-data/quickstart.md); this command grants no classification permission. A first explicit discovery passage may establish child identities, but imports no unclassified calendars and queues no second passage.

```sh
java -jar apps/backend/target/backend-0.0.0-SNAPSHOT.jar \
  --spring.profiles.active=initial-reconstruction \
  --blockout.reconstruction.operator="$OPERATOR_UUID" \
  --blockout.reconstruction.action=request \
  --blockout.reconstruction.season-id="$SEASON_UUID" \
  --blockout.reconstruction.revision="$SEASON_REVISION" \
  --blockout.reconstruction.sources="$SOURCE_BINDING_UUIDS"
```

`sources` and `scopes` lists use comma-separated UUIDs. `sources` is mandatory and exact; `scopes` optionally selects previously failed scopes beneath those roots. An identical pending selection returns the same request; a conflicting selection is refused. Acceptance is pending intent, not a supplier observation. On first admission the existing collector freezes only that selection, locks used qualified references and leaves periodic activity disabled and history PREPARING. Classification, division activity, coverage and current restrictions remain effective. A narrower retry updates only its selected current results; untouched failures remain visible. A logo-only retry rereads its qualified parent calendar to resolve the selected native team image, then submits only that image. Admission rechecks PREPARING even if a launch occurred after the request.

Use `action=report` with `season-id`, optional zero-based `page` and `size` (1–200; default 200). Read further pages while `hasNext` is true. The application view used by F14 retains current requested, obtained, rejected and unavailable evidence by source/scope/stage/phase, measured counts or explicit absence, and original logical ordering. Acquisition and integration remain independent. Candidate transport failures and uncategorized legacy failures are unavailable; explicit structural/context refusals are rejected. Unconfirmed work is unavailable after completion; an interrupted original context is not success. Ordinary periodic results cannot overwrite this report. No report certifies exhaustive provider coverage or migration readiness.

For closure, use `action=close`, `season-id`, the freshly read season `revision` and exact canonical `label`. Closure is definitive: it cancels unstarted intent and refuses new validation, launch or collection; only already admitted selected work may finish once. It preserves history, reference locks, other seasons and seasonless controls. After a lost command acknowledgement, read current source/control/coverage state before an explicit decision; do not blindly replay a command or allocate another cycle.

The serving backend's [ordinary complete F04 rebuild](../../infra/operations/README.md#search-projection-and-reconstruction) covers operator-side PostgreSQL changes. Verify current filtered searches and aliases through that existing owner before relying on search; the non-web command never starts a second index writer. F14 owns review of gaps and any actual launch/closure/cutover authorization.

Validate the command against a disposable migrated database and real F01/F02/F07 owners. Missing qualification, revoked grants, closed history, source conflicts and blank/foreign narrowing must be refused without widening work. Explicit preparation may renew an interrupted candidate validation; it adds no automatic recovery.

Verify discovery-only work, exact pending selection, lost admission acknowledgement, independent failures, narrower retries including one team logo, interrupted/unconfirmed coverage, periodic-result isolation and closure with admitted draining. Expect initial finished facts to suppress announcements, classification refusals to remain rejected and unavailable acknowledgements to remain distinct. A published empty initial standings read retains accepted rows and their usable-table timestamp while advancing publication attribution. A logo-only retry changes no neighboring coverage or calendar facts.

Use the serving backend's ordinary full-rebuild owner for the F04 handoff. The non-web command must start no second HTTP server or projection writer. Controlled owner checks do not establish actual supplier coverage, Auth0, notification delivery, logo reassociation or migration readiness; F14 owns any actual transition decision.
