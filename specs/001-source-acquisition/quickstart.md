# Validation guide: acquisition and source operations

Follow the [local development setup](../../README.md#local-development) and run the [repository verification commands](../../README.md#verification). Use the prerequisites and scenarios below to qualify acquisition end-to-end; shared checks alone do not establish provider coverage or complete acquisition/integration.

## Prerequisites

Use an isolated environment with the backend, PostgreSQL and single collector instance, generated consumers from the same [canonical contracts](contracts/README.md), a collection-authorized operator and accounts without that right. Prepare deterministic sanitized/synthetic FFVB, LNV and IGN fixtures, controlled transport responses and a controllable test clock. No personal provider payload belongs in Git. Live-source qualification requires its own authorized scope and is not a CI dependency.

## Discovery and professional adapter checks

The collector suites `FfvbDiscoveryTest`, `DiscoverSeasonSourcesTest`, `QualifySourceTest`, `LnvObservationsTest`, `LnvHttpCachingIntegrationTest`, `LnvObservationReaderTest` and `CollectPassageTest` exercise native contexts, refusal/partial behavior, clocks, generated identity handoff and controlled HTTP caching. The backend's source-preparation and match-detail integration suites exercise the current-incarnation fence and established document associations against migrated PostgreSQL. Run the repository's full verification to include generated producer/consumer compatibility; these tests establish their represented boundaries, not exhaustive provider coverage.

Discovery consumes shared pages immediately for already admitted scopes and retains no page reserve. Regression cases distinguish a season header from an actual catalog, reject an isolated round as a seasonal root, preserve contextual Cup exclusions and unrelated roster failures, and retain document refusals across independent successful details. The auxiliary-index test verifies one read across pools with its original timestamp and ordinal. Other regressions cover contradictory seasons before shared-page consumption, redirected document identities, championship standings without a phase query, partial date/result fields, native forfeits and independent current-menu failures.

Verified document-team associations remain explicit configuration scoped to season, championship and native team. Empty configuration leaves auxiliary XML codes unavailable. No test fixture, sampled current identifier or ordinary discovery run supplies missing historical associations or activates collection. Actual provider qualification, native operator journeys and scheduling remain with their owning tasks.

## Ordered uncertainty cases (T044 preparation)

These cases are prepared for T050's isolated qualification. Do not inject faults against FFVB, LNV, IGN or a shared environment. Use the generated collector client, a local HTTP fault peer and the actual migrated PostgreSQL/F02 owner. Control the response **after** the indicated commit, and count writes independently of received responses. Keep accepted business facts and source locks throughout.

1. **Admission response lost:** let the backend commit RUNNING, then drop its response. The collector reads the same allocated cycle UUID before any provider read. A confirmed running context permits only its frozen selection. If that read is unavailable or contradictory, perform no provider read, second admission or fresh UUID attempt. Inspect that original cycle explicitly. Repeat with admission rejected before commit; a missing cycle is not successful admission.
2. **Sporting write response lost:** commit one F02 match transaction, then drop the response. Keep that accepted match and independently successful matches. Record unconfirmed integration; never resubmit the mutation or replay the passage. Attempt ordinary completion for the passage. A later ordinary eligible cycle may recover facts still published, subject to newer observation/visibility guards; it cannot reconstruct lost user corrections or custom image bytes.
3. **Completion response lost:** commit completion, drop the response, and allow the original-cycle GET. Matching terminal state confirms acceptance without a second POST. Repeat with an unavailable GET and with a completion refused before commit: an alive collector still leaves that scope unresolved/RUNNING and logs manual intervention. Repeated ticks and manual requests create no second cycle. Inspect current state; restart the single collector explicitly only when needed to invalidate unfinished work.
4. **Validation-result response lost:** commit qualification and validation completion together, then drop the response. A completed same-cycle read confirms acceptance; no control-completion substitute is sent. Repeat with unconfirmed terminal state and a still-alive process: no validation replay or automatic new request. After explicit replacement, an interrupted candidate projects as unvalidated. Reread the source and issue a new explicit validation request only if qualification is still needed and the season remains open. Accepted qualification survives replacement.
5. **Replacement during a held transaction:** hold a real F02 transaction after its shared runtime fence and before domain commit. Start registration of a different startup UUID with the current runtime revision. Observe its PostgreSQL lock wait, release and commit the first transaction, then confirm replacement. The committed fact survives; subsequent old-incarnation results, details and terminal writes are refused. Repeat admission versus exact-label closure in both lock orders: closure first prevents admission; admission first permits only that running selected work to finish once.

For every case, retain the original cycle/candidate identity privately, check actual SQL effects and HTTP call counts, and separate confirmed acceptance, refused acceptance and unresolved outcome. Availability evidence does not identify an instant crash: no heartbeat, watchdog, retry worker, sweep, checkpoint or broad reset is involved. An empty/unexecuted selection supplies no failure or recovery observation.

Construction evidence for [T044–T049](tasks.md) consists of native trigger/dispatch tests, actual F12/MVC/PostgreSQL command tests and the existing admission/fence/F02 suites. It does not execute this full integrated fault protocol or establish live-provider availability; T050 remains its qualification owner. The [operations guide](../../infra/operations/README.md#collection-inspection-and-explicit-recovery) owns actual inspection and restart instructions.
