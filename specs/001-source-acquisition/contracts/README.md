## Operator interface

Seasons are listed/read under `/administration/collection-seasons`. `POST /{seasonId}/closure` processes terminal closure with exact label and revision; `POST /{seasonId}/source-launches` atomically launches the explicitly selected qualified sources. Provider-specific launch uses the same operation with that provider's selection. This focused configuration command avoids duplicate season/provider launch APIs and never edits classification.

Source bindings are listed/added under the owning season. Their member GET, candidate PUT, validation POST and season-confirmation PUT supply the approved preparation journey. Validation returns 202 and is observed through the binding GET; it is one current candidate state, not a new execution-history product. A candidate edit invalidates prior qualification. Closed or locked sources refuse preparation. Discovery references may be supplied only for supported source identities/formats. Child pack/pool reads remain separate from F02 mapping controls.

Collection controls expose GET, desired-activity PUT, manual-request POST and current result reads. One accepted pending request is distinct from RUNNING: 202 means waiting, 200 may return existing running work only while the control remains enabled. Paused/pausing controls reject relaunch before checking for duplicate work. The control GET is the status read, so no separate job resource or status URL is needed. Pause cancels pending intent; resume restores ordinary eligibility only. Idempotent desired-state changes and duplicate requests never authorize automatic mutation retry.

All operations require current `collection.manage`, independent of sporting or moderation rights. The backend rechecks domain state and grants in the same transaction as effects. The operator is authorized when the request is accepted. Later collector admission separately checks its service credential and current domain conditions; no account-session registry or retained actor identity is needed. These individually authorized operational routes remain usable during F12 maintenance without granting ordinary admission or a version exception.

Use body revisions and 409 as in existing administration contracts. The season preparation revision covers relevant binding changes; candidate revisions cover candidate/evidence changes; control revisions cover desired activity, pending intent and admission. Freshness-only result updates do not create needless editor conflicts. A refusal changes nothing; after an uncertain response the mobile rereads the relevant resource before an explicit retry. Default errors use the existing ordinary presentation, not new screens.

Configuration lists are complete and deterministically ordered. Potentially larger child/result lists use zero-based pages, size 50 by default and at most 200, with `hasNext` and no total count. These are ordinary bounded reads, not an export or a consistent snapshot across concurrent changes. JSON mutations use the existing 8 MiB bound; oversized input is refused without truncation or automatic chunking. Responses are `no-store`; this does not prohibit the approved session-bound in-memory query cache.

## Collector interface and integration

Runtime GET/PUT registers one startup UUID using the current runtime revision. Current-work GET is polled every minute. It returns controls and candidate validations; it performs no admission. The backend is the authority for pending initial-import mode, source locks and existing cycles.

Cycle POST admits either a control passage or one source validation. The latter uses the same admission protection and candidate revision rather than introducing another worker/queue lifecycle. Exactly one of `controlId` or `sourceBindingId` identifies the admitted operation. `mode` is present only for a control passage (`periodic`, `manual`, `initial-import`); a validation has candidate context and cannot submit sporting observations. A cycle UUID is generated once before admission. A lost response requires GET of that UUID; no new UUID or supplier read is attempted blindly. Backend admission selects due targets for periodic work or the explicit manual/initial scope. Targets reuse the domain scope UUID and are read in stable `(kind, scopeId)` pages from that snapshot; currently permitted locality and its revision are resolved from F02 rather than archived in a cycle. An empty selection provides no observation or recovery evidence. No automatic fine-grained resume is implied by pagination.

Targets supply known backend IDs, qualified references, effective starting classification and locality revisions. Provider adapters interpret their supported native forms, not caller-defined HTTP methods or arbitrary scraping instructions. Competition URL provenance is retained through optional `calendarUrl`/`standingsUrl` in catalog candidates and `detailUrl` in match candidates. These additive request fields coordinate F01 discovery with the F02 owner; they are neither raw archives nor public URL proxies. A failed/partial catalog cannot clear usable prior references. New child pools discovered during a passage become eligible under a subsequent starting snapshot; newly identified matches inside an already authorized calendar may receive their first detail and logo reads in that passage.

The seven sporting writes retain F02 atomicity, byte/item bounds, partial outcomes and `(cycleOrder, readOrdinal)` order. Each domain transaction holds the current runtime fence until commit, including each match transaction and final absence reconciliation. A stale process cannot commit after replacement. An uncertain or failed write is reported, never replayed automatically. Acquisition success cannot stand in for integration success.

Current result POST records one attributable scope/stage/phase observation. `scopeId` is the stable binding, pool, match, club or team UUID defined by the stage; it is never a newly allocated per-cycle result identity. The backend checks its membership in the admitted scope, including match/team identities resolved through an authorized calendar. Separate acquisition/integration phases retain the original stage so that calendar and standings failures remain independent. It preserves other scopes and old usable successes; stale ordinals change nothing. Cycle completion marks selected work finished, not all stages successful. Candidate-validation submission rechecks its admitted candidate and open season and atomically ends that validation with its accepted result. Control completion cannot stand in for a missing validation result. A terminal write whose outcome remains uncertain after rereading leaves the operation unresolved for logged manual intervention; no automatic mutation replay is implied. A late qualification cannot edit a closed season. Registration, result acceptance and source discovery use normal database transactions; no network call occurs inside them.

Automatic seasonal-entry discovery submits one qualified season/source proposal at a time. It reuses canonical start-year identity and never activates, reopens or overwrites an operator candidate/accepted binding. The supported current entries are inspected every 30 minutes independently of a yet-uncreated season control. This narrow discovery responsibility creates no extra operator control or historical archive crawler.

The existing environment-specific M2M credential and `sporting:ingest` scope authorize the collector surface; they grant no mobile administration right. Current incarnation, cycle purpose and resource conditions remain mandatory. Source allowlists and redirects are checked before acquisition; internal URLs/diagnostics contain no credentials or personal payloads.

## Backend-only initial reconstruction

The non-web entry point requires the current operator account UUID. Preparation accepts explicitly selected sporting start years, supported provider/organizer identities and official candidate URLs. Reuse/create canonical F02 seasons in PREPARING and their source bindings through existing application services; refuse closed seasons and conflicting locked references. Preparation requests ordinary candidate validation; missing seasonal evidence still requires explicit confirmation through the existing preparation flow. No year is inferred from a provider ID.

Acquisition takes the resulting season/source-binding IDs, with an optional narrower selection of previously failed scopes for a targeted retry. Retain that selection on the pending initial request and copy it at admission; no scheduled or later request may widen it. If child pools are not yet known, an explicit initial passage discovers them without importing unclassified calendars. The existing F02 classification flow supplies missing settings before an explicitly requested acquisition passage; no automatic follow-up or per-pool acceptance gate is added. Current grants, qualified references and calendar eligibility are checked through existing services before effects. Historical seasons stay PREPARING; used references lock before first admission. Only this authorized backend path selects initial-import suppression for F07. F14 reads requested/obtained/rejected/unavailable coverage by scope through the same application services. No new public import endpoint, bootstrap administrator, task framework or execution-history schema is introduced.

## Compatibility and qualification

The shared mobile and ingestion roots remain on OpenAPI 3.0.4 and the F13 Redocly → generation → consumer-validation chain. New operations, optional capability and optional provenance fields are additive. An old server still rejects new request properties: deploy the backend contract change before its collector/mobile consumers; generate all from the same reviewed source. Enum additions are not automatically compatible. F02 request/response shapes and accepted semantics otherwise remain intact.

Use existing common Problem Details and `stale-revision` / `invalid-cycle-context` where applicable. Source qualification/lifecycle refusals use the existing generic conflict or unprocessable-content category with a safe specific detail; no second error catalogue is needed. Responses allow additional properties, requests reject unknown fields, and domain checks enforce conditional target fields, current scope and allowed terminal validation states without a polymorphic DTO hierarchy.

The [quickstart](../quickstart.md) defines integrated qualification still to perform. Lint/bundle success establishes source structure only, not generated Java/TypeScript compatibility, provider coverage or production behavior.
