# Implementation Plan: Source acquisition and operations

**Branch**: `tech/47-source-acquisition-plan` | **Date**: 2026-10-14 | **Spec**: [Source acquisition](spec.md)

**Input**: [spec.md](spec.md), [F02](../002-sporting-data/plan.md), [F12](../013-administration-app-configuration/plan.md) and [F13](../003-shared-quality/plan.md).

## Summary

A separately deployed Java collector reads supported official FFVB and LNV sources and sends normalized observations to the existing backend. The backend remains the sole PostgreSQL business writer. Native scheduling, bounded HTTP reads, source-specific parsing and current operational state implement the accepted cadences and manual controls without a queue platform, retained raw documents or automatic pipeline recovery.

The scoped prototype and Figma scope are approved. [Tasks](tasks.md) track implementation and remaining qualifications.

## Technical Context

**Language/Version**: Java 25 Temurin; mobile TypeScript under the [F13 baseline](../003-shared-quality/plan.md).

**Primary Dependencies**: Spring Boot 4.1.1, its managed Spring Framework 7.0.9 and Apache HttpClient 5.6.4; jsoup 1.23.2 for HTML; Apache Commons CSV 1.14.1; Resilience4j RateLimiter 2.4.0 only. Existing Spring Data JPA, generated RestClient interfaces and mobile TanStack Query remain as approved.

**Storage**: PostgreSQL 18.6 through backend application services. Collector memory holds bounded work and a bounded native HTTP image cache; no persistent source archive.

**Testing**: JUnit, Spring MVC, Testcontainers PostgreSQL; existing Expo/React Native testing tools for operator interactions; sanitized or synthetic parser fixtures. Live providers are not CI dependencies.

**Target Platform**: One Linux collector instance per environment, existing backend deployment, iOS/Android operator application.

**Project Type**: Acquisition application plus existing backend and mobile feature extensions.

**Performance Goals**: Domain scheduling only: discovery every 30 minutes; calendars/standings every 30 minutes or five minutes in the pool's H−1…H+4 window; individual LNV detail hourly or five minutes in its own window; club sheets daily; new address-first geocoding needs within one hour when enabled and available. These are scheduling rules, not freshness or availability guarantees.

**Constraints**: No provider calls in SQL transactions; no unbounded pending work, automatic integration replay, browser automation, raw-data archive, generic job engine or monthly availability/load programme. Closed seasons accept no new work; already admitted work may finish once.

**Scale/Scope**: Covered FFVB national/regional/departmental championships and youth qualifying pools; the three professional LNV championships and all published phases. Initial reconstruction targets the current and three completed seasons subject to source availability. French Cups and bracket/progression interfaces are excluded.

## Acquisition and scheduling

Spring `TaskScheduler` triggers eligible work through one bounded passage `ThreadPoolTaskExecutor`, with at most `3 * concurrencyPerProvider` callers and no pending queue; current-entry discovery adds one synchronous caller. Startup is sequential. Supplier reads run directly through each provider's native STRICT connection pool and finite lease timeout. Resilience4j acquires permits after leasing, immediately before `MAIN_TRANSPORT`, for every actual retry, redirect and cache revalidation; fresh cache hits consume none. Saturated callers wait for a lease or time out. The HTTP boundary preserves native retry/origin/body/cache behavior and translates checked I/O once to `UncheckedIOException`; timers and the passage executor retain shutdown ownership. Native lenient triggers skip overruns, while backend admission excludes a second cycle for the same control. Shared provider limits cover all seasons/families; qualification establishes bounded behavior, not speculative throughput.

Read operator requests every minute through the internal API. A pending request is durable current intent, not a promised start within one minute. Repeated requests return existing pending/running state. Pause and closure cancel unstarted requests; resume restores ordinary eligibility without replay. Dashboard refresh only reads state. Configuration unavailable at admission prevents new work; a known admitted cycle retains its configuration snapshot.

Use a five-minute ordinary competition tick; backend admission selects due targets from their last actual attempts and current reliable fast windows; discovery remains on its 30-minute cadence. The seasonless controls check newly encountered clubs and changed geocoding needs on the existing minute tick, respecting daily club refresh and suppression of unchanged normal no-result localities. The admission scan uses the same geocoding attempt to assess suppression and apply cadence. These are eligibility checks, not repeated supplier calls or catch-up queues. Initial current-entry discovery runs every 30 minutes without depending on a season already having been created.

Use the existing 30-minute source discovery cadence before and after activation. Backend work selection and admission include discoverable sources in the preparing current season and active seasons, subject to their own control state and normal configuration checks. The same passage discovers newly published child pools and phases. Season activation changes PREPARING to ACTIVE under the season lock and current collection grant. Provider controls and F02 mappings retain their owners. The ordinary calendar, standings and match-detail target selection applies only to active seasons and effectively eligible pools. An active-repeat activation has the same intended season effect; closure refuses further activation. Current-entry rollover preserves the older qualified binding.

Keep the F02 classification snapshot for acquisition and apply current corrections/restrictions again at integration. Dedicated calendar reads require eligible admitted pools. Shared resources use qualified native context to partition rows and discard ineligible data immediately.

A newly discovered LNV match gets its first detail read. Subsequent detail scheduling is per match, including final results. Unknown start times create no fast window; a missing result never extends H+4. Logos are read once per distinct team during the ordinary calendar passage. Use Apache's bounded in-memory HTTP cache only for images, honoring origin directives; disable heuristic freshness, asynchronous refresh and stale-on-error substitution. A cached reuse is not a new provider observation. No separate logo schedule is introduced.

For periodic work, the backend freezes the due targets and the qualified standings reference for each LNV pool with an admitted calendar or match detail. An off-cadence standings target is conditional on an accepted final-score change in its pool. A passage that never uses that target records no standings attempt. Manual/initial passages select their explicitly authorized scope instead. An empty selection performs no supplier observation and cannot advance recovery or last-success evidence. Newly discovered pools use a subsequent snapshot; newly identified matches within an already authorized calendar can receive their first detail and image reads in that passage. Result recording resolves the admitted target once and reuses its source binding for initial-reconstruction attribution. Multi-pool admission remains one bounded selection; image-write admission retains its additional current-parent check. Store only qualified current URL provenance with the existing identities, never raw source documents. Current privacy restrictions still apply when targets are served and data are integrated.

## Provider boundaries

`ProviderPages` returns a bounded `ProviderResponse` synchronously, carrying complete bytes, the final URI and actual supplier-read provenance. [Acquisition configuration](../../apps/collector/src/main/java/com/blockout/collector/config/AcquisitionConfiguration.java) selects each client's origins, page headers and native cache policy. The source adapters choose form encoding and interpret their own formats. Historical candidate qualification, bound discovery and ordinary calendar/standings collection each select FFVB or LNV explicitly. FFVB qualification uses the bound catalogue reader with the candidate's source context and submits only the validation result. LNV qualification interprets the candidate response it already read. The [shared composition decision](../003-shared-quality/plan.md#application-use-case-families) keeps application response ownership local to each application.

Apache HttpClient owns HTTP transport, connection pools, bounded timeouts and its standard retry policy, configured for at most two additional attempts with `Retry-After`. The [research](research.md#runtime-and-bounded-transport) states the native status, method and exception limits; read-only POST does not imply I/O retry. Parser failures are not retried. The generated backend client has no automatic business-write retry. Bound decompressed response bytes and reject overflow rather than truncate it into a plausible empty document. Use jsoup solely to parse content fetched by this transport; its convenience HTTP defaults are unsuitable for the observed large LNV pages.

The FFVB reader indexes the single decoded HTML document by published group before interpreting admitted scopes. It qualifies and submits the export with the same ordered form fields. Its lazy export read retains one indexed CSV result or transport failure for that resource, including export-wide anomalies and original row order. Each group still owns its own calendar and standings outcome. The LNV reader shares the decoded document and its season heading within the admitted resource. Its calendar groups also reuse roster and phase-date evidence. Detail and document readers can share a decoded match page while checking and reporting their own outcomes. A document postback qualifies its own response. The first LNV calendar enrichment creates index state that retains one XML lookup result per applicable code for the passage. A successful reused XML index carries its original read time and ordinal. A failed lookup supplies acquisition attempt evidence for the affected matches in each pool. Page documents and export indexes leave scope after their last use. A later independent page read acquires a fresh body.

FFVB discovery follows published frames, options, links and forms, retaining native pack and pool identities and verifying the supported season and organizer before accepting the catalog. Distinguish byes, qualifiers, normal missing values, invalid fields and contradictory rows before F02 handoff. Club lookup uses the currently published form action.

Reuse the qualified FFVB HTML match rows for their published information-sheet and scoresheet forms. Verify the official HTTPS origin, the exact action path and the exact season, organizer and match before populating the existing document facts. A qualified information-sheet form takes precedence. For a scoresheet, retain the published action when its query carries exactly `saison`, `codent` and `codmatch` and the form supplies no additional submitted fields. Equivalent query encodings identify the same document. If no information-sheet form qualifies, reuse these verified identifiers for the existing information-sheet locator in the same calendar passage. This requires no additional provider request. Omit unqualified references without withdrawing previously accepted facts. Qualify numeric results from the existing official results export under [F02’s result rule](../002-sporting-data/spec.md#sources-results-and-time), independently of document presence. ## Admission, transactions and failure handling

The collector keeps only acquisition inputs from each generated target. Effective classification and due-time evidence remain backend-owned selection rules; copying their unused fields into the collector adds no protection. The admitted cycle retains its immutable candidate snapshot directly, so qualification consumes the same confirmed capability without another candidate GET. `CollectorLifecycle` owns admission diagnostics and runtime-conflict inspection for work, discovery and passages. An unavailable inspection preserves the original refusal, and confirmed supersession stops further work. Backend current state owns eligibility for later ordinary polling.

Use the [current-state model](data-model.md) and F02's existing seven ingestion operations. Backend admission allocates `cycleOrder`, binds a cycle to the current collector incarnation and freezes its authorized acquisition scope. The collector assigns `readOrdinal` before each source read. The commit that marks RUNNING is the logical cycle start; only the successful admission response permits provider work. A failed response ends that attempt; later ordinary polling uses current backend eligibility. A committed RUNNING admission still blocks new work until explicit incarnation replacement, while an uncommitted admission may receive a fresh cycle UUID at a later opportunity.

Each cycle-related write checks the current collector incarnation under a shared runtime-row lock held in the same transaction as the write. Restart registration exclusively locks that row, waits for admitted transactions to finish, replaces the incarnation and makes old unfinished cycles obsolete. No mass update or distributed fencing service is needed. Repeating the current startup identifier is harmless; stale startup revisions are refused. A superseded process stops and does not automatically register again.

Historical candidate validation reuses the admission protection, keyed to the source and candidate revision. That context identifies validation without a collection-mode value. Control passages use `periodic`, `manual` or `initial-import`. In a preparing season, ordinary periodic admission authorizes catalogue discovery, while calendar, standings and detail selection require an active season. Initial reconstruction admits its explicitly selected, verified references only while the season is PREPARING. Candidate validation can start for an unlocked candidate in an open season, and its result rechecks the unchanged revision and lifecycle.

Acquire locks in this order when needed: runtime fence, season, collection control/cycle, sporting roots in F02 order, then account. No provider/network call holds these locks. New startup needs the runtime row only. Already accepted sporting facts and completed successes survive a restart; the new collector uses the next ordinary opportunity, never resumes checkpoints or replays a failed pipeline. Without heartbeat, the backend cannot immediately distinguish a crashed from an isolated collector; F13 availability signals and later registration provide the available evidence.

Sporting writes use the cycle already locked with their admitted scope for observation order and mode. Result recording shares the same target resolution rules under its exclusive passage lock. Each accepted F02 write retains its own atomicity. [F02 catalog authority](../002-sporting-data/plan.md#catalog-authority) owns entry reconciliation and the last complete read within the admitted binding. Incomplete or unavailable reads preserve accepted entries; the existing discovery result records the attempt and its available reason. Calendars retain per-match transactions and reconcile absence only after complete successful integration; standings replace a whole qualified table. Discard stale observations and preserve independent successes. An uncertain write is reported without automatic replay. End the passage through its ordinary completion operation. Completion and historical validation results each use one generated-client call. A failed response gets no confirmation GET or replay. The next ordinary poll reads current backend work: a committed terminal write permits a later opportunity, while unfinished RUNNING work requires explicit restart through the existing incarnation fence. The native lenient trigger skips missed firings and backend admission excludes concurrent work. Each collector registers once at startup. Startup failure ends the process and [F13 hosted supervision](../003-shared-quality/plan.md#hosted-packaging-and-delivery) owns its configured restart limits. Historical candidate validation interrupted by incarnation replacement uses its explicit request path.

Integration evidence carries available safe typed F02 refusals, including a club sheet integrated with a refused secondary field. Acquisition evidence remains independent of that refusal. The generated client decodes evidence and completion acknowledgements. At the collector application boundary these operations use the acknowledgement alone, while admission maps the response to the capability used throughout the passage. When result recording fails outside a cycle conflict, the collector emits one diagnostic for the affected scope, stage and phase, distinguishing rejection from an unconfirmed acknowledgement. A cycle conflict follows the existing passage refusal handling.
