# Implementation Plan: Source acquisition and operations

**Branch**: `tech/47-source-acquisition-plan` | **Date**: 2026-10-14 | **Spec**: [Source acquisition](spec.md)

**Input**: [spec.md](spec.md), [F02](../002-sporting-data/plan.md), [F12](../013-administration-app-configuration/plan.md) and [F13](../003-shared-quality/plan.md).

## Summary

A separately deployed Java collector reads supported official FFVB and LNV sources and sends normalized observations to the existing backend. The backend remains the sole PostgreSQL business writer. Native scheduling, bounded HTTP reads, source-specific parsing and current operational state implement the accepted cadences and manual controls without a queue platform, retained raw documents or automatic pipeline recovery.

The scoped prototype and Figma scope are approved. [Tasks](tasks.md) track implementation and remaining qualifications.

## Technical Context

**Language/Version**: Java 25 Temurin; mobile TypeScript under the [F13 baseline](../003-shared-quality/plan.md).

**Primary Dependencies**: Spring Boot 4.1.1, its managed Spring Framework 7.0.9 and Apache HttpClient 5.6.4; jsoup 1.23.2 for HTML; Apache Commons CSV 1.14.1; Resilience4j RateLimiter 2.4.0 only. Existing Spring Data JPA, generated RestClient interfaces and mobile TanStack Query remain as approved.

**Storage**: PostgreSQL 18.6 through backend application services. Collector memory holds bounded work and a bounded native HTTP image cache; no persistent source archive.

**Testing**: JUnit, Spring MVC, Testcontainers PostgreSQL; existing Expo/React Native testing tools for operator interactions; sanitized or synthetic parser fixtures. Live providers are not CI dependencies.

**Target Platform**: One Linux collector instance per environment, existing backend deployment, iOS/Android operator application.

**Project Type**: Acquisition application plus existing backend and mobile feature extensions.

**Performance Goals**: Domain scheduling only: discovery every 30 minutes; calendars/standings every 30 minutes or five minutes in the pool's H−1…H+4 window; individual LNV detail hourly or five minutes in its own window; club sheets daily; new address-first geocoding needs within one hour when enabled and available. These are scheduling rules, not freshness or availability guarantees.

**Constraints**: No provider calls in SQL transactions; no unbounded pending work, automatic integration replay, browser automation, raw-data archive, generic job engine or monthly availability/load programme. Closed seasons accept no new work; already admitted work may finish once.

**Scale/Scope**: Covered FFVB national/regional/departmental championships and youth qualifying pools; the three professional LNV championships and all published phases. Initial reconstruction targets the current and three completed seasons subject to source availability. French Cups and bracket/progression interfaces are excluded.

## Acquisition and scheduling

Spring `TaskScheduler` triggers eligible work through one bounded passage `ThreadPoolTaskExecutor`, with at most `3 * concurrencyPerProvider` callers and no pending queue; current-entry discovery adds one synchronous caller. Startup is sequential. Supplier reads run directly through each provider's native STRICT connection pool and finite lease timeout. Resilience4j acquires permits after leasing, immediately before `MAIN_TRANSPORT`, for every actual retry, redirect and cache revalidation; fresh cache hits consume none. Saturated callers wait for a lease or time out. The HTTP boundary preserves native retry/origin/body/cache behavior and translates checked I/O once to `UncheckedIOException`; timers and the passage executor retain shutdown ownership. Native lenient triggers skip overruns, while backend admission excludes a second cycle for the same control. Shared provider limits cover all seasons/families; qualification establishes bounded behavior, not speculative throughput.

Read operator requests every minute through the internal API. A pending request is durable current intent, not a promised start within one minute. Repeated requests return existing pending/running state. Pause and closure cancel unstarted requests; resume restores ordinary eligibility without replay. Dashboard refresh only reads state. Configuration unavailable at admission prevents new work; a known admitted cycle retains its configuration snapshot.

Use a five-minute ordinary competition tick; backend admission selects due targets from their last actual attempts and current reliable fast windows; discovery remains on its 30-minute cadence. The seasonless controls check newly encountered clubs and changed geocoding needs on the existing minute tick, respecting daily club refresh and suppression of unchanged normal no-result localities. These are eligibility checks, not repeated supplier calls or catch-up queues. Initial current-entry discovery runs every 30 minutes without depending on a season already having been created.

Use the existing 30-minute source discovery cadence before and after activation. Backend work selection and admission include discoverable sources in the preparing current season and active seasons, subject to their own control state and normal configuration checks. The same passage discovers newly published child pools and phases. Season activation changes PREPARING to ACTIVE under the season lock and current collection grant. Provider controls and F02 mappings retain their owners. The ordinary calendar, standings and match-detail target selection applies only to active seasons and effectively eligible pools. An active-repeat activation has the same intended season effect; closure refuses further activation. Current-entry rollover preserves the older qualified binding.

Keep the F02 classification snapshot for acquisition and apply current corrections/restrictions again at integration. A shared FFVB resource may serve discovery or several eligible pools; fetch it once within a passage, partition only with qualified native context, and discard ineligible sporting rows. Do not retrieve a dedicated calendar solely for an unclassified pool or retain a reserve of such calendars.

A newly discovered LNV match gets its first detail read. Subsequent detail scheduling is per match, including final results. Unknown start times create no fast window; a missing result never extends H+4. Logos are read once per distinct team during the ordinary calendar passage. Use Apache's bounded in-memory HTTP cache only for images, honoring origin directives; disable heuristic freshness, asynchronous refresh and stale-on-error substitution. A cached reuse is not a new provider observation. No separate logo schedule is introduced.

The admitted target snapshot contains the due targets selected by the backend, starting eligibility and qualified references. Manual/initial passages select their explicitly authorized scope instead. An empty selection performs no supplier observation and cannot advance recovery or last-success evidence. Newly discovered pools use a subsequent snapshot; newly identified matches within an already authorized calendar can receive their first detail and image reads in that passage. Result recording resolves the admitted target once and reuses its source binding for initial-reconstruction attribution. Multi-pool admission remains one bounded selection; image-write admission retains its additional current-parent check. Store only qualified current URL provenance with the existing identities, never raw source documents. Current privacy restrictions still apply when targets are served and data are integrated.

## Provider boundaries

`ProviderPages` and `ProviderResponse` belong to collector application. Discovery and qualification depend on that narrow asynchronous page seam, while the existing provider HTTP adapter owns transport and the FFVB/LNV adapters retain their technical GET/POST/image operations. One response value carries complete bytes, final URI and actual supplier-read provenance across these consumers; passage timing/order remains unchanged. The [shared composition decision](../003-shared-quality/plan.md#application-use-case-families) keeps application response ownership local to each application.

Apache HttpClient owns HTTP transport, connection pools, bounded timeouts and its standard retry policy, configured for at most two additional attempts with `Retry-After`. The [research](research.md#runtime-and-bounded-transport) states the native status, method and exception limits; read-only POST does not imply I/O retry. Parser failures are not retried. The generated backend client has no automatic business-write retry. Bound decompressed response bytes and reject overflow rather than truncate it into a plausible empty document. Use jsoup solely to parse content fetched by this transport; its convenience HTTP defaults are unsuitable for the observed large LNV pages.

FFVB discovery follows published frames, options, links and forms, retaining native pack and pool identities and verifying the supported season and organizer before accepting the catalog. Parse semicolon-delimited Windows-1252 exports with Commons CSV and qualified headers, keeping quoted fields and leading zeros. HTML supplies missing source context. Use published group evidence before treating a matchday or part of a shared export as a distinct pool. Distinguish byes, qualifiers, normal missing values, invalid fields and contradictory rows before F02 handoff. Club lookup uses the currently published form action.

Reuse the qualified FFVB HTML match rows for their published information-sheet and scoresheet forms. Verify the published action and exact season, organizer and match before populating the existing document facts. For a scoresheet, retain the published action when its query carries the full identity and the form supplies no additional submitted fields. Equivalent query encodings identify the same document. Omit unqualified references without withdrawing previously accepted facts. Qualify numeric results from the existing official results export under [F02’s result rule](../002-sporting-data/spec.md#sources-results-and-time), independently of document presence. Keep special notations and absent scores distinct. Collection never retrieves these PDF bodies.

LNV adapters use the three official championship entries. Discover phases from a supported official structure attributed to that championship and season. A later authoritative read can add a newly published phase with its native identity. Unqualified, cross-season or cross-championship content supplies no phase or binding. Interpret grouped HTML without executing scripts or advertisements and deduplicate mobile/desktop representations by contextual native reference. Pin the provider's `timezoneoffset=0` convention. For a confirmed date/time rendered in that convention, interpret offset zero as UTC and use Java time to produce the corresponding Europe/Paris local date/time for the existing F02 contract. An unknown-time flag preserves a date-only source value. Qualify calendar/detail extraction separately, since hidden fields need not use the rendered clock. The F03 document integration uses the narrow F01/F02 exception for information-sheet codes, with verified championship/season-scoped team associations and an unambiguous participant/date match. Read an applicable XML index once per eligible collection pass. Extract published scoresheet and statistics-PDF links using ordinary HTTP form requests and page hidden fields. Keep these references and their read outcomes separate from sporting facts. Collection never retrieves PDF bodies. An absent unpublished standings table is distinct from an unrecognized or broken table.

Both providers hand off the full contextual standings table in its published sequence, retaining any printed ranks as separate source values.

The non-web historical preparation command records a credential-free HTTP candidate for its explicitly selected season. Qualification checks provider hosts, paths, redirects and organizer/championship context. Explicit historical operator confirmation fills missing attribution only. A changed historical candidate invalidates prior evidence; apply asynchronous validation only to that unchanged revision in a preparing season. Ordinary discovered references come from the qualified provider structure and are read-only to the operator.

IGN Géoplateforme remains the sole geocoder. Read F02's current permitted address, municipality, optional postal code and locality revision from the target, without a personal-data copy in the cycle. Without a permitted municipality, make no provider request. Seek a unique full-address result first when an address is present. An absent address or a qualified empty or ambiguous address response uses the ordinary municipality lookup; choose no address heuristically. Transport errors and malformed responses remain technical failures without a fallback that conceals them. Both requests reuse the existing bounded transport, IGN budget and source interpretation boundary. Preserve final no-candidate/ambiguity outcomes separately from failures. F02's revision covers effective address/city/postcode changes and rejects late results. A located municipality fallback is accepted current data: neither ordinary collection nor family rerun repeatedly upgrades it while context is unchanged; only unresolved contexts are rerun. No score threshold, second provider, precision column, fallback flag or new retry mechanism is introduced. This prioritizes the actual permitted club address while retaining a useful point through the same provider and existing locality state; storing resolution history or a precision state would add synchronization without changing the approved silent map experience.

The native Apache client owns intermediate redirect/retry response disposal, including error-body consumption under its configured socket/response timeouts. These are inactivity bounds, not a whole-response elapsed deadline. The collector retains complete-or-fail decoded success-body limits, terminal status interpretation and origin checks; it does not close and erase intermediate response entities itself.

## Admission, transactions and failure handling

The collector keeps only acquisition inputs from each generated target. Effective classification and due-time evidence remain backend-owned selection rules; copying their unused fields into the collector adds no protection. The admitted cycle retains its immutable candidate snapshot directly, so qualification consumes the same confirmed capability without another candidate GET. `CollectorLifecycle` owns runtime-conflict inspection for work, discovery and passages: an unavailable inspection preserves the original refusal, while confirmed supersession stops further work. Neither outcome authorizes replay. Backend current state owns eligibility for later ordinary polling.

Use the [current-state model](data-model.md) and F02's existing seven ingestion operations. Backend admission allocates `cycleOrder`, binds a cycle to the current collector incarnation and freezes its authorized acquisition scope. The collector assigns `readOrdinal` before each source read. The commit that marks RUNNING is the logical cycle start; only the successful admission response permits provider work. A failed response ends that attempt; later ordinary polling uses current backend eligibility. A committed RUNNING admission still blocks new work until explicit incarnation replacement, while an uncommitted admission may receive a fresh cycle UUID at a later opportunity.

Each cycle-related write checks the current collector incarnation under a shared runtime-row lock held in the same transaction as the write. Restart registration exclusively locks that row, waits for admitted transactions to finish, replaces the incarnation and makes old unfinished cycles obsolete. No mass update or distributed fencing service is needed. Repeating the current startup identifier is harmless; stale startup revisions are refused. A superseded process stops and does not automatically register again.

Historical candidate validation reuses the admission protection, keyed to the source and candidate revision. That context identifies validation without a collection-mode value. Control passages use `periodic`, `manual` or `initial-import`. In a preparing season, ordinary periodic admission authorizes catalogue discovery, while calendar, standings and detail selection require an active season. Initial reconstruction retains its explicitly selected, verified references. Historical candidate validation begins only for an unlocked candidate in a preparing season and its result rechecks the unchanged candidate and lifecycle.

Acquire locks in this order when needed: runtime fence, season, collection control/cycle, sporting roots in F02 order, then account. No provider/network call holds these locks. New startup needs the runtime row only. Already accepted sporting facts and completed successes survive a restart; the new collector uses the next ordinary opportunity, never resumes checkpoints or replays a failed pipeline. Without heartbeat, the backend cannot immediately distinguish a crashed from an isolated collector; F13 availability signals and later registration provide the available evidence.

Each accepted F02 write retains its own atomicity. Catalog observation state and any authoritative entry changes commit atomically in their source scope. A complete observation advances the last complete read. Incomplete or unavailable reads preserve accepted entries; the existing discovery result records the attempt and its available reason. Calendars retain per-match transactions and reconcile absence only after complete successful integration; standings replace a whole qualified table. Discard stale observations and preserve independent successes. An uncertain write is reported without automatic replay. End the passage through its ordinary completion operation. Completion and historical validation results each use one generated-client call. A failed response gets no confirmation GET or replay. The next ordinary poll reads current backend work: a committed terminal write permits a later opportunity, while unfinished RUNNING work requires explicit restart through the existing incarnation fence. The native lenient trigger skips missed firings and backend admission excludes concurrent work. Each collector registers once at startup. Startup failure ends the process and [F13 hosted supervision](../003-shared-quality/plan.md#hosted-packaging-and-delivery) owns its configured restart limits. Historical candidate validation interrupted by incarnation replacement uses its explicit request path.

## Initial reconstruction and operations

Use a non-web Spring Boot `ApplicationRunner` entry point in the backend executable, calling the same application services. An explicitly supplied operator account must currently hold `collection.manage`; this creates neither a bootstrap privilege nor a second database writer. The same entry point supports preparation from explicitly supplied historical start years and supported provider/organizer URLs, reusing canonical F02 season services and existing source validation. It creates missing PREPARING seasons/bindings without guessing years or reopening history. Acquisition then selects prepared references and requests one ordinary collector passage in initial-import mode. It is an exploitation tool, with no new mobile journey or CLI framework. This non-web invocation does not start the [F04 index scheduler](../008-search-discovery/plan.md#projection-lifecycle); the serving backend remains the sole search-index writer and its full rebuild covers relevant operator-side data changes.

Historical seasons remain PREPARING. Activation refuses an accepted initial request that still awaits admission, preserving its scope. An already admitted cycle retains its capability. Initial reconstruction locks references without enabling periodic activity; calendar and standings selection for ordinary collection remains governed by season activation and current pool eligibility. Lock used references on their first admitted initial pass; retain obtained/rejected/unavailable coverage by scope for F14 review. A targeted retry refreshes only results actually observed inside its frozen selected scope; unrelated scopes retain their gaps and successes. Admission rechecks PREPARING after a pending request. A failed team-logo retry explicitly selects the UUID of an eligible parent pool under the same source binding. The identified failed logo makes that pool eligible for retry even when its calendar/standings already succeeded. Admission freezes the ordinary pool calendar/standings selection and rechecks its current eligibility; it selects neither discovery nor other pools. Ordinary LNV calendar processing may integrate authorized sporting facts, team images and first details for newly created matches. It provides no image-only isolation or automatic retry. Source-validation failure categories retain unavailable transport separately from refused content; uncategorized failures remain unavailable. Preserve F02’s typed content/staleness refusals through collector evidence instead of classifying them as transport failures. Published empty initial standings advance publication attribution but preserve the last usable table and its own observation time; ordinary current empty-table replacement remains effective. Prevent periodic results from overwriting that initial report before its decision. F07 initial-import suppression is backend-controlled. Terminal closure requires the exact season label and current authorization/eligibility; it prevents all subsequent preparation and new work while allowing already admitted work to finish once.

Mobile reads use the existing generated clients and TanStack Query owners for seasons, source catalogues, children, controls, results and closure. F13 owns initial skeletons, native refresh progress and same-card Retry after a final required-read failure; failed next-page reads keep authorized rows, pagination state and native scroller with the shared footer Retry. The landing menu’s seasons Query is indispensable to its whole body: after final failure, `hasReadError`/`ReadFeedback`/`ScreenState` replaces the menu, including Competitions and Clubs links, while the header/Back stays available. Query retains authorized cache; visible rows are masked. Preserve the initial skeleton; explicit seasons-only Retry keeps the card and real button progress, omits competing pull and restores the menu after success. This landing boundary is distinct from the collection-control view. All result details belong to the results read. Its failure leaves independently authorized commands usable. A result Retry calls only its result GET. The mounted `CollectionControl` action owner publishes the A25/A27 copy through [F13 action feedback](../003-shared-quality/plan.md#repeated-interaction-conventions) after its own season/provider write is acknowledged. The activity response determines whether resumption was accepted or pause is immediate or draining. The relaunch response distinguishes an accepted or already pending request from an existing running cycle. The pending outcome publishes the A27 confirmation. Current command authority, request invalidation and the results read retain their owners. The shared mobile read budget is independent of FR-037’s at-most-two-additional supplier attempts. Recorded acquisition/integration failures remain ordinary result data. F05 ordinary entry no longer waits for the first account response. In collection-dashboard-screen landing and season/control scopes, source-children-screen, season-preparation-screen and shared account/access feedback, keep the same ScreenState/ReadFeedback/native container during first account failure and explicit Retry. Use existing hasReadError/Query metadata; account.isLoading alone must not select a new skeleton after failure. Only the explicit active read animates Retry. Matching account/current grants still gate private reads/commands, while results and independently authorized controls retain their separate scopes.

Present the current application read error directly. Resource reads withdraw data that a refusal makes forbidden, independently of account grants. Source catalogue reads reuse the scoped F13 feedback and paging. A stored provider failure is catalog data and can show the retained authoritative entries. Typed closure alone owns its editable baseline and [F13 form composition](../003-shared-quality/plan.md#frontend-form-conventions). A failed required closure read hides the editor and its command while retaining the same mounted typed draft. Card Retry only rereads the failed dependency.

Operational projections retain current outcome, observation time, logical order and the latest successful observation/integration for each control/scope/stage/phase. Failed, partial and unconfirmed observations are immediately actionable for every family, including transient club/geocoding failures. A usable observation after a non-successful outcome emits recovery evidence only for that exact key. Current reads own the latest projection. Existing Spring transaction events carry only safe facts already available in the committing operation: stable control/scope/stage/phase, provider/season, observation time, outcome, logical order, latest useful success and bounded counts. The native AFTER_COMMIT listener emits failure/recovery observations without a new transaction, season/control lock or projection reread. A delayed log retains its original observation even if newer evidence has committed. Rollback produces no accepted-result log, and diagnostic failure cannot change business acceptance. Existing ingestion order and runtime fencing remain business responsibilities. Success elsewhere does not prove recovery. Normal unresolved geocoding results are not outages, and exact outage age is unavailable.

Keep Bilan on the existing collection-result GET. Check the operator's collection grant before reading the selected control. Resolve established labels and catalogue links in the bounded result query, applying criteria and deterministic ordering before paging. The whole-control aggregation supplies Suivi and establishes control existence. The control GET continues to own scheduling, execution and its timestamps. Both reads reuse the existing current-result projection.

F02's existing `sporting_catalog` row adds two nullable facts, `complete` for the latest committed catalog observation and `last_complete_read_at` for the latest complete read. The catalog transaction retains its existing cycle order, read ordinal and observation time. A partial observation may advance its committed evidence while preserving previous entries and complete-read time. The source projection compares that committed evidence with the existing discovery result by cycle order and ordinal. A newer unsuccessful attempt supplies its own outcome and available reason. A committed complete read establishes completeness even if its result acknowledgement is missing. Earlier rows with unknown completeness supply no inferred complete read. Follow [F13’s Liquibase posture](../003-shared-quality/plan.md#runtime-data-and-consistency) for the initial schema and retain hosted data between deployments.

Existing source/catalog events report accepted activity through structured logs grouped by provider/season/subject. A source report records one actual creation and is omitted for repeated proposals. Catalog reports carry available obtained/rejected counts from the accepted result, leaving unmeasured counts absent. The existing events carry those safe facts and observation time to the after-commit listener. Reports describe their operation; F02 administration owns classification needs. Diagnostics use those available facts without additional count queries in or after the business transaction. Use bounded counts and the existing administration destination without per-pool/item reports or an outage classification for ordinary waiting. Local process output and existing application projections are the consumers; no hosted dashboard or log-order coordinator is required. Diagnostics exclude raw documents, contacts and secrets; F11 restrictions remain effective during reimport and reconstruction.
