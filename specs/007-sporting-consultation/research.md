# Research: Sporting consultation

## Public reads and calendar progression

**Decision**: Extend the existing backend mobile API with resource reads for clubs, teams, pools and matches. Use one filtered match collection, seven complete nonempty display days per page, with an exclusive continuation day. Read projections include the summaries needed by their actual callers; there is no endpoint per screen or generic batch dispatcher.

**Rationale**: The accepted calendar moves by days rather than by an arbitrary match count. F02 retains identities, facts and visibility; F03 derives presentation without another database or projection worker. A short read-only repeatable-read transaction keeps day selection and match retrieval coherent within one response. PostgreSQL supplies date/time conversion; Hibernate/JPA remains the ordinary persistence boundary.

**Alternatives**: Match-count pagination splits days; durable cursors or a frozen snapshot add state without the accepted continuity guarantee. Ordinary reads may miss a concurrently moved match until refresh; identity deduplication prevents duplicate cards. No total count is needed.

**Evidence**: [PostgreSQL date/time functions](https://www.postgresql.org/docs/18/functions-datetime.html), [transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html), and [Hibernate 7.4 query language](https://docs.hibernate.org/orm/7.4/querylanguage/html_single/) support the relevant building blocks. The implemented two-query JPA projection, generated consumers and bounded native execution have [scoped qualification](quickstart.md#complete-day-calendar-qualification--t020t022-t024t031). Known instants and date-only values follow different grouping rules; a date-only value is never converted into a fictional instant.

Club seasons, club-season teams and current participation identities use focused F02 owner queries with the same current visibility predicates. This avoids loading search aliases/terms or applying the search hydration batch limit to consultation. The existing read transaction loads the addressed club and season before selecting teams; subsequent F02 presentation mapping reuses that standard JPA persistence context. Team selection excludes parent columns so a club logo is not repeated for every row, and division metadata is loaded together without image bytes. These reads retain complete selections, closed seasons and effective values without an application cache or second visibility authority.

## Retained mobile queries

**Decision**: Use TanStack Query memory state and generated query functions/keys. Retained calendars disable automatic focus, reconnect and mount refetches, ordinary retries and invalidation-triggered refetches. A newly opened page reads its common information and initial tab; other tabs load when first opened. Manual refresh replaces only the active tab and, for calendars, only the first page on success. Match detail keeps its accepted focus, foreground and explicit refresh behavior.

**Rationale**: This preserves the accepted distinction between a retained calendar and a fresh match detail without another cache or synchronization loop. Cancel pending pagination before replacement and reject obsolete responses by their query/session context. Known restrictions remain authoritative. F13's `networkMode: 'always'` prevents offline attempts from becoming paused work; retry/refetch flags alone do not control this continuation, as documented in [TanStack network modes](https://tanstack.com/query/latest/docs/framework/react/guides/network-mode). The ordinary bounded transport reports failure without a custom connectivity queue.

**Alternatives**: Default infinite-query refetch reloads retained pages and violates the selected refresh scope. Clearing the cache before fetching loses the usable list on failure. A handwritten backup cache duplicates ownership.

**Page lifetime**: Native Query [`gcTime: 0`](https://tanstack.com/query/latest/docs/framework/react/reference/functions/useQuery) discards a traversal after its last page observer is removed, so closing and reopening reads a new first page. Visited panels remain mounted while their resource page is retained; changing tabs or opening/back from a match therefore preserves their observed pages. The [F13 shared native paging composition](../003-shared-quality/plan.md#native-paging-and-scroll-composition) now hosts calendars and existing neighbouring panels through `PagedTabs` and the official scroll/list adapters. It replaces the application-owned `SportingPager`/horizontal `ScrollView` composition without taking ownership of panel queries or introducing another offset store.

**Presentation adoption**: [F13's adoption research](../003-shared-quality/research.md#native-paging-adoption) owns the selected RNCT/LegendList mechanisms and alternatives. Individually virtualized calendar cells use public spans and sticky indices for the lateral date rail; native refresh forwards its progress properties through the existing refresh control. F03 retains query lifetime, complete-day grouping, identity deduplication, cursors and success-only first-page replacement. The earlier calendar qualification still supports those business boundaries; native collapse, sticky geometry, gestures and accessibility of the replacement require their own scoped integration evidence.

**Evidence**: The published TanStack Query 5.104.2 implementation and [QueryClient API](https://tanstack.com/query/latest/docs/framework/react/reference/classes/QueryClient) were inspected for the native infinite-query `pages: 1` option and replacement only after successful fetching. The installed F13 Query 5.104.3 and generated consumer now have [scoped calendar qualification](quickstart.md#complete-day-calendar-qualification--t020t022-t024t031); this required no dependency update.

**Context identity**: Consultation keys include the captured F05 generation and, for explicit bypass, F12's exact intent identity. F12 creates that identity once per deliberate choice so every consumer shares the same Query entry; clearing and re-enabling bypass creates a different one. The installed Query 5.104.3 deduplicates simultaneous same-key reads onto the existing promise: response rejection alone would let an obsolete session or cleared/re-enabled bypass cancel the new context's read. Separate serializable [native query keys](https://tanstack.com/query/v5/docs/framework/react/guides/query-keys) avoid that collision without a feature-local identity generator, session/grant registry or cancellation coordinator. Generated resource/season/category/zone keys remain part of the identity; F12 admission and F13 transport retain current authorization, cancellation and session checks. Controlled observer/transport regressions cover context changes and same-intent sharing; screen retention and native networking remain story qualifications.

**Known refusal and retained data**: A current 401/403/404 clears the addressed query's retained representation before propagating the original HTTP error. Calendar refusal also cancels pending sibling reads and clears retained categories/zones of that same selector/club-season and session-bypass context through native partial query-key matching; another selector remains unaffected. TanStack Query 5.104.3 otherwise keeps successful data through subsequent errors: success → 404 → network/503 failure could therefore redisplay a forbidden representation. Use the documented [QueryCache](https://tanstack.com/query/latest/docs/framework/react/reference/classes/QueryCache) and [Query.setState](https://tanstack.com/query/latest/docs/framework/react/reference/classes/Query#setstate) to clear retained data and preserve the refusal in the existing cache. `setQueryData(undefined)` deliberately does nothing; removing or resetting an active query changes its lifecycle. This retains the native error/request lifecycle without an empty successful DTO, a restriction registry, a second cache or automatic recovery. Controlled regressions exercise later failures and a late cancelled sibling append; native/provider qualification remains separate.

A current match-detail refusal also cancels older calendar reads in that session/bypass context with native `revert: false`, then removes only the refused match from retained pages through `Query.setState`. Other rows, grouping, exclusive continuation, source evaluation and cache timestamps remain retained. The cancellation prevents a late response from republishing the known hidden match; an interrupted initial calendar can be retried explicitly. No persistent suppression registry or local reclassification is introduced.

A new page opening rereads its initial table while mounted RNCT panels remain retained across tab changes. Query failures retain only still-authorized data and its source observation time. A current team refusal cancels older table requests in that same session/admission context, then removes only the team association from retained rows through native Query state. Table metadata identifies this query family for filtering; no restriction registry is stored. Official values/order, source observation and cache attribution remain unchanged. A current refusal from the detail, standings, participants or pool-selected calendar cancels older reads and clears the same pool’s independent representations in that context. The calendar’s existing native partial-key refusal cleanup is shared for this selector; other pool selectors and contexts remain untouched. Retained team/club calendars remove only groups of the refused pool after cancelling older mixed reads. Source attribution, loading zone, other groups and continuation remain retained. Native Query metadata distinguishes the existing infinite traversal wrapper from the generated direct calendar window; neither response shape is duplicated. No sibling refetch or calendar presentation change is introduced. The existing team participation relationship entry remains owned by the team page; calendar composition is unchanged.

## Native maps

**Decision**: Use `react-native-maps` 1.27.2 with Apple Maps on iOS and Google Maps on Android. Keep the approved Blockout markers, location selection and participant summaries. Use only accepted municipality coordinates, group coincident points without displacement, and request no device location. Native basemap behavior replaces the former requirement to detect every tile failure; zero and partial location coverage remain explicit.

**Rationale**: The [Expo map-view integration](https://docs.expo.dev/versions/latest/sdk/map-view/) supports this ordinary platform split within the accepted Expo 58 baseline. Google key restrictions and build configuration are future implementation work, not provider changes in this task.

**Alternatives**: `expo-maps` was still alpha in the examined documentation, with relevant Apple marker interactions requiring a newer iOS minimum. A timer or tile-error detector cannot reliably establish basemap failure. Google-only maps on both platforms adds an iOS integration the accepted experience does not need.

**Evidence limits**: `onMapLoaded` is Google-specific; readiness is not proof that all tiles loaded. The [Google callback documentation](https://developers.google.com/android/reference/com/google/android/gms/maps/GoogleMap.OnMapLoadedCallback) also distinguishes loading and interruption. The web prototype's Leaflet/OpenStreetMap background illustrates interactions only. Native marker rendering, touch handling, accessibility and physical-device behavior remain unqualified.

## Match documents and source authority

**Decision**: Keep three separate documents: information sheet for any viewable match with a qualified reference; official scoresheet after a definitive result; and professional statistics PDF under the same result condition. F02 treats a published official result as definitive unless contrary evidence exists. No additional confirmation, homologation wait or player-statistics extraction is added.

**Professional association**: DataProject remains the sole source of professional sporting identity, presence, participants, schedule, results and standings. The applicable LNV XML supplies only an FFVB information-sheet code. Verified team-label associations are technical configuration scoped to season and championship; exact participants/date and a unique candidate establish the document association. Once established, its code stays attached to the same match through rescheduling. No fuzzy matching, automatic alias learning, operator UI or historical reconstruction from current feeds is selected. Unmatched references remain unavailable.

**Observed evidence**: The official [LAM](https://www.lnv.fr/xml/calendrier-LAM.xml), [LAF](https://www.lnv.fr/xml/calendrier-LAF.xml) and [LBM](https://www.lnv.fr/xml/calendrier-LBM.xml) feeds and DataProject calendars were examined. Exact names/date alone matched 90 of 536 examined current-calendar entries; this bounded exploratory comparison establishes neither complete coverage nor production parser correctness. Differing published labels explain the need for verified associations. A current professional prematch code returned an information-sheet PDF through the official FFVB form before the match had a result. Current feeds establish no historical availability.

**Acquisition**: The [FFVB information-sheet endpoint](https://www.ffvbbeach.org/ffvbapp/adressier/fiche_match_ffvb.php) returned a PDF for a form POST using `wss_saison`, `codmatch` and `codent`; equivalent GET parameters returned HTML in the examined request. The [FFVB scoresheet endpoint](https://www.ffvbbeach.org/ffvbapp/resu/ffvolley_fdme.php) returned a PDF for a qualified amateur reference. Completed DataProject matches exposed distinct Scoresheet and DataVolley links through ordinary Telerik form POSTs using the page's hidden fields and actual tab event. The examined documents were PDFs, including one served as `application/octet-stream`. Do not guess blob URLs, fixed tab indices or a document from another match.

**Alternatives**: Recreating V1's full FFVB/XML/DataProject sporting merge adds competing authorities. Guessing codes or joining only by labels risks opening another match's document. Dropping prematch information sheets loses accepted utility. The narrow qualified-reference exception preserves both simplicity and sporting ownership.

**Evidence limits**: Sampled current and historical documents establish concrete retrieval paths, not complete seasonal coverage or perpetual supplier support. Qualified origins/redirects and form context must be tested against representative fixtures before implementation adoption. No raw provider PDF or personal information is committed.

## PDF transport and reading

**Decision**: The backend relays the qualified document on demand, outside SQL transactions, using bounded ordinary HTTP requests and the accepted source reference. It accepts no arbitrary client URL. The mobile downloads through its shared transport with cancellation, writes a temporary Expo FileSystem file and displays that local URI with `react-native-pdf` 7.0.5. Remove temporary files on close/failure and leftovers at cold start; no offline archive, export workflow, token renewal, job or automatic retry is added.

**Rationale**: [react-native-pdf 7.0.5 source](https://github.com/wonday/react-native-pdf/blob/v7.0.5/index.js) supports direct PDF viewing on both platforms. Its inspected 7.0.5 download implementation retains cache files even with `cache: false` and does not actively cancel its download on unmount. Keeping network ownership in the common transport avoids relying on those behaviors. The reader receives a local file only. [Expo FileSystem](https://docs.expo.dev/versions/latest/sdk/filesystem/) provides cache files, byte writes and deletion; [Expo Fetch](https://docs.expo.dev/versions/latest/sdk/expo/) supplies the standard transport building blocks.

**Alternatives**: System external readers do not guarantee reading without another installed application. A Google Drive viewer adds a third-party dependency and disclosure of the source URL. A custom PDF renderer or patched dependency would duplicate supported native rendering.

**Evidence limits**: The examined supporting package was `react-native-blob-util` 0.25.1. Published config plugins 14.0.2 declare Expo >=56 compatibility; unpublished repository versions are not selected. PDF reader source/release notes address Android page-size compatibility, but no Expo 58/RN 0.88 native build, physical-device rendering, cancellation or cleanup has been executed here. Qualify the declared package combination before adoption; failure reopens this boundary rather than authorizing a fork or a changed minimum platform.

## Contracts, privacy and operations

**Resource implementation boundary**: The canonical `Consultation` tag groups resource and logo operations into a generated Java interface independently of pending calendars, standings, participants and documents. HTTP paths, operation identities and response meanings stay unchanged. The application read port exposes only implemented resource projections; later stories extend it. The schedule source zone is optional because F02 accepts a sporting date without a known zone. Such a date remains unchanged; neither transport nor presentation supplies a fictional zone or instant.

**Decision**: Retain F13's OpenAPI 3.0.4, Redocly, OpenAPI Generator and Orval pipeline and existing Problem Details responses. Public projections contain only effective authorized values. Account, follow and editing state remain separately owned. Binary PDF/image responses are intentionally not parsed as JSON; successful JSON is validated once before caching. Common access restrictions apply to public reads and document/image delivery.

**Rationale and limits**: Resource summaries avoid repeated calls without exposing private administrative values or adding a universal aggregate. Ordinary logs identify operation, bounded outcome and safe diagnostics, never contacts, referee names, PDF contents or provider payloads. F11's durable suppression applies to club contacts; F03 adds no generic personal-data registry. There is no collection schedule, incident workflow, performance programme or recovery service specific to consultation.

**Verification**: Contract lint/bundling and prototype checks are distinct from generated-consumer compilation, native behavior, source qualification and design approval. The latter retain the explicit gates and scenarios in [plan.md](plan.md) and [quickstart.md](quickstart.md).
