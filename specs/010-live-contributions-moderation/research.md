# Research: live contributions and moderation

## Local address recognition

**Decision:** Parse with Java 25 `URI`, require an absolute HTTP(S) address, a nonempty recognized host and no user information. Compare case-insensitive exact domains or dot-delimited subdomains of youtube.com, twitch.tv and facebook.com; also accept youtu.be and fb.watch. Preserve the submitted path, query and fragment. Compare stored addresses literally for same-owner active/pending deduplication; no provider identity inference.

**Rationale:** [Java URI](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/net/URI.html) supplies syntax and host/user-info components without network resolution. Recognition establishes neither video existence nor availability. No provider request, SDK, redirect expansion or query cleanup is justified by the accepted journey.

**Alternatives:** Remote validation introduces provider availability and access dependencies without guaranteeing later playback. A custom URL parser adds no useful guarantee.

**Generated-binding rationale:** F08 URI properties retain `format: uri` without a redundant `minLength`. OpenAPI Generator 7.26.0 maps them to `java.net.URI`; a length constraint on that type produces `@Size`, which is invalid for URI and causes `UnexpectedTypeException`. [Jakarta Validation 3.1 §8.13](https://jakarta.ee/specifications/bean-validation/3.1/jakarta-validation-spec-3.1#builtinconstraints-size) supports character sequences, collections, maps and arrays, not URI. The schema preserves the URI contract and required fields; local HTTP(S)/host/credential rules remain T007/T010, rather than being claimed from DTO binding. No generator template, shared configuration or generated output is edited.

## Transactions, quotas and erasure

**Decision:** Use short JPA transactions and the existing sporting-root/account lock order. Match publication and sporting result acceptance serialize on the match. Lock the submitting account for quota evaluation across matches. Count recorded ordinary versions and distinct matches between successive Europe/Paris midnights; record quota participation when creating a version. Use partial uniqueness for active match versions, pending owner/match versions and reports with an existing author. Re-read original ownership after account locking before copying it into a reactivation.

**Rationale:** [Spring Data JPA locking](https://docs.spring.io/spring-data/jpa/reference/jpa/locking.html) supports repository lock metadata. [PostgreSQL partial indexes](https://www.postgresql.org/docs/18/indexes-partial.html) enforce conditional uniqueness, and [explicit locking](https://www.postgresql.org/docs/18/explicit-locking.html) supplies transaction-scoped row protection. [LocalDate.atStartOfDay](<https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/time/LocalDate.html#atStartOfDay(java.time.ZoneId)>) expresses calendar boundaries; adding 24 hours would fail on Paris daylight-saving changes. F05 erasure retains report facts but nulls their author and reason; these anonymous rows must not collide.

**Alternatives:** Unsynchronized counts alone cannot enforce concurrent quotas. Synchronized counters, daily reset jobs and distributed locks add lifecycle work without need. A general decision/event ledger duplicates the necessary version state. F07's required internal effects stay in the same transaction; its ordinary post-commit push is not guaranteed delivery. Moderation REJECT and WITHDRAW retain actor/attribution locks and revision checks without selecting or locking subscribers, because they publish no announcement. Publishing branches retain the audience and atomic inbox boundary; blanket best-effort inbox generation would weaken the accepted transaction semantics.

## Current-state reads and HTTP resources

**Decision:** Keep the existing mobile OpenAPI root, page-based twenty-item lists and shared Problem Details. Version-change commands carry the viewed contribution revision; administrative commands also carry the original actor account UUID. Reports retain their canonical reason-only input and exact version resource. A stale revision returns 409 before duplicate/no-op evaluation. A lost version-change response uses ordinary failure feedback and query invalidation; a later explicit action carries the original target and revision under current rights without requiring a successful GET. Safe-read Retry invokes only its GET. An accepted acknowledgement remains accepted if the invalidated read later fails. There is no dedicated confirmation read or failed-command ledger, automatic write retry or exact historical receipt. A current authorized `reported:true` for the exact account/version establishes “already reported”, including after a lost POST response, without claiming a particular request succeeded. False or failed reads retain useful input and ordinary retry; false cannot exclude delayed completion. The report’s account/version uniqueness and unchanged-duplicate response preserve the first reason and effects without a dedicated recovery state, mandatory after-error read or automatic replay. Use the existing Surface/icon/color roles for the owner-requested minor terminal-card refinement: a decorative CircleCheck beside the same status message, secondary address metadata and the ordinary header Back, without a duplicate bottom return button. The reason form keeps its submit/cancel controls and ordinary dirty-draft protection while unresolved. Once acknowledged or authorized already-reported state is established, the existing discard guard no longer prompts on header Back, even if the retained RHF reason is still dirty. This is a condition on the current guard, not a new mechanism; no new route, library component or interaction pattern is needed.

**Rationale:** The existing [contract conventions](../003-shared-quality/contracts/README.md), [HTTP semantics](https://www.rfc-editor.org/rfc/rfc9110.html) and [PATCH semantics](https://www.rfc-editor.org/rfc/rfc5789.html) fit completed synchronous operations. Body revisions follow already approved business-conflict semantics; no HTTP conditional header is introduced. Known current state is useful even when a delayed request can still finish afterward.

**Alternatives:** Requiring the missing acknowledgement when an authorized exact account/version read already proves the useful business state adds uncertainty without changing that state. A request registry, durable job or replay queue adds retention and reconciliation work. Cursor snapshots are unnecessary. The personal proposal list requires an exact `proposalCount` across all owner/match versions, including active and terminal states, to satisfy the always-visible total; compute it with a SQL aggregate beside the page in the same repeatable-read transaction. No stored counter or downloaded-page count is needed. Other list envelopes are unchanged. No generic bulk endpoint or hypermedia framework is needed by the current callers; resource-shaped routes alone are not a claim of full REST conformance.

The private owner collection also projects its exact active member independently of pagination. An old active version may be outside the first twenty rows after moderator-created exempt versions; searching those rows cannot establish ownership or prefill the editor reliably. Reuse the existing owner/match/ACTIVE query in the same read snapshot rather than downloading history, exposing public attribution or interpreting a foreign-member 404 as global access refusal.

## Own-command compatibility

**Decision:** Keep exact-member PATCH for active withdrawal and remove only the pending `cancel` action and `canCancel` capability. Preserve historical cancelled states/decision values, quota participation and their exclusion from reactivation. The admitted backend/mobile boundary and current native consumers expose no pending cancellation journey; no admitted external consumer was identified.

**Rationale:** An executable command without an admitted caller duplicates lifecycle and qualification work. Read-only history, superseding by a later eligible submission and authorized moderation retain the accepted proposal handling.

**Alternatives:** Keeping an unexposed command preserves unnecessary authorization, mapping and test branches. Removing the PATCH or historical values would break active withdrawal or readable retained history and is outside the intended amendment.

## Search, attention and mobile freshness

**Decision:** Use parameterized PostgreSQL substring queries over effective team names and recorded addresses, escaping LIKE metacharacters. Filter by season, platform and state. “To review” is a query over pending proposals, unresolved hiding waits and reported active versions. Use native Spring Data paging/Slice and TanStack Query's existing explicit fetching/invalidation, with no polling. The queue includes optional canonical season labels from retained contribution roots; deriving choices from only the loaded page would omit valid hidden or off-page seasons, while a new filter endpoint is unnecessary.

**Rationale:** [PostgreSQL pattern matching](https://www.postgresql.org/docs/18/functions-matching.html) provides ILIKE; [Spring Data query methods](https://docs.spring.io/spring-data/jpa/reference/jpa/query-methods.html) provide the ordinary query boundary. [TanStack Query invalidation](https://tanstack.com/query/v5/docs/framework/react/guides/query-invalidation) and [query cancellation](https://tanstack.com/query/v5/docs/framework/react/guides/query-cancellation) support the selected memory-only lifecycle. Current counts come from database aggregates, not downloaded pages.

**Alternatives:** A search index duplicates private moderation state. An “examined” state would create an unrequested workflow. Polling and persistent caching add freshness and privacy obligations without an accepted need. Retain manual refresh and ordinary action/read feedback.

## Evidence limits

The [approved design](plan.md#approved-design-and-evidence) covers complete moderator actions, unavailable report reasons and current-state recovery. Prototype behavior does not establish native/provider qualification.

Documentation supports native capability choices; use [the quickstart](quickstart.md) to validate generation, compilation, PostgreSQL concurrency and owner integration. Native networking/accessibility and F07 integration require their actual runtime boundaries; source inspection establishes none of those outcomes.

## Contribution draft lifetime under admission gates

Use route-local RHF fields and a coherent original revision, following the shared [form conventions](../003-shared-quality/plan.md#frontend-form-conventions). The same RHF owner and native scroller/RefreshControl ancestors remain mounted through required account, Match and private-owner loading/error/Retry. Dirty address/reason, choices and applicable prepared files survive while admissible. F05 owns account recovery; exact resource/form readers own their scoped F13 card. A disabled dependent Query still has an explicit prerequisite result. Exhausted initial/full-read errors replace the dependent content even when Query retains admitted data; the form stays mounted but its dependent content is hidden until recovery. Technical failures and lost write responses mark affected reads stale without immediately refetching them, so mutation recovery does not become a successful-GET prerequisite; the [plan](plan.md#mobile-state-and-failures) owns that Query policy. Only a failed next page retains the list with the shared error footer. Query owns server state and retries, with no copied draft or recovery manager. Current read errors remain current; refusal removes forbidden data, and a later technical failure restores neither data nor authority. Ordinary submission/replacement/saves act directly; withdrawal, draft abandonment and actual moderation decisions retain their existing safeguards. A protected-route removal discards the draft; reopening uses current server data. A detached RHF registry or mutation acknowledgement recovery owner is unnecessary. Native Query mutations retain ordinary pending/error outcomes and invalidate affected views at settlement. Server revisions, original-target ownership and deduplication preserve domain effects independently of client acknowledgement. Native/provider evidence remains scoped to the owning [qualification](quickstart.md); JavaScript lifecycle tests do not establish native execution.
