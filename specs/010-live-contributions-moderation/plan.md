# Implementation Plan: Live contributions and moderation

**Branch**: `tech/52-live-contributions-moderation` | **Date**: 2026-10-15 | **Spec**: [spec.md](spec.md)

**Input**: [spec.md](spec.md), [F02 sporting data](../002-sporting-data/plan.md) and [F09 entitlements](../006-pro-subscriptions/plan.md).

## Summary

Add account-owned stream contributions, exact-version reports and a complete video-moderation grant to the existing backend/mobile boundary. PostgreSQL versions, ordinary transactions, row locks and conditional unique constraints protect ownership, quotas and decisions. Validate addresses locally; use normal mutation errors and invalidation without an acknowledgement-recovery protocol. Use ordinary private database search and manual refresh rather than a search service or moderation workflow engine.

## Technical Context

**Language/Version**: Java 25 / Spring Boot 4.1.1 and TypeScript / Expo 58 / React Native 0.88 / React 19.3.0, under [F13](../003-shared-quality/plan.md).

**Primary Dependencies**: Existing Spring Data JPA/Hibernate, Java URI/time libraries, TanStack Query and the F13 generated HTTP boundary. No video-provider SDK or new dependency.

**Storage**: PostgreSQL 18.6 for contribution state, versions and reports; mobile query cache in memory only.

**Testing**: JUnit/Spring MVC/Testcontainers PostgreSQL, Jest Expo/React Native Testing Library and repository documentation/OpenAPI checks. [Quickstart](quickstart.md) defines runnable validation scenarios and expected outcomes.

**Target Platform**: Existing Linux backend and native iOS/Android clients.

**Project Type**: Mobile application with a modular backend.

**Performance Goals**: No throughput, load/capacity benchmark or monthly availability commitment. Page ordinary private lists; avoid per-row lookup loops.

**Constraints**: Current rights and sporting visibility, original account identity, seven-day age/H−1 rules, Paris-day quotas, no provider calls, mutation replay, polling, durable recovery journal or additional service.

**Scale/Scope**: Nonprofessional match links, personal proposals, reports and private moderation. Professional links, sporting truth, subscriptions and notification delivery remain owned by their existing features.

## Backend behavior and ownership

The [data model](data-model.md) defines versions, current match revision/hold and report facts. An approval publishes the pending version itself. Reactivation creates a new version linked to its historical source, preserving only a still-present owner; it inherits no report and uses no ordinary quota. Selected moderator publication/approval/reactivation supersedes other proposals and resolves the report hold. Rejection and withdrawal do not resolve an unrelated hold. Pending proposals expose no cancellation command; historical cancelled versions and decision values remain readable and cannot be reactivated.

Use Java URI for local syntax/host recognition as defined in [research](research.md#local-address-recognition). Do not fetch provider content or infer equivalence between short links, query variants or channel/video addresses. Only an identical current active/pending address for the same owner qualifies for an unchanged-submission response, after current revision and authorization checks and before quota rejection.

Acquire necessary sporting roots in [F02 order](../002-sporting-data/plan.md#acceptance-and-concurrency), then all concerned accounts in UUID order, then re-read current eligibility, grants and ownership. Moderation REJECT and WITHDRAW select and lock the actor and affected attribution accounts only; neither branch publishes an announcement, so subscriber-audience selection and locking are unnecessary. APPROVE and all other publishing branches additionally select and lock the F07 audience before publication, preserving its required atomic publication/inbox effects. No provider call or sporting-root acquisition follows an account lock. The match lock serializes publication against definitive-result acceptance. The submitting account lock serializes quotas even for different matches. Counts derive from persisted quota-participating versions; no refunds after lifecycle changes. Read current Auth0 principal-age evidence from F05; missing evidence fails the dependent publication only, with its existing explicit retry.

F05 local erasure removes report attribution and reason, detaches version/decision ownership and preserves report facts and decisions. Re-read ownership after locking before copying a historical version. A deleted account cannot be resurrected through pending requests or re-registration. Addresses with personal content remain subject to F11's existing rights procedure, not an invented automated scrubber.

## Interfaces and compatibility

The [contract guide](contracts/README.md) identifies providers, consumers and canonical routes. The admitted boundary is the backend and signed-in mobile client; native callers use the exact-member PATCH only for active withdrawal. No admitted external pending-cancel consumer was identified. Retire only the pending `cancel` action and `canCancel` projection, preserving the PATCH route, required revision, active withdrawal and readable historical cancellation states/decisions. Personal routes use the original account UUID. Administrative commands include the original actor UUID and require `stream-links.moderate`; the corresponding `moderateStreamLinks` projection permits all video-moderation actions, without unrelated powers or implicit maintenance bypass. All routes retain existing application admission and explicit bypass semantics.

Use the viewed match contribution revision in version mutations. Stale revision means 409 without effects, including a stale no-op. Reports target a version and deduplicate by account without transferring to a later version; the first reason remains authoritative. Completed creations return 201 and Location, recognized current repetitions return 200. No 202 or historical command receipt.

Lists return twenty items with optional `nextPage`, following the existing page convention. Keep filters for continuation and restart at page zero on refresh. Concurrent changes may move items; no snapshot traversal guarantee. Private match context can represent hidden or dateless matches, so it does not incorrectly reuse F03's publicly viewable dated-match wrapper. Reuse its identity, pool, schedule and result primitives where their meanings fit.

Moderation search uses parameterized ILIKE with literal wildcard escaping. A matching version must satisfy platform/state/address criteria together; team-name matching applies to its owning match. “To review” is pending versions, unresolved report-hidden wait or reported active links. Match badges distinguish current attention from history: count reports on the active or unresolved hidden version, and expose rejected versions as a historical total. Retain old reports in per-version history. Count through SQL aggregates over current data; no stored counter and no total inferred from a loaded page. Read related context, page and counts in a short read-only repeatable-read transaction when multiple queries are needed, keeping one internally coherent response without promising stability across requests. The private queue also supplies canonical season labels for all retained contribution activity, including hidden roots, independently of filters. This small additive response projection supports the existing season selector without a new endpoint or unrelated collection-management grant.

F03 adds `streamContributionId` only alongside a contributed `streamUrl`. It exposes no author, report, quota or moderation detail. F05's account response gains the optional moderation capability through F12's existing projection. These are additive fields; request shapes and enums remain strict, response fields additive. F13 owns admitted-client compatibility and generated Java/Orval/Zod integration; no dialect or generator change is selected.

F07 consumes accepted transitions in-process under the same match transaction, with necessary inbox/announcement facts committed together. At sporting result acceptance it reads the current public link under that same lock. A rollback changes neither versions nor internal notification state. Push follows commit under existing best-effort rules, including maintenance. No report reset, reactivation or inbox purge replenishes an already consumed announcement allowance. No private moderation notification is added; the [F07 plan](../011-notifications-delivery/plan.md#announcement-processing) owns delivery and recipients, with current link presentation derived on reads rather than synchronized text copies.
