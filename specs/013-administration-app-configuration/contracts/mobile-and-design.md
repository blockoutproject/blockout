# Mobile access, forms and design contract

## Ownership and request lifecycle

`apps/mobile/src/features/configuration/` owns process-local access configuration, maintenance/version forms and their domain projections. Thin Expo Router routes compose existing F05 sign-in, F10/F11 support/privacy/legal and F13 UI. Tokens and session generation remain F05/F13-owned. Capabilities are private in-memory server data; bypass is an account-bound memory choice; neither belongs in public persistent storage.

Run a complete public check on process cold start and explicit Retry. Auth0 browser return is not a cold start and must preserve pending access context; resolving capabilities after sign-in is a separate private query. Disable focus, reconnect, interval and incidental remount access refetches. F13's single eligible automatic read retry is inside one check, with its 10-second request deadline and one-second delay. Never start a session-expiry timer.

Read the installed native application version, not an OTA bundle value or internal build number, whenever its condition is reassessed. Return from a store does not by itself trigger a full configuration check; the explicit Retry action does. Store opening does not prove an installation.

## Access decision and precedence

Compute both maintenance and relevant-platform version restrictions. Presentation shows maintenance first, as FR-027 requires; bypassing/lifting it still leaves a version restriction. A known minimum also prevents navigating to mobile administration even when maintenance is the currently displayed page.

| Established condition                            | Ordinary application                                | Configuration administration                                                                                                                | Retained paths                         |
| ------------------------------------------------ | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| Reliable unrestricted snapshot                   | Domain rules                                        | Current corresponding manage permission                                                                                                     | Legal/privacy, support, identification |
| Active maintenance                               | Blocked unless explicit currently authorized bypass | Corresponding manage permission, no bypass needed                                                                                           | Same                                   |
| Unsatisfied applicable minimum                   | Blocked                                             | Blocked, including owner                                                                                                                    | Same                                   |
| Unknown/malformed installed version with minimum | Explainable blocking error with Retry/support       | Blocked                                                                                                                                     | Same                                   |
| Unknown installed version without minimum        | No version restriction                              | Other rules still apply                                                                                                                     | Same                                   |
| Complete public verification unavailable         | Blocked                                             | Targeted recovery entry only with current permissions, provided no known version block; editing requires reliable administrative group read | Same                                   |

An unavailability state does not fabricate maintenance or a minimum. Keep an already known restriction until a reliable newer/equal observation establishes its removal. Administrative group reads/writes can update the observed group but cannot establish complete ordinary access from unavailability; Retry must succeed. Recovery navigation never exposes ordinary tabs/deep links. Failed capabilities loading cannot imply permission. A version block already observed during this process remains effective in recovery.

## Complete verification and out-of-order responses

Start each process with no access snapshot and an unavailable verification outcome. Never hydrate access configuration, revisions or a verification timestamp from storage, including a legacy persisted value. No access-storage adapter, envelope, age allowance or wall-clock threshold remains. Public observations belong to the current environment/API origin and process; discard responses from a different context.

For each resource maintain its highest accepted revision/value in memory. Accept only structurally and semantically valid responses. An equal revision must describe the same normalized value; conflicting equal-revision content is invalid/unavailable rather than last-response-wins.

- On a complete public response, compare both resource revisions against all accepted observations. If either is older, do not install it as a verified complete snapshot or reopen access. Valid non-older groups may strengthen resource knowledge, but cannot turn this stale full response into complete verification. Do not automatically issue another check; retain truthful state and explicit Retry.
- On an eligible non-stale complete response, install both groups, mark complete verification successful and recompute both restrictions. A current restrictive complete response is still a successful verification; its restriction remains effective.
- On `503 MAINTENANCE_ACTIVE`, validate its typed maintenance projection and merge only if non-older. Apply blocking unless the response is older than established newer state. This observation remains in memory and cannot establish complete verification.
- Administrative reads/saves establish only their returned group. Merge by revision without certifying complete access. During unavailability they never open ordinary navigation, even when the observed maintenance is now inactive; complete Retry must succeed.
- A failed check keeps ordinary access unavailable. A recent success from a previous process, stored permissive value or successful partial read is no substitute. Retain current-process restrictions/revisions so failure or a late permissive response cannot remove them.
- An already open session has no expiry timer or added periodic, foreground, authentication-return or reconnect check. Ordinary server refusals still apply. At the next cold start, discard the prior process state and require complete verification again.

Public responses may remain usable across an account change because they contain no rights. Private responses and private mutation continuations must match F05/F13's session generation. Access verification never restores private capabilities or bypass choices.

## Bypass and typed errors

After explicit choice, store bypass only in the current account's memory context and send `X-Blockout-Maintenance-Bypass: true` on concerned requests. Recheck current capability for UI, and current account/permission on the server. Logout, account change, deletion or full restart clears the choice. Maintenance deactivation/reactivation within the same memory context does not. Minimum versions are never bypassed.

F13's API mutator recognizes `MAINTENANCE_ACTIVE` before deciding whether HTTP 503 merits a read retry: this business refusal never retries automatically. It validates the `maintenance` extension before installing public state. A recognized refusal with unusable projection must still prevent ordinary continuation and surface an unavailable state; malformed content cannot manufacture a reliable configuration. Technical configuration/dependency errors use bounded eligible read retries; mutations never auto-replay. Unknown safe error codes use the generic F13 fallback.

## Forms and uncertain outcomes

| State                            | Required semantics                                                                                                                                                    |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Initial loading/read failure     | No invented published defaults; disabled editing/saving until a reliable group read                                                                                   |
| Published / clean                | Display server resource and revision; previews have no side effects                                                                                                   |
| Dirty draft                      | Preserve user input across refresh, failed refresh and capability changes; never install draft globally                                                               |
| Saving                           | Prevent duplicate submission, preserve submitted expected revision and draft; F13 deadline                                                                            |
| Refusal or confirmed failure     | Keep accepted resource intact, explain correction/retry; no hidden activation                                                                                         |
| Conflict                         | Keep draft; read current resource, present conflict, then explicitly rebase/edit and resubmit against current revision                                                |
| Uncertain result / lost response | Read the relevant administrative resource before another submission. Show observed state without claiming which request caused it. Failed reread retains uncertainty. |
| Saved                            | Install actual returned state/revision; maintenance content save never toggles state; subsequent edit starts from that state                                          |

A lost response followed by another operator's edit is not resolved by comparing text and inventing request history. No automatic retry, receipt registry or overwrite of a dirty draft is introduced. Navigating away from dirty input uses the approved discard confirmation. Previewing image/message/versions never saves or activates them.

For adding/raising any minimum, show the correct-platform store link and the approved unchecked availability confirmation. Submission requires human confirmation; server independently validates the command flag and candidate. Do not reuse an old checkbox acknowledgement for a newly changed minimum/link. No periodic store checks. Use understandable French fallback update text without a deadline or availability promise. Failed image rendering retains text and actions; honor reduced motion for animated media. Failed store opening retains the restriction with retry/support.

Retry uses the approved shared page pull-down action, with the visible explanation on the unavailable screen; do not revive its hidden button. The web prototype also exposes Alt+R. Native implementation must expose an understandable accessible refresh action, announce its outcome and place focus coherently on the gate heading, without duplicate read-error toasts or mutation replay. Future native review covers both themes, small screens, large text, semantic labels/roles, focus after errors/dialogs, touch targets, reduced motion and support/store external navigation. Metadata/screenshots support design mapping only; browser evidence cannot qualify native authentication, installed version or actual store availability.
