# F12 research and decision record

**Date**: 2026-10-09. Authority: [specification](spec.md), [architecture](../../docs/architecture.md), [design authorities and approvals](../../docs/design.md). This is design rationale, not a runtime or provider qualification report.

## R01 — Current permissions independent of authentication

**Need:** FR-001–005 require immediately effective revocation, no implicit privilege and ordinary account capabilities. **Decision:** Auth0 authenticates; `accounts.account_permission` stores a fixed catalogue against the current business UUID. Resolve account usability and required permission on the server for each protected action and again at domain mutation where work crosses an external operation. **Simpler alternative:** token scopes alone would avoid a SQL grant lookup but remain bounded by already-issued token lifetime. Auth0 roles plus a second permission copy create competing authorities. **Consequence:** authentication success or an old capability response never grants authorization. No per-resource grant model is built today; domain services still receive and validate the target resource. **Proof:** new account defaults, retained revocation after login, direct requests with stale tokens, final checks after upload and account replacement.

Auth0 documents that an [API token remains valid until expiry](https://support.auth0.com/center/s/article/Invalidate-the-API-token-after-user-logout). [Spring method security](https://docs.spring.io/spring-security/reference/servlet/authorization/method-security.html) offers enforcement hooks; Blockout's accounts interface supplies current business decisions rather than relying solely on JWT authorities.

## R02 — Owner-operated SQL rather than permission administration

**Need:** FR-002 reserves privileged assignment to the product owner without a console. **Decision:** controlled transaction targeting a verified environment and exact current UUID, with before/after grant review. Only the owner has the operational database access needed for this procedure. Three ordinary contribution grants are inserted in the actual F05 new-account transaction and removed in its local erasure transaction. **Alternative:** a permission-management API, role hierarchy, delegation or email lookup adds product capability or target ambiguity. **Consequence:** grants are explicit and global to their present domain; SQL remains an operational boundary, never an app permission. **Proof:** invalid code/FK/duplicate constraints; no regrant on subsequent bootstrap; rollback on invalid target; recreation gets no privileges.

## R03 — Two singleton resources with independent optimistic revisions

**Need:** FR-006–011 separate content from activation, prevent stale writes and preserve unrelated settings. **Decision:** maintenance shares one revision across content and state; versions has another revision. Read a coherent public snapshot with one SQL statement (or equivalent single repeatable snapshot). Mutations validate the merged candidate, lock/check the owning row and change revision only on an effective write. **Alternative:** last-write-wins loses decisions; separate content/activation revisions permit activation of unseen content; one global revision conflicts across unrelated groups. **Consequence:** safe integer revisions, explicit null/absence, no runtime default recreation. **Proof:** two concurrent writers, content/activation race, no-op, missing singleton, revision overflow and independent group changes against PostgreSQL.

## R04 — Admission is not durable business acceptance

**Need:** FR-012/019/020 block new ordinary HTTP work while preserving accepted operations and collection. **Decision:** root security checks maintenance once before the use case. Domain mutation still checks usable account, current permission, target, revision and invariants. **Alternative:** checking maintenance at every intermediate step would imply cancellation/compensation of external effects; checking only at HTTP admission would permit revoked rights after uploads. **Consequence:** a request admitted just before activation can finish under its domain rules, but may still fail its final authorization or revision check. External HTTP calls never run inside SQL transactions. **Proof:** activation between admission and mutation, revocation during upload, concurrent F01 closure/control and unchanged collection state.

## R05 — Explicit in-memory maintenance bypass

**Need:** FR-014 requires a personal choice without global or version exemption. **Decision:** memory boolean in the current F05/F13 account session; attach the explicit bypass header only to concerned requests. Server resolves the current permission. Full process restart, logout or account switch clears the choice; maintenance off/on in the same memory context does not. **Alternative:** persisted preference risks carrying intent across startup/accounts; server bypass sessions add an unnecessary lifecycle. **Consequence:** no extra token, table or permission. **Proof:** separate operators, forged header, revoked bypass, same-process off/on, cold restart and native auth-browser return.

## R06 — Complete verification separate from partial observations

**Need:** FR-015–018 require complete verification at every cold start and prevent late permissive responses from erasing current-process restrictions. **Decision:** keep the complete-verification outcome and per-resource revision/value knowledge only in memory. Start unavailable with no restored snapshot; a failed check stays unavailable, even immediately after a prior successful process. Gate complete responses against both observed revisions. **Simpler alternative:** accept whichever response arrives last; rejected because partial or older observations could reopen access. Persisted fallback adds storage, age and corruption handling without retained product need and is removed. **Consequence:** only an eligible complete successful check admits ordinary access; partial administrative observations never do. Open sessions acquire no timer, polling or foreground/authentication check. **Proof:** successful cold start; failed next cold start after recent success; explicit retry success/failure; ignored legacy stored state; current-process refusal/late-response races; partial administrative recovery and Auth0 return.

[TanStack Query focus refetching](https://tanstack.com/query/latest/docs/framework/react/guides/window-focus-refetching) is normally automatic; disable it for this access check along with reconnect/mount retries that would create additional checks. F13's one bounded eligible read retry belongs to the same explicit verification attempt.

## R07 — Business maintenance error before generic retry

**Need:** FR-016 must block on an ordinary operation's refusal without silently replaying it. **Decision:** identify `503 MAINTENANCE_ACTIVE` before F13 transient-error retry selection; consume its typed maintenance projection. Configuration-read failure is a distinct technical unavailability, never invented maintenance. **Alternative:** treating every 503 as transient delays meaningful blocking and repeats unwanted actions. **Consequence:** mutations are never automatically repeated; technical reads retain F13's limits. **Proof:** maintenance 503 causes zero retries; dependency 503 follows the bounded read policy; malformed error payload never installs invalid configuration.

## R08 — Native numeric versions and human store confirmation

**Need:** FR-024–030 require per-platform thresholds, truthful unknown versions and actual availability checks. **Decision:** compare `expo-application` native application version, using one to three bounded numeric components normalized to three. New/raised minima require the correct qualified Blockout HTTPS store URL and an explicit human acknowledgement. **Alternative:** lexical comparison misorders 2.10/2.9; JavaScript update metadata or build numbers do not represent the installed published version; store polling introduces unrequested automation. **Consequence:** real store identities are F14 inputs, URL format is not availability proof, unknown installed version blocks only when a minimum exists. **Proof:** numeric boundaries, normalization parity in Java/TS, actual native builds, wrong store identity, checkbox and failed store opening.

Expo distinguishes [native application version](https://docs.expo.dev/versions/latest/sdk/application/) from the native build version and describes [app version management](https://docs.expo.dev/build-reference/app-versions/). No browser or Expo Go result qualifies the installed production binary.

## R09 — URL media and truthful form outcomes

**Need:** FR-007–011/031 preserve optional imagery, draft input and verifiable uncertain outcomes. **Decision:** absolute HTTPS image URL without userinfo, no backend fetch, local preview, accessible text/actions on image failure. Keep published resource, draft, request state and observed revision separate. Read before resubmitting after lost response. **Alternative:** upload/provider verification or a receipt ledger adds a new media or workflow owner; blind retry risks replacing newer content. **Consequence:** observing matching content does not prove which lost request committed. **Proof:** optional removal, invalid URL, failed image, unchanged active state, dirty refresh, conflict and lost acknowledgement.

## R10 — Push suppression at the real F07 sending boundary

**Need:** FR-021–023 retain inbox/history without a maintenance backlog. **Decision:** F07 calls configuration's in-process maintenance read immediately before an ordinary push attempt. Active or unavailable means skip sending; retain ordinary inbox/purge semantics. **Alternative:** operator bypass or deferred replay would violate intended notifications; pausing all F07 processing would lose announcements. **Consequence:** no queue, retry window or recall guarantee. **Proof:** actual F07 integration including maintenance failure, operator recipient, reopening and already-handed-off message. A controlled interface test alone cannot complete that evidence.

## R11 — Proportionate diagnostics and scoped design revalidation

**Need:** FR-034–036 require understandable states, native accessibility and transition compatibility. **Decision:** F13's safe Problem/diagnostic ID, ordinary operational errors, French UI, the 2026-10-09 F12 prototype/Figma revalidation under [#37](https://github.com/blockoutproject/blockout/issues/37), and F14 compatibility matrix. **Alternative:** extra audit ledger, emergency app, SLA accounting or re-created designs add no required capability. **Consequence:** no secrets, bearer tokens, private account data or image URL payloads in logs; report safe operation/error category and opaque diagnostic reference. **Proof:** payload exclusion, approved visual mapping, actual themes/text scaling/focus/reduced motion, old-client additive fields and F14 store qualification.
