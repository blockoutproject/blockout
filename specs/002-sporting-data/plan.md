# Implementation Plan: Sporting identity, integration and lifecycle

**Branch**: `tech/43-f02-technical-plan` | **Date**: 2026-10-13 | **Spec**: [spec.md](spec.md)

**Input**: [spec.md](spec.md) and the accepted [F13 foundation](../003-shared-quality/plan.md).

**Status**: Accepted technical decisions and scoped design. [Tasks](tasks.md) track implemented work and remaining qualification; [quickstart](quickstart.md) defines runnable validation scenarios and expected outcomes.

## Summary

Keep one authoritative sporting model in the modular backend. The separate collector submits contextual observations; the backend accepts matches independently, preserves useful partial success and reconciles absence only after a complete successful current calendar. Professional teams use LNV identities without requiring a club. Standard PostgreSQL transactions, JPA locks, unique constraints and retained observation/locality revisions protect current facts and ordering without a recovery platform.

**Scale/Scope**: Covered FFVB competitions and three professional LNV championships; current season and initial three completed seasons under F14. Ingestion JSON transport bound: 8 MiB, with an additional 1,000-entry calendar limit and explicit refusal instead of truncation.

## Identity and retained data

[Data model](data-model.md) defines stable Blockout UUIDs, contextual provider references, team participation, classification and presentation. PostgreSQL constraints prevent duplicate references and broken relationships; application use cases decide authorization and valid continuity. Names, dates and participant pairs never become substitute match identities.

`EstablishMatchIdentity` selects the [provider team key](data-model.md#corrections-and-provider-references) from the admitted pool. FFVB uses the attributable club and exact comparison name, with a scoped verified alias as a fallback. LNV uses the native `TeamID` in the admitted championship. Both paths verify continuity of the expected participant and compatibility with the pool's accepted classification. A professional club association is a controlled manual database edit, without an association API or dedicated workflow.

Derive visibility from the [current independent reasons and relationships](data-model.md#current-facts-ordering-and-visibility), rather than storing a universal copied flag. Season closure and privacy remain owner constraints on retained data.

### Professional context

This holds for a team without a club and across permitted changes to editorial division. [F08](../010-live-contributions-moderation/plan.md#backend-behavior-and-ownership) owns the contribution eligibility decision.

## Acceptance and concurrency

The [ingestion contract](contracts/README.md#ingestion) carries a qualified cycle context and normalized observations. A globally invalid context fails before writes. Identical source-reference repetitions collapse; contradictory duplicates isolate that match. Recognized byes/qualifiers remain distinct from failures and cannot create fictitious teams. A source-parsing failure is an explicit local outcome, never a silently omitted row presented as complete.

A nontransactional application loop calls a separately proxied transactional match use case. Each successful match commits independently. The final absence transaction runs only for complete, current, correctly contextualized and fully successful calendar processing. A single failed, unassociated or stale match blocks that finalization. A qualified current empty calendar may hide all its matches/participations; historical empty input cannot.

Use a monotonically increasing backend cycle order plus a collector read ordinal allocated before each supplier request. The cycle order dominates; it is a conservative logical ordering, not a supplier publication timestamp or a measurement of parallel request completion. F01 owns cycle registration, starting configuration and reconstruction mode. Per-match accepted order prevents old whole observations from applying, including late fields previously missing. No per-field salvage or observation history. Preserve actual observation times separately for freshness.

The pool's current calendar order advances when a globally qualified calendar is admitted. Check it before each match transaction and before finalization; a superseded request cannot create late identities, restore participation or reconcile absence. Keep the last completed order to recognize already finalized repeats without undoing newer work. Details only enrich already known matches and never restore calendar presence. Standing, club, logo and catalog observations use the same order discipline at their own replacement scope. [Catalog authority](#catalog-authority) owns source-wide presence. Calendar match commits retain their independent boundaries.

Serialize short sporting identity/participation/classification writes with `PESSIMISTIC_WRITE` on the existing season row, released after each match. Match writes and F08 publication share the match lock; club changes use the club row. For collection writes, first take the F01 shared runtime fence, then season and current control/cycle as needed, before the remaining sporting roots (division when required, match, club; sorted IDs within a kind). Keep the runtime lock through each domain commit; a startup replacement waits for those writes before invalidating the old incarnation. Manual sporting commands need no collector-runtime lock and retain the season-first order. Operations acquiring a later kind do not then acquire an earlier one. When the same transaction needs account locks for current grants, erasure coordination or personal inbox insertion, acquire them after sporting root locks and in sorted account UUID order; no sporting root lock follows an account lock. Manual permission changes lock the account before changing grants, under [F12](../013-administration-app-configuration/data-model.md#permissions-and-locking). Division state checks for new classifications are protected in the command transaction. Clubs shared across seasons retain unique provider-reference constraints; a concurrent creation conflict rolls back that item and is reported for a later collection, without speculative SQL upsert or distributed locking.

Separate locking a retained match's season, current division when classified and match from reading the facts the caller needs. Under those locks, [F07 due processing](../011-notifications-delivery/plan.md#announcement-processing) uses current visibility, reliable start, result finality and match, pool and team identities. The [F07 read acknowledgement](../011-notifications-delivery/plan.md#inbox-retention-and-mobile-state) takes the same locks before checking its own account and inbox member. F08 uses the [professional match fact](#professional-context) for contribution eligibility.

Current manual classification changes cannot be overwritten by the cycle's starting snapshot. Reject incompatible stale classification proposals from a collector cycle snapshot; removing acquisition settings retains accepted published classification. Division deactivation and source withdrawal remain independent visibility restrictions even when already-running work records otherwise valid facts.

### Catalog authority

F01 admits the source binding and qualifies completeness for its canonical season, provider and native organizer. The organizer denotes the FFVB organizer or LNV championship. `AcceptCatalog` verifies compound pool identities and LNV phase-label attribution before qualifying reconciliation. LNV pack and competition references must equal the admitted championship, and supplied phase labels must refer to phases in the observation.

An accepted newer complete catalog has authority over every pool of that same season, provider and organizer, across all packs, competitions, tours and groups in that binding. This includes discovery before ordinary season activation. A complete empty catalog during initial reconstruction preserves the retained population. A newer qualified partial observation advances only its own evidence. A reconciliation commits entry changes, catalog absence and reappearance, submitted phase labels and last complete read time together. A previously omitted pool that returns keeps its UUID and mapping and clears its catalog-absence reason under [FR-042](spec.md#visibility-history-and-recovery). The [F01 passage](../001-source-acquisition/plan.md#passage-execution) uses confirmed reconciliation to exclude remaining targets of that binding.

The operator read passes its authorized source binding to F02. FFVB projects packs and pools. LNV projects distinct phases and their accepted labels. F01 combines the retained entries with the latest discovery result, including a later partial or unavailable read.
