## What can run in the documentary repository

From the repository root, use the pinned formatter, then whitespace checks:

```sh
npx --yes prettier@3.9.6 --check README.md AGENTS.md "docs/**/*.md" "specs/**/*.md" ".github/**/*.{md,yml}" .prettierrc.json
npx --yes prettier@3.9.6 --check "specs/002-sporting-data/contracts/*.yaml"
git diff --check
```

A previously cached copy of the same formatter is acceptable; do not install application dependencies for this dossier. Check local Markdown targets/anchors against the final tree, OpenAPI version/path/schema references and unique operation IDs, sequential task IDs/story labels and requirement coverage. Static schema checks do not prove generated runtime validation. Apply the official Spec Kit checklist and analysis procedures; do not replace them with a repository workflow. Preserve constitution, imported skills/templates and accepted specs byte-for-byte.

## Fixture provenance and failure handling

Reduce observed provider structures into synthetic/anonymized fixtures with the exact tested anomaly and source/method notes. Keep real observations in [provider evidence](provider-evidence.md) distinct from negative controls and generated cases. Do not commit raw provider pages, contact details or referee identities. Recognized notation/column structure is evidence; absent mapping remains unresolved.

A failed qualification blocks its dependent capability: preserve prior state, disable unqualified enrichment/publication or keep transition closed as appropriate. Return a newly discovered product/design question to its owner before finalization. No automatic approximate mapping, new scraper engine, custom supervisor or changed cadence is an acceptable hidden workaround.
