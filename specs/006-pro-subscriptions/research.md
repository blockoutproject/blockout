# Research: Pro entitlements and subscription continuity

## Native SDK and provider UI

**Decision**: Keep paired `react-native-purchases` / `react-native-purchases-ui` 10.13.0 and their bundled iOS 5.95.0, Android 10.27.0 and hybrid-common 19.11.0 dependencies. The existing Pro owner presents a standard React Native `Modal` containing only official `RevenueCatUI.Paywall`. Every existing connected entry uses that same host after a usable current account and successful SDK association, independently of free, paid, gifted or unavailable current rights information. Preserve entry visibility. Dismissal returns to the still-mounted source; logout, accepted erasure or account replacement removes the host. There is no commercial route, Blockout Page/Header, catalogue Query, recovery screen, app restore fallback or active-account dispatch to Customer Center.

**Rationale**: The [versioned public React Native UI API](https://github.com/RevenueCat/react-native-purchases/blob/10.13.0/react-native-purchases-ui/src/index.tsx) exposes `Paywall`, explicit `options.offering`, `onDismiss`, purchase/restore outcomes without a Blockout transaction interceptor. Resolve the `offeringIdentifier` supplied by `REVENUECAT_OFFERING_ID` with `Purchases.getOfferings()` and select only `offerings.all[identifier]`. The retained SDK identifier is `default`; omitting the offering would instead use the SDK’s implicit `current`. Missing/failed offering resolution keeps the source screen with brief feedback and a later explicit opening action. No price extraction or remote catalogue state is needed. The [official presentation guide](https://www.revenuecat.com/docs/tools/paywalls/displaying-paywalls#react-native) documents component ownership and explicit removal. Normal Modal ownership meets teardown without private APIs or a navigation destination. Do not use entitlement-conditioned `presentPaywallIfNeeded`, which skips active beneficiaries. Imperative presentation has no public programmatic dismissal in this pinned API.

The retained paywall configuration and public SDK options own close, restoration, management and available assistance. Blockout retains its independent F10 Profile support entry. For RevenueCat Paywalls V2, `displayCloseButton` is ignored; qualify the existing paywall’s actual close control in the installed clients. That SDK generation is independent of the Blockout V2 release name. The pinned [iOS V2 button implementation](https://github.com/RevenueCat/purchases-ios/blob/5.95.0/RevenueCatUI/Templates/V2/Components/Button/ButtonComponentView.swift) supports restoration and navigation to Customer Center inside the paywall. Its URL actions may use the provider browser/deep-link journey. This establishes supported native actions, not their presence in the selected offering or an authenticated F10 handoff. Unavailable native actions remain accepted limits, without a Blockout replacement. `Paywall` exposes `onUrlOpened`; it does not expose Customer Center's `onCustomActionSelected` callback. A nested Customer Center custom action therefore cannot be assumed to reach JavaScript through the Paywall props. Observe the actual supported private assistance path and close/return behavior, reporting missing native capabilities; keep independent Profile Support available. Changing the shared paywall or Customer Center configuration affects still-supported V1 consumers and requires their bounded compatibility review before authorized publication.

The pinned [iOS purchase button](https://github.com/RevenueCat/purchases-ios/blob/5.95.0/RevenueCatUI/Templates/V2/Components/Packages/PurchaseButton/PurchaseButtonComponentView.swift) disables a generic in-app purchase control for an operation in progress, then invokes purchase for its selected package. It does not itself establish that an active subscriber sees no redundant purchase encouragement or that another store's subscription is managed correctly. Observe free, paid, gifted and unknown-rights presentations with the configured offering and original-store cases. Record generic native purchase proposals and other provider limitations truthfully; accept library behavior without app-owned hiding/disabling, transaction interception or a substitute interface. Blockout adds no automatic payment replay or purchase encouragement. Configuration source, SDK source and a console preview cannot complete those observations.

The native SDK owns transaction concurrency. The [iOS event forwarder](https://github.com/RevenueCat/react-native-purchases/blob/10.13.0/react-native-purchases-ui/ios/PaywallViewWrapper.m) holds a weak view, while Android dispatches view-tagged events. A removed view need not deliver a later completion. Keep no global purchasing/restoring reservation waiting for that callback. Teardown proves neither store cancellation nor transaction transfer. Supplied `CustomerInfo` is accepted only for the original still-current SDK owner and retires obsolete reads; no mandatory second read precedes another action. The surviving SDK owner, its listener and normal foreground/current reads establish subsequent rights independently of the removed view.

Store-pending, confirmed payment and active entitlement remain distinct. Preserve genuine pending/confirmed facts without turning an ordinary SDK error into an app-owned uncertainty/Verify state. The official Paywall owns ordinary purchase/restore failure feedback and later explicit SDK actions. Blockout adds no duplicate native-action toast, mandatory verification, automatic replay or claim that no charge occurred; only failures before opening use originating-screen feedback. An inactive restore result establishes only its returned current rights. SDK/source inspection does not qualify real store outcomes.

**Alternatives considered**: Recreating provider pages, adding a catalogue Query or retaining an independent restore action duplicates native responsibilities. A second entitlement store, recovery controller, global busy lock or private dismissal patch adds no required guarantee. The standard Modal and explicit offering are sufficient application presentation responsibilities. Provider actions and actual purchase proposals remain subject to configuration and native observation, with library limitations accepted and reported.

**Evidence limits**: The installed pins and supported APIs are verified from committed lockfiles and upstream versioned sources. Actual configured actions, subscriber proposals, original-store management, private assistance, native teardown and store/payment activation still require their owning observations. Components do not provide exit offers, which the accepted no-retention scope does not require. [Customer Center configuration](https://www.revenuecat.com/docs/tools/customer-center/customer-center-configuration) and promotional purchase support do not establish Blockout's final journey or its native appearance.

## Identity, cache and uncertain outcomes

**Decision**: Use the usable business UUID, sequential native identity calls, `CustomerInfo` and the existing F05 native principal and business UUID. Only Pro waits for successful current-account association; F05 browser logout or explicit local clearing completes according to the native SDK result, independently of RevenueCat. Treat SDK update events as signals for a current-session native read. Keep operation presentation transient and restoration/management within the configured paywall journey.

**Rationale**: [Identifying customers](https://www.revenuecat.com/docs/customers/identifying-customers) recommends non-guessable identifiers and describes shared project identity, known-account login and anonymous creation on logout. [Customer information](https://www.revenuecat.com/docs/customers/customer-info) owns cache and updates; listeners do not receive server pushes. [Errors](https://www.revenuecat.com/docs/test-and-launch/errors) distinguish pending payment, cancellation and failure. Only supplied entitlement state decides activation.

The versioned [React Native SDK](https://github.com/RevenueCat/react-native-purchases/blob/10.13.0/src/purchases.ts) broadcasts `CustomerInfo` events to current listeners without an application session tag. Its native [iOS identity manager](https://github.com/RevenueCat/purchases-ios/blob/5.95.0/Sources/Identity/IdentityManager.swift) and [Android identity manager](https://github.com/RevenueCat/purchases-android/blob/10.27.0/purchases/src/main/kotlin/com/revenuecat/purchases/identity/IdentityManager.kt) can complete identity/cache mutations after asynchronous work. Rejecting obsolete JavaScript callbacks does not itself order those mutations. Static source evidence supports awaiting each native identity call; it does not qualify actual device behavior.

**Alternatives considered**: Backend entitlement mirrors, webhooks, custom grace clocks, polling, persisted operation records and automatic retries add synchronization or recovery ownership without an accepted need. F05's native principal credentials and fresh private QueryClient replace the generic session epoch. The native Pro owner retains only the sequencing needed by the process-wide SDK. Blocking all account navigation widens a Pro-only boundary. RevenueCat also supports custom-ID-only use without `logOut`, but retaining the previous SDK identity/cache in guest mode would change accepted logout cleanup and would not remove successive-login overlap. Keep native login/logout and a single in-flight identity call in the existing Pro owner. Deterministic tests establish stale-response rejection and serialized calls; focused native observations retain actual global SDK identity/storage and pending-transaction effects. A session change cannot guarantee cancellation or reassignment of a native transaction.

**Evidence limits**: SDK source/documentation do not establish every interruption/account-switch/store outcome. Native transaction tests remain necessary; isolated receipt-path inspection is not proof of the full lifecycle. Native SDK/store controls own concurrent operations after view removal. Current CustomerInfo from the SDK listener, foreground or explicit read establishes rights without waiting for a removed-view callback or a Blockout reservation; restart re-establishes SDK state without a recovery record.

## Existing project and V2 presentation

**Decision**: Reuse the existing `default` offering and the same published `Blockout Pro Paywall`, adapting its content/actions for Blockout V2. Keep the existing RevenueCat project, platform keys, `Blockout Pro` entitlement and monthly products: Apple `monthly`, Google `monthly:monthly` and Test Store `monthly`. There is no separate Blockout V2 offering, duplicated paywall, new commercial tier or product. Select the retained offering explicitly through `REVENUECAT_OFFERING_ID=default`.

**Rationale**: One retained offering/paywall meets the direct-entry journey without duplicated configuration. The ad-free-only V2 benefit replaces sporting/premium-support claims on that shared presentation under the authorized configuration/publication scope. Changes to the shared paywall must account for still-supported V1 clients; there is no independent V1 paywall to maintain. The monthly EUR decrease from 2.99 to 1.99 applies at the V2 cutover for new and existing subscribers through native store mechanisms, not during this implementation or ordinary paywall configuration. [F14 research](../014-v1-v2-transition/research.md#subscription-price-and-purchase-continuity) owns preparation, activation, localized amounts and renewal constraints. Blockout displays the provider price without a hardcoded client amount.

**Alternatives considered**: A second offering/paywall introduces parallel content and qualification without a product need. A second project or product duplicates identity/catalogue settings and adds continuity work. Recreating provider screens or adding a second support-ticket channel has no useful role.

**Evidence limits**: The retained offering/paywall and product identifiers establish configuration selection, not successful native rendering, restoration, management, private assistance or absence of repurchase encouragement. A paywall preview is not store price/renewal evidence. Provider edits and price activation retain their separate authorization, and no price change follows from selecting `default`.

The [explicit-selection implementation](../../apps/mobile/src/features/pro/pro-offering.ts) reads only the configured identifier in `offerings.all`; its [existing test](../../apps/mobile/src/features/pro/__tests__/pro-offering.test.ts) supplies a different `current`. This proves deterministic explicit selection without requiring a second real offering or provider-console mutation. Complete retained configuration review, representative native price/period/trial/renewal formats and observation of the retained configured paywall on each platform establish the remaining integration boundary. A campaign in every store locale adds repeated format checks; it does not replace F14’s real first-payment/new/existing-cohort and renewal evidence. The [quickstart](quickstart.md#configuration-review-and-representative-native-formats) selects formats from actual configured differences, without inventing a locale or trial.

## Test environments

**Decision**: Keep native sandbox access `Anybody`; use controlled test accounts, Test Store for routine development and real platform sandboxes for release qualification.

**Rationale**: [Sandbox access](https://www.revenuecat.com/docs/projects/sandbox-access) explains that restrictions apply to both Test Store and native sandboxes, allowing a transaction to be recorded without granting rights to an excluded customer. [Apple App Review](https://developer.apple.com/help/app-review/before-submitting-for-review/configure-in-app-purchases) tests purchases in sandbox. Taken together, an allowlist would risk excluding an unknown reviewer business UUID. Keeping the native default avoids that process; this is an inference from the two documented behaviors, not an Apple recommendation naming RevenueCat.

**Alternatives considered**: A customer allowlist adds reviewer/test administration; a second project introduces duplication and continuity work. Neither is needed for the accepted scope. [Sandbox documentation](https://www.revenuecat.com/docs/test-and-launch/sandbox) confirms test and production receipts can coexist on a customer; tests therefore use dedicated accounts, with no claim of project-level isolation.

The SDK owner retains successive identity calls and attributed read/outcome tokens because these sequence a process-wide native API. F05 owns the ordinary private account lifetime; no detached editor registry or failed-command ledger is needed. Transient native purchase facts and the existing native/provider qualification gates remain applicable.

## Restoration, gifts and erasure

**Decision**: Keep `Transfer to new App User ID`, with no separate sandbox restore mode; use explicit native restoration, supported owner console intervention and F05 local-first erasure. No V1 gift-migration mechanism is needed for the population the owner confirmed absent.

**Rationale**: The selected restore setting follows [native transfer behavior](https://www.revenuecat.com/docs/projects/restore-behavior). It can transfer a receipt's purchases rather than one selected benefit. [Customer profile operations](https://www.revenuecat.com/docs/dashboard-and-metrics/customer-profile) and [support guidance](https://www.revenuecat.com/docs/dashboard-and-metrics/supporting-your-customers) supply grant/revoke/manual intervention mechanisms. Gifts remain tied to the beneficiary and do not cancel billing. F14 verifies applicable populations before cutover; F05 preserves discoverable original-target references for cleanup.

**Alternatives considered**: An automatic migration/recovery engine, per-purchase transfer guarantees, email-based merging and automatic compensatory gifts exceed the agreed behavior or provider guarantees. Manual assistance with verified evidence covers exceptions without a new service or ledger.

**Evidence limits**: Console settings are not successful restoration evidence. Both stores, cross-store assistance, independent gifts and deletion/recreation require controlled native qualification. No customer inventory proves absence of gifts; that premise comes from the owner and must be rechecked before cutover.

Gift qualification reviews the supported operator procedure, verifies beneficiaries and independent billing, and observes focused SDK reflection on each platform. Existing deterministic gift/state tests cover application errors, unknown state and expiry; T018 retains native cache/refresh observations. Repeating a provider-console failure matrix on both platforms adds no Blockout-owned behavior proof. Actual supported grant/change/revoke outcomes and paid/gift coexistence remain required, while transfer/erasure evidence is reused from T034 rather than repeated for every gift variant. An uncertain real operation still requires a private reread before repetition; no failure drill weakens that rule.

The installed 10.13.0 [purchases API](https://github.com/RevenueCat/react-native-purchases/blob/10.13.0/src/purchases.ts) requires explicit restoration because the store may prompt for authentication. The configured Paywall executes that action and supplies its result through the public callbacks in the [plan](plan.md#entry-offers-and-assistance); Blockout has no independent `restorePurchases` fallback and never repeats restoration from a callback. Preserve operation completion separately from current active rights and let ordinary SDK reads recover. No custom retry, receipt inspection endpoint or automatic compensation is warranted. Controlled callbacks and host checks establish local attribution and teardown only; T034 retains actual receipt, cross-store, independent-gift and erasure qualification.
