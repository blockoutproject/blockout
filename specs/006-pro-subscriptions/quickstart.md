# Quickstart: qualify Pro integration

Follow the [local development setup](../../README.md#local-development) and run the [repository verification commands](../../README.md#verification). Apply [F13’s proportionate qualification](../003-shared-quality/plan.md#proportionate-qualification): deterministic tests cover Blockout-owned state and ordering; native observations qualify the changed SDK, provider UI and store boundaries. Shared checks and browser simulations do not qualify RevenueCat or the stores.

Native accessibility verification follows [F13 FR-030](../003-shared-quality/spec.md#platforms-accessibility-and-bounded-continuity).

## Prerequisites and setup

- Use the [plan](plan.md)'s paired purchases/UI 10.13.0 packages and existing F05 account session in the native mobile application.
- Use dedicated test accounts in the existing RevenueCat project. Select the V2 offering with existing products and simple Customer Center actions. Keep sandbox access `Anybody`; never test destructive cleanup against a real customer.
- Use Test Store for routine development, then native platform keys, products and Apple/Google sandbox accounts for store qualification. Never ship a Test Store key in a production candidate. Provider changes require their own authorization.
- Reuse compatible iOS simulator/Android emulator development clients for functional SDK/UI integration under F13 FR-029. Use physical devices and the exact production-identity EAS/store candidates for the store, release or provider boundaries that require them. Reuse applicable minimum/latest OS evidence rather than replay every case on every runtime; Expo Go is insufficient.

Run Pro feature tests through the mobile verification target documented in the README. Reuse the existing `pro-offering`, `pro-state`, `pro-session`, `pro-refresh`, `pro-verification`, `pro-purchase`, `pro-restore`, `pro-gifts`, `pro-presentation` and `pro-appearance` suites in `apps/mobile/src/features/pro/__tests__/` for explicit selection, entitlement/eligibility variants, obsolete callbacks, sequential identity effects and payment safeguards. Native checks exercise ordinary transitions plus focused SDK storage/identity, cache/refresh and pending-store behavior; they do not require precisely delaying every callback already covered deterministically. Reuse compatible F05/F11/F13 evidence at its demonstrated boundary. Missing native or provider outcomes remain unchecked in [tasks](tasks.md).

## Evidence and release boundary

Record actual platform/build, tested scenario and outcome in the normal delivery evidence. Keep receipts, customer IDs and diagnostics private. Test Store, mocked callbacks or one successful purchase do not establish native lifecycle, complete continuity or store approval.

Unavailable evidence remains a release qualification, not a passing test. Resolve a failed required native behavior before release; do not add a custom recovery system as an unreviewed workaround.
