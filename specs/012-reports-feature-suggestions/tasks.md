They authorize no provider configuration, private submission or production activation. Real private attachment access and exceptional image erasure must be qualified before real support content is accepted.

Controlled boundaries qualify application behavior, not GitHub permissions, image erasure or native media behavior.

**Organization**: Setup/foundation, P1 US1/US3/US4, P2 US2, then cross-cutting qualification. All stories remain required. Backend file validation and complete delivery belong before the first send; later US2 adds the actual native selection journey.

## Format: `[ID] [P?] [Story] Description`

- `[P]` identifies separate files with no unfinished dependency between those tasks, after named prerequisites.
- `[USn]` maps to the specification story; setup/foundation/polish carry no story label.
- Every checkbox remains unchecked until its implementation or qualification actually passes.

## Path Conventions

- Backend: `apps/backend/src/main/java/com/blockout/backend/support/`, mirrored tests under `src/test/java/`. Keep generated transport types at the API boundary and immutable application values/ports within this feature.
- Mobile: `apps/mobile/src/features/support/` with co-located `__tests__/` and a thin Expo Router route. Reuse F13 controls, transport and Query, F05 session ownership and F12 admission.
- Canonical source: `contracts/http/mobile/support/{paths,schemas}.yaml` and the existing mobile root. Generated Java interfaces/DTOs and Orval functions/types/Zod remain ignored projections.
- GitHub is the sole durable support store. No SQL table, Liquibase migration, collector feature, support service, durable upload volume or independent support backup is introduced.
