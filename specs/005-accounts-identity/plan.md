## Summary

Keep public access independent of authentication. Resolve each validated Auth0 principal to one PostgreSQL business account, with a neutral username, optional square photo and current server-side permissions. Native Auth0 identity, a subject-keyed React lifetime and its private QueryClient isolate private state; RevenueCat's SDK remains the entitlement authority.

Delete the original account and its local personal data synchronously, then attempt bounded provider cleanup. Private failure diagnostics support manual repair; no pending account, recovery worker, polling or replay is introduced. The app returns directly to guest home after the request.

## Identity and account establishment

Validate JWT signature, issuer, environment audience, expiry, allowed client and required scopes with Spring Security. Use the validated `(issuer, sub)` as the unique principal mapping; never trust a body-supplied subject or resolve by email. Attempt creation once with one neutral username candidate under the same format/uniqueness rules as manual edits; email is not unique. After a principal uniqueness refusal rolls back, read the concurrently established winner without another insert. A generated-name collision propagates as ordinary unavailability for a later explicit request, without replacement candidates or a retry loop.

After an explicit successful login, `POST /accounts` establishes the account or synchronizes its necessary provider email and age evidence. Read Auth0 by exact principal ID outside the SQL transaction, then recheck the original account state when committing. A synchronization started for an existing UUID cannot become creation or update of a replacement UUID. An ordinary startup/profile read uses `GET /accounts/me` and never contacts Auth0 or creates an account. Its response includes the [F12 permission projection](../013-administration-app-configuration/data-model.md#permission-projection). This narrow read remains available during maintenance for operator identification, without enabling profile navigation, photo access or account establishment. A 404 never triggers automatic establishment. Missing necessary age evidence can be retrieved through an explicit targeted retry using bootstrap, without requiring another login while authentication is valid.

The explicit login event awaits the native SDK command and submits establishment with its returned original principal; no effect converts restoration into a write. The initiating UI may remount when the subject changes, so it dispatches the authorized command before checking mounted presentation. Success or failure then retains the existing Profile replacement for ordinary login. An explicit SDK recovery captures its requested internal destination with Expo Router's global `usePathname`, `useGlobalSearchParams` and `useSegments`, excluding dynamic path parameters from its query. It validates the local `returnTo` parameter and uses `replace` to restore that exact destination after login/establishment, including when its deferred child navigator remounts; no navigation state is copied. Its current private query resolves a committed/lost-response creation normally; the common initial member recovery offers an explicit account-establishment action after a current 404, without another hosted login. Ordinary read Retry never establishes the account. Query mutation options own command completion/invalidation on their captured client; no old POST error is copied into the new private cache. The new lifetime obtains its current-account read with ordinary retry/error behavior if it overlaps first establishment. Ordinary pending UI prevents normal repeated lifecycle actions; no synchronous generation reservation or guest-supersedes-login protocol is retained.

First creation without a usable provider email fails without a partial account. Existing known email/age survive a provider outage; username and photo are never provider-synchronized. Account age uses the actual Auth0 principal's `created_at`, including existing linked methods. A principal surviving failed cleanup retains its age after new business registration; successful identity deletion normally yields a new principal date. Unknown age remains unknown and only age-dependent actions are suspended.

Open Auth0 Universal Login through the SDK’s platform authentication browser; Blockout supplies no credential form or social-provider UI. Use separate native app registrations, clients and API audiences in the existing tenant. Enable the dedicated database connection only for preproduction, with native signup; enable Google/Apple only for production. No credentials or Management API secret in the mobile. Before any preproduction destructive provider operation, establish that the principal belongs exclusively to the dedicated connection, without linked foreign identities. Shared tenant administrative powers remain a real isolation limit. The actual environment configuration and provider qualification remain governed by the owning tasks and operational authorization.

Server Auth0 OAuth transport uses Spring's native JDK request factory with a total response deadline and a managed JDK HTTP/1.1 client with redirects disabled. The deadline bounds progressive response bodies as well as inactivity, so cleanup cannot be retained indefinitely by continuing bytes. No application timeout wrapper or pool/lease tuning is added. The Management SDK retains its actual native client. Destination confidentiality and credential-boundary qualification remain independent from transport quality of service.

This is the [documented Bearer configuration](https://github.com/auth0/react-native-auth0/blob/master/FAQ.md#13-what-is-dpop-and-should-i-enable-it), not a custom token conversion. Previously issued DPoP credentials remain DPoP until explicit sign-out/sign-in; do not relabel them or add an automatic credential purge. Qualify subsequent restoration and API access with the actual provider before native acceptance.

Attempt old destination disassociation once before discarding its credentials, with bounded waiting; failure never prevents local sign-out. No persisted cleanup secret or retry is added. [F07](../011-notifications-delivery/plan.md#expo-handoff-and-association-lifecycle) guards the old association so a delayed removal cannot remove B or a later sign-in of A. Failure or an old registration already in transit may leave old-account system pushes deliverable until normal reassociation, provider invalidation or manual intervention; opening them cannot expose A's private state under guest/B. Erasure removes all associated destinations server-side. The same F07 boundary resets the app-controlled badge on local sign-out/account change or confirmed erasure. Presented system notifications follow platform behavior and may remain; no dismissal or cleanup retry is added.

Configure RevenueCat for the usable business UUID and use SDK-provided entitlement state only. Reject old-session callbacks and do not reconfigure an erased account on startup/re-entry. Guests have no previous-account rights; an absent SDK state is not a free-account decision. Existing SDK instances on another device are not remotely revoked by customer deletion: qualify that lifecycle under F09/F14, without inventing an independent session service.

All protected business use cases verify current account usability and their own current ownership/permission before committing. They coordinate their short mutation transaction with account erasure using the account row lock; manual F12 grant changes use the same lock before reading/changing grants. Where domain root locks are also needed, acquire those in their owner order before account locks (sorted UUIDs for several accounts), and acquire no domain root lock afterward. Account erasure changes private associations/attribution without acquiring sporting root locks; erasure cannot race a new follow, destination or attribution into the deleted lifecycle. F06’s [association lifecycle](../009-following-personal-feed/data-model.md#persisted-associations) participates in the same local erasure transaction and account lock, including hidden follows; it adds no provider cleanup or pending-erasure state. Collector tokens are not account credentials. F12 determines baseline capabilities and distinct administration grants; this plan does not create its grant catalogue or API.

## Erasure and manual resolution

1. Navigate from the profile to the ordinary erasure screen with concise consequences, the confirmation checkbox and plain store-billing guidance; no subscription-management action. Cancel/back returns without deletion. Validate the owner and explicit confirmation; capture the original business UUID and known Auth0/RevenueCat targets, including justified historical references. Do not block local deletion on a live provider lookup. Missing external target/scope evidence is logged for manual handling; no destructive provider call proceeds without the applicable environment and identity-scope checks.
2. In one short PostgreSQL transaction, lock and remove the original account, photo and personal associations; detach retained contribution/decision attribution and remove reporter associations and free-text reasons under F08, preserving counted report facts and moderation decisions. A definite transaction failure starts no external cleanup and preserves the usable account/session. Other personal writers use the same account lock.
3. After commit, attempt each known original Auth0 and RevenueCat cleanup once with ordinary bounded calls. Continue to the other targets on failure; never roll back local deletion. Trust documented acknowledgments: Auth0 204 confirms user removal; RevenueCat v2 200 queues asynchronous customer deletion. That successful acknowledgment alone needs neither polling nor manual intervention. Global Google/Apple accounts and store billing remain separate.
4. Emit a private failure/uncertainty diagnostic for missing target evidence or failed external cleanup. Use the local structured diagnostic and current owner evidence. The operator uses existing database/provider/support tools to inspect and repair original targets, verifying current use before destructive action. Never guess a replacement or match by email. No pending record, outbox, worker, retry ledger or new administration screen.
5. Return HTTP 204 after local deletion and bounded attempts, including logged provider failure. On acknowledgement, use standard local sign-out/private-state clearing and navigate to guest home without a receipt, progress view, success toast or post-deletion cleanup-recovery state. A failed or lost response uses ordinary mutation failure feedback, preserves confirmation input and permits an explicit manual new send to the original UUID without a verification read. Repeated DELETE of an absent original UUID returns 404 without new provider calls.

Private diagnostics may retain only the original account ID, relevant provider references and minimal original-target verification evidence, with operation, environment, provider, time and a safe outcome/reason. Exclude email, profile content, images, tokens, secrets and raw provider payloads. Keep these references out of metric labels and Discord messages. Existing private handling retains only still-needed references while their manual-cleanup purpose or another obligation requires them; no log-storage duration is selected. [F11](../004-advertising-privacy-legal/spec.md) governs purpose and recipients.

A process interruption after commit but before logging can leave external cleanup unreported. No durable mechanism closes that accepted gap, and an alert's native closure does not establish repair. Manual handling has no guaranteed response time.

Explicit sign-in may create a new business UUID immediately, without a cleanup gate or polling. Its profile, follows, grants, gifts and attribution start empty; age uses the actual Auth0 principal. No special coordination handles simultaneous return and an in-flight provider delete: ordinary errors and manual assistance apply. Standard Auth0 token validity is retained; an earlier still-valid same-subject token can authorize the new account under its current rights. No custom session registry, lifecycle claim or re-registration delay is added. An old UUID-targeted request still cannot act on the replacement UUID.

## Continuity, operations and limits

F14 preserves existing Auth0 principals, linking and age while establishing new V2 business UUIDs. Recover paid entitlements through explicit native restoration and verified manual assistance for exceptions; preserve valid gifts separately. Keep necessary historical RevenueCat references discoverable for continuity and erasure, including old records left after purchase transfer. This is not a full profile export or mandatory mapping registry for the whole user population.

F10/F11 own external privacy requests and any data within retained content. The existing public privacy page provides the external deletion request direction and contact, without a new portal; its store registration is qualified by F14. Reusing retained data requires manual reconciliation of current erasures/rights/expiry before reopening affected access or sends.

The implemented schema establishes only the V2 UUID RevenueCat customer reference. It has no historical-reference registry or source from which additional targets can safely be inferred. `OriginalAccountTargets` carries only captured original references; cleanup deduplicates established references and never expands them through aliases, email or the replacement mapping. F14's historical coverage remains a private cutover prerequisite. This construction adds no population export or registry.

Provider cleanup is disabled by default through typed `blockout.accounts.cleanup` settings. Explicit preproduction activation additionally requires the exact dedicated Auth0 connection (every linked identity must belong exclusively to it) and an exact privately verified RevenueCat test-customer allowlist, because the shared project has no sandbox identity namespace. Production accepts the retained Google/Apple identity families under the configured issuer/project. Auth0 exact-ID scope inspection runs after local commit, without email/profile fields, and failure never blocks local deletion. The installed Management SDK owns DELETE and its documented Apple revocation; the native Spring/JDK RevenueCat v2 client has positive total deadlines and redirects off. Under the standard JDK 25 HTTP/1.1 policy, transmitted POST/DELETE requests are not replayed; native connection establishment before dispatch remains within the total deadline. The existing Auth0 OAuth/SDK transport is shared with establishment rather than duplicated. No provider configuration is activated by repository defaults.

Private provider credentials stay server-side. The narrowly scoped private cleanup-reference exception follows F05/F11; all other diagnostics retain F13’s personal-data exclusions. Use existing F13 operations; no erasure dashboard or automated repair service. F13's evolving Liquibase baseline and later freeze policy apply without additional schema history during disposable development.
