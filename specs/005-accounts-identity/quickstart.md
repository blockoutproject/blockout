2. Implement the owning F05 paths/tasks and actual participating F06/F07/F08/F09/F11/F12 adapters before claiming end-to-end erasure. Use controlled adapters only for scoped module tests.
3. Apply the accounts Liquibase schema to isolated real PostgreSQL. Keep provider API credentials, tokens and test identities in private configuration, not fixtures, logs, GitHub or screenshots. Images use a separate private test prefix/bucket under the authorized F13 storage setup.
4. Qualify actual Auth0 callback/logout URLs, API audience, Google/Apple connections, refresh configuration and retained settings. Do not substitute historical observations/defaults. Remove the obsolete V1 role-assignment dependency only through authorized F14 work.
5. Configure an isolated RevenueCat/store qualification context under F09, with explicitly approved customer targets and restore behavior. Do not silently change provider settings or use production billing.
6. Run F13 contract lint/bundle/generation twice from clean ignored outputs; compare output and compile real Java/TypeScript consumers. Run F13 Python synthetic generation proof without creating a fictional F05 Python consumer.
7. Execute backend tests through the F13-created Maven wrapper/owning verify target, mobile tests through its installed Jest Expo/RNTL targets, then actual iOS/Android provider journeys. Use the resulting committed manifests as command authority; none exists in this dossier and no placeholder runtime command is claimed runnable today.

## API exercise recipe

After implementation, use the generated mobile client or an authenticated API client against the isolated environment and [OpenAPI](contracts/account.openapi.yaml). Keep bearer material in private client configuration. These are concrete request bodies, not executed calls:

```json
{
  "username": "player-example",
  "expectedRevision": 0,
  "expectedAccountId": "d7ef3a20-88c4-4c69-9f5c-935f611cf537"
}
```

```json
{
  "confirmed": true,
  "expectedAccountId": "d7ef3a20-88c4-4c69-9f5c-935f611cf537"
}
```

Authenticate explicitly, POST `/api/v1/me/bootstrap`, record the current business UUID and revision privately (the UUID above is synthetic), GET `/api/v1/me`, PATCH `/api/v1/me/profile` with that revision, then reread. PUT `/api/v1/me/photo` uses multipart `file`, `expectedAccountId` and `expectedRevision`; DELETE the same resource uses the original `expectedAccountId` and current `expectedRevision` query parameters. Preserve the original UUID on any uncertain repetition; do not retarget to a newly discovered account. GET image requires the same owner authorization and returns `Cache-Control: no-store`.

For erasure, use only a disposable authorized account. POST `/api/v1/me/deletion`; expect 202 acceptance before external completion. Follow [the erasure runbook](contracts/erasure-and-operations.md) for injected failure/uncertainty. Never interpret GET absence or provider 200/202 as universal physical-erasure proof. Ordinary GET must not recreate an account.

A private read-only pending-state inspection after schema implementation is:

```sql
SELECT id, deletion_requested_at
FROM accounts.business_account
WHERE status = 'DELETION_REQUESTED'
ORDER BY deletion_requested_at, id;
```

Do not paste its output into public artifacts. This is an operator inspection, not a periodic supervisor or a restart/retry worker. Destructive manual continuation requires the documented original-target checks and owning schema procedures, not an unguarded universal DELETE statement.
