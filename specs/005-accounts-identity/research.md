## Principal and business identity

**Decision:** uniquely map validated Auth0 `(issuer, sub)` to a new business UUID. Preserve existing linked identities; never link or merge by email. Bootstrap is explicit, ordinary reads are local, and provider synchronization is limited to required email at explicit login or establishment.

**Rationale:** a stable business UUID distinguishes a new account after erasure from an old provider reference and is the V2 RevenueCat App User ID. Exact-ID Auth0 reads request only `user_id,email`, without a broad user search or provider creation-date retrieval. A PostgreSQL unique constraint settles concurrent creation: one insert is attempted and a principal conflict reads the winner after rollback. A generated-name collision is an ordinary failure for a later explicit request, without an automatic candidate loop.

**Alternatives:** using email would confuse legitimate distinct principals; reusing a provider ID as the business lifecycle would make old-target cleanup unsafe. A new linking process, periodic profile synchronization and business session registry have no accepted need.

**Evidence:** [Auth0 exact user lookup](https://auth0.com/docs/manage-users/user-search/get-users-by-id-or-email), [profile structure](https://auth0.com/docs/manage-users/user-accounts/user-profile-structure), [existing account linking](https://auth0.com/docs/manage-users/user-accounts/user-account-linking). The retained tenant and historical samples establish neither complete population coverage nor every token invalidation path.

## Backend Management API integration

**Decision:** use the official [`auth0-java` 5.4.0](https://github.com/auth0/auth0-java/tree/5.4.0) Management SDK for exact-ID reads and deletes. Spring Security OAuth2 Client retains the standard client-credentials acquisition, in-memory expiry cache and renewal through the environment's native `auth0` registration. SDK models remain inside the account infrastructure adapter; account establishment receives only necessary email. Erasure uses the original subject captured from the deleted business account and verifies its issuer before calling Auth0.

**Rationale:** the official SDK owns endpoint construction and provider decoding instead of a handwritten HTTP/JSON projection. Its native `ClientOptions` header supplier accepts Spring's bearer without a second token cache. The 5.4.0 built-in `OAuthTokenSupplier` uses its own static HTTP client with a fixed 30-second call deadline; that path does not inherit the selected token transport's deadlines/redirect policy. The supported header-supplier integration preserves the already selected bounded Spring token client. Management calls use the SDK's supported native OkHttp transport with explicit deadlines, disabled connection retries and redirects; SDK retries and payload logging remain disabled. Maven needs the explicit `okhttp-jvm` compile artifact corresponding to the SDK's 5.2.1 transport dependency; this does not upgrade the workspace or replace the mobile SDK.

**Evidence:** [official SDK usage and configuration](https://github.com/auth0/auth0-java/blob/5.4.0/EXAMPLES.md), [`ClientOptions`](https://github.com/auth0/auth0-java/blob/5.4.0/src/main/java/com/auth0/client/mgmt/core/ClientOptions.java), [`OAuthTokenSupplier`](https://github.com/auth0/auth0-java/blob/5.4.0/src/main/java/com/auth0/client/mgmt/core/OAuthTokenSupplier.java), and [Spring's authorized-client API](https://docs.spring.io/spring-security/reference/servlet/oauth2/client/authorized-clients.html). Qualify actual SDK decoding, exact ID, token audience, native expiry reuse, token/resource deadlines, refusal and safe diagnostics with controlled HTTP. Actual tenant configuration/provider behavior needs its own qualification.

## Native authentication and environment boundary

**Decision:** one Auth0 tenant, distinct application/audience configuration. Production exposes Google and Apple. Preproduction exposes its dedicated email/password connection with native signup. Local sign-in currently shares the preproduction configuration, so local deletion can remove a shared test identity. Use the native SDK's secure credential management and ordinary renewal. Normal browser logout failure leaves its native user authenticated; explicit local clearing is a separate action.

**Rationale:** native signup removes manual test provisioning without a second tenant or an application password form. Signup is connection-wide; the dedicated connection is disabled for production, so no custom Action is needed for this separation. Connection settings are not per-user directory isolation. The installed SDK's combined logout can fail before local clearing, so the application presents that failure honestly and permits retry. Acknowledged erasure uses the native credential manager after withdrawing the erased account. The existing erasure action retries only that local effect on native failure because the server has already completed its part.

**Alternatives:** another tenant adds account/configuration cost without an accepted requirement; public signup on a shared production-enabled connection would weaken the intended boundary. Federated global logout, ephemeral-session policy changes, bespoke refresh timers and custom JWT claims are not selected.

**Evidence:** [Auth0 connection signup scope](https://support.auth0.com/center/s/article/disable-sign-ups-for-a-specific-application); [`react-native-auth0` 5.11.1 provider implementation](https://github.com/auth0/react-native-auth0/blob/v5.11.1/src/hooks/Auth0Provider.tsx). F13 selects `react-native-auth0` 5.11.3 for [Expo SDK 58 scene compatibility](https://github.com/auth0/react-native-auth0/releases/tag/v5.11.3); the SDK config plugin leaves URL forwarding to Expo rather than inserting an obsolete AppDelegate override. Native callbacks, cancellation, logout failure, retained token validity and the actual client/connection settings still require device/provider qualification.

## Atomic profile and original image

**Decision:** one atomic multipart PATCH for the existing single Save action. Omitted fields retain current state; last accepted supplied value wins. Adopt only response-confirmed profile fields into the still-usable matching original client/UUID, preserving current permissions and refusals; subsequent invalidation failure cannot undo that confirmation. A failed or lost response keeps the mounted draft/photo directly editable, uses ordinary mutation failure feedback and allows a later explicit manual submission. Existing invalidation is not a verification prerequisite; no separate uncertainty card, return-to-edit mode or read-before-repeat gate is introduced. Use [F13’s shared native crop mode](../003-shared-quality/plan.md#single-image-selection), one awaited owned copy of the delivered admissible PNG/JPEG and standard format/header recognition before byte-identical S3 storage and publication of the PostgreSQL photo reference.

The native picker owns crop confirmation and export, which may transcode the library asset. Profile and sporting owners reuse `shared/images/copy-selected-image.ts`: Expo FileSystem's `File` checks the delivered PNG/JPEG and 5 MiB byte bound, then an awaited copy supplies the independently owned upload without modifying its pixels or metadata. This is byte preservation after native delivery, not a promise that the native export equals the untouched library original. The server uses ImageIO reader format/width/height recognition and retains those submitted bytes without storing dimensions, decoding a raster or re-encoding. FileSystem is the existing Expo runtime dependency declared directly by the mobile consumer. Servlet multipart buffering retains accepted parts in memory within the existing per-file/request bounds; ImageIO uses memory-backed streams rather than disk staging.

**Rationale:** saving username and photo independently would introduce partial success without a corresponding user need. Standard picker editing lets the holder choose the framing. FileSystem copy and Expo Image `contain` preserve the complete delivered image in the existing square field, including a rectangular result. Standard ImageIO header recognition establishes the accepted PNG/JPEG format within 5 MiB. A full raster served only the removed preparation pipeline and is no longer allocated; complete pixel decodability is not guaranteed.

**Alternatives:** a custom editor or image transformation would add ownership beyond the native crop interaction. A persistent staging store, image job, quality-search loop or synchronization service adds no value to the atomic save. No optimistic revision UX, response-merging engine, second account cache or write-receipt protocol is needed for owner edits with accepted per-field last-write behavior. An external URL alone supplies neither verified bytes nor controlled erasure. The [F13 storage lifecycle](../003-shared-quality/plan.md#application-image-storage) preserves the last accepted association through replacement and keeps the existing private read route.

**Evidence:** [Expo SDK 58 ImagePicker](https://docs.expo.dev/versions/v58.0.0/sdk/imagepicker/) supplies single-image selection and native crop confirmation, [FileSystem](https://docs.expo.dev/versions/v58.0.0/sdk/filesystem/) supplies the awaited owned copy and [Expo Image](https://docs.expo.dev/versions/v58.0.0/sdk/image/) supplies proportional `contain` without bitmap measurement. [Java 25 ImageIO](https://docs.oracle.com/en/java/javase/25/docs/api/java.desktop/javax/imageio/ImageIO.html) provides standard image-reader and format/header recognition. Native selection and hosted Auth0 UI remain outside prototype/Figma reproduction; design sources establish no native permission, file-lifetime or provider outcome.

**Decision:** use an Auth0-subject-keyed React private lifetime with its own QueryClient. The process public access owner remains outside it. **Evidence limits:** installed Auth0 and Query source establish API behavior, not native browser, token storage, purchase, UMP or push-delivery qualification. Deterministic tests at the real F05/session/Query owners cover original-principal dispatch, detached-client isolation and late callbacks; consumers add only their distinct effect. Ordinary native sign-in, sign-out, account/route transitions and recovery establish functional integration without repeating precisely timed races for every command. Actual SDK storage, serialized global identity changes and provider reflection retain focused native/provider evidence, with physical hardware only where that boundary requires it. ## Synchronous business deletion and manual external cleanup

**Decision:** remove business data in one transaction, attempt each known external target, including the original S3 photo object, once after commit and use private failure logs for manual repair. No durable pending state, automatic recovery or recreation gate. The [plan](plan.md#erasure-and-manual-resolution) owns sequencing and target safeguards.

**Rationale:** the local transaction withdraws access to the original account and photo before cleanup. Capturing the photo key under the original lock allows the operation to delete the exact object even after the account is gone. The owner accepts interruption between commit and log emission and ordinary errors when re-login overlaps provider deletion. A new business UUID prevents an old local deletion from targeting its replacement. The narrowly scoped original-target logging exception makes manual repair possible without a database workflow record.

**Alternatives:** a durable tombstone/outbox would improve crash recovery and block recreation, but adds state and operational handling beyond the accepted need. No provider polling, queue, retry scheduler, custom session registry or permanent profile archive is selected. A provider acknowledgment is trusted without demanding inaccessible proof of physical erasure. Rejected mechanisms are not deferred roadmap items.

**Documented capabilities:** [Spring transactions](https://docs.spring.io/spring-framework/reference/data-access/transaction/programmatic.html) delimit ordinary local transactions. [Auth0 DELETE](https://auth0.com/docs/api/management/v2/users/delete-users-by-id) returns 204; [RevenueCat v2 DELETE](https://www.revenuecat.com/docs/api-v2/customer#delete-a-customer) returns 200 for asynchronously queued removal. Successful asynchronous acknowledgment does not by itself create manual work. [Auth0 Apple revocation](https://support.auth0.com/center/s/article/deleted-apple-users-receive-email-service-id-has-revoked-your-sign-in-with-apple-account) describes supported behavior, not this tenant's qualification. [Customer deletion](https://www.revenuecat.com/docs/dashboard-and-metrics/customer-profile#delete-customer) does not cancel store subscriptions.

**Total response bound:** the installed Spring Web 7.0.9 [JDK request implementation](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-web/src/main/java/org/springframework/http/client/JdkClientHttpRequest.java) owns cancellation through headers and body consumption. RevenueCat and the shared Spring OAuth token client use that native JDK factory to bound progressive bodies as well as inactivity. Managed HTTP/1.1 clients disable redirects; [OpenJDK 25's native replay policy](https://github.com/openjdk/jdk/blob/jdk-25%2B36/src/java.net.http/share/classes/jdk/internal/net/http/MultiExchange.java) does not replay transmitted POST/DELETE under standard JVM settings. Connection establishment may be retried before dispatch inside the same total bound; no global JVM retry property is changed. Controlled peers qualify progressive bodies and dropped responses for both methods. The Management SDK retains its native OkHttp call deadline. No timeout executor, custom request factory, copied OAuth parser or additional dependency is needed.

**Operational evidence:** [OWASP logging guidance](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) supports purpose-limited event context and protected access, with credential/payload exclusions. F05/F11 authorize only necessary original-target references in private diagnostics and the existing private manual process while their cleanup purpose or another obligation requires them. No log-storage duration or external alert provider is selected. Local diagnostic checks establish neither guaranteed delivery nor actual provider cleanup.

**Limits:** Auth0 supplies no conditional incarnation delete. Manual intervention verifies original targets/current use but does not invent atomic provider guarantees. Customer removal does not remotely revoke all existing SDK instances. The [quickstart](quickstart.md#erasure-and-return) defines local SQL, controlled HTTP and live provider qualification for the built revision.

## HTTP and proof boundaries

**Decision:** extend F13's canonical mobile root; use explicit account bootstrap, owner reads, atomic profile PATCH and original-UUID DELETE returning 204 without a body. Reuse shared Problem Details and no-store headers. DTOs remain generated boundary objects.

**Rationale:** [HTTP semantics](https://www.rfc-editor.org/rfc/rfc9110.html) and [atomic PATCH semantics](https://www.rfc-editor.org/rfc/rfc5789.html) fit these observable effects. No separate photo-write routes, login/logout API, job resource or bulk endpoint has a real consumer need. A 204 confirms local resource removal after bounded external attempts; a 404 confirms original resource absence, not physical provider purge. No monitor resource is needed.

**Qualification:** multipart JSON/file binding, optional-field preservation, unknown-request rejection, additional-response tolerance and PNG/JPEG response handling must pass the integrated Java/TypeScript chain before adoption.
