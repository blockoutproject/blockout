# Research: search and discovery

**Scope**: Decisions for [F04](spec.md). Official documentation and scoped static code inspection inform this dossier. They do not establish integrated runtime behavior.

## Search engine and client

**Decision**: OpenSearch 3.9.0 with official `opensearch-java` 3.10.0 and the recommended Apache HttpClient 5 transport, called from the existing backend. Retain the F13 Java/Spring baseline; no Spring Data OpenSearch integration.

**Rationale**: Native text analysis, word prefixes, typo tolerance, exact filters, relevance, bulk indexing, deep traversal and atomic aliases cover the accepted behavior without building a search engine in application SQL/code. [OpenSearch releases](https://opensearch.org/releases/) and the [Java client release](https://github.com/opensearch-project/opensearch-java/releases/tag/v3.10.0) establish the selected versions; [official Java client guidance](https://docs.opensearch.org/latest/clients/java/) recommends Apache HttpClient 5. Its [compatibility matrix](https://github.com/opensearch-project/opensearch-java/blob/v3.10.0/COMPATIBILITY.md) lists tested JDKs through 21, not Java 25. This is a qualification gap, not evidence of incompatibility or permission to change Java.

**Alternatives considered**: PostgreSQL-only full-text/trigram search avoids another service but requires more application composition for the accepted multi-field prefix/fuzzy relevance semantics. Elasticsearch retains familiar V1 concepts but is not a continuity obligation. A second framework integration adds a dependency without a needed abstraction. The engine adds local security and rebuild work. Hosted topology and provisioning are outside the current scope.

**Validation**: Check client TLS, serialization and native query/bulk/alias behavior under the selected Java/client/engine combination through [the quickstart](quickstart.md#contracts-and-access). Analyzer behavior, business traversal, deployment and capacity cannot be inferred from dependency documentation.

## Native matching rather than token orchestration

**Decision**: Native aggregate fields via [`copy_to`](https://docs.opensearch.org/latest/mappings/mapping-parameters/copy-to/), standard tokenization/lowercase/accent folding, a prefix aggregate and a whole-word aggregate. Require a whole-query AND match through either branch; ordinary optional boosts favor direct names. Native [`match`](https://docs.opensearch.org/latest/query-dsl/full-text/match/) provides AND and `fuzziness: AUTO`; [`edge_ngram`](https://docs.opensearch.org/latest/analyzers/token-filters/edge-ngram/) supplies indexed prefixes with original-word preservation.

**Rationale**: All query terms can match across fields of one resource. Separate complete branches keep prefix and typo behavior understandable without an application token parser. An explicit [search analyzer](https://docs.opensearch.org/latest/mappings/mapping-parameters/search-analyzer/) keeps whole query terms intact: OpenSearch otherwise reuses the index analyzer, whose prefix expansion could admit unrelated words sharing only a short beginning. `preserve_original` alone does not cover intermediate prefixes beyond `max_gram`; the [plan](plan.md#matching-and-current-data) therefore bounds native analysis for the entire accepted input, rather than truncating queries or adding a token-count restriction. Lucene’s [ASCII folding implementation](https://raw.githubusercontent.com/apache/lucene/main/lucene/analysis/common/src/java/org/apache/lucene/analysis/miscellaneous/ASCIIFoldingFilter.java) allows expansion up to four characters, including ligatures; qualification covers the selected engine’s actual analyzer, not only this source inspection.

**Alternatives considered**: One fuzzy clause per analyzed token, reissuing relaxed queries and broad synonym expansion create a query-composition subsystem. Fuzzy matching is not applied in the same way to synonym-expanded terms, so a synonym chain is not assumed to solve every combination. The accepted simpler behavior does not guarantee arbitrary mixed fragments, typos and abbreviations. No stemming, stop-word removal, scripts or custom ranking service.

**Division terms and aliases**: Use known division-associated abbreviations and F02 identity-scoped aliases as indexed inputs. They are distinct meanings: `N2` describes a division, while a verified team alias identifies one contextual team. Format/gender use existing French labels and exact enum filters. Controlled technical maintenance suffices; no new editing journey or global similarity dictionary.

## Complete traversal without retained snapshots

**Decision**: Native [`search_after`](https://docs.opensearch.org/latest/search-plugins/searching-data/paginate/) on score descending and stable UUID ascending. One primary shard per resource index, opaque positional continuation and current-data checks. No PIT.

**Rationale**: Deep traversal must not stop at the ordinary 10,000-result offset window. Stable ties and unchanged indexed data satisfy complete browsing. F04 already accepts order changes after data changes and ordinary refresh; it does not require a frozen result set. The isolated local index uses one primary shard and no replicas; this does not select a hosted topology or availability commitment.

**Alternatives considered**: Offset paging has a deep result window and changing boundaries. PIT plus `search_after` gives stronger consistency but introduces creation, identifiers, expiry and release/error handling for a snapshot guarantee not required here. Scroll is not the user pagination mechanism. No retained result table or cursor signing service is needed: the cursor is a validated position, never an authorization credential. Identity deduplication and a fresh traversal handle changed data; no permanent-omission guarantee is claimed during concurrent mutation.

**Current-data filtering**: Bounded candidate iteration is required because an index may lag a restriction. Continue internally rather than ask users to traverse empty pages; return ordinary failure if no eligible results or actual exhaustion can be established within the bound. Hydrate each nonempty native batch of at most 200 candidates once through the existing current-data owner, then consume its ordered eligible results. A mostly eligible batch may load unused candidates, while one snapshot avoids repeated short hydration transactions. Slicing into smaller groups can save that tail but adds another traversal loop and snapshots; reconsider it only if measured bounded cost warrants it. Sparse successful empty pages would transfer scanning and end proof to HTTP/mobile and are not selected. A simple indexed/current city comparison rejects stale candidates, accepting temporary omission instead of token attribution or a separate contact synchronization workflow.

## Automatic refresh with one writer

**Decision**: Relevant after-commit submissions and a full startup/fixed-delay rebuild run on one dedicated one-thread Spring scheduler. Start the next full run one hour after completion, configurable. Re-read current state for every targeted task. Create new generations, use the native aggregate bulk failure flag, refresh and atomically switch the three aliases only after complete success.

The native [Manage Aliases API](https://docs.opensearch.org/latest/api-reference/alias/aliases-api/) resolves the owned index-name pattern in each remove action; `must_exist: false` permits the first publication when aliases are absent. Combine those three removals with the three candidate additions in the same atomic request, without a preliminary metadata read or application-side target expansion. A failed or uncertain acknowledgement ends the rebuild; only later cleanup after a successful publication reads native alias ownership.

**Rationale and documented capabilities**: Spring [transaction-bound events](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html) separate commit from projection work. [`ThreadPoolTaskScheduler`](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/scheduling/concurrent/ThreadPoolTaskScheduler.html) executes on its own threads and supports fixed delay and ordinary submissions. One thread serializes writes without distributed locks. OpenSearch [bulk responses](https://docs.opensearch.org/latest/api-reference/document-apis/bulk/) expose item failures, and [index aliases](https://docs.opensearch.org/latest/im-plugin/index-alias/) support atomic replacement. These primitives support the design; validate their integrated behavior through the quickstart.

**Alternatives considered**: Targeted updates alone lose work on process interruption. Manual reconstruction alone was not the retained recovery behavior. A durable outbox, broker, job ledger or per-item retry framework is unnecessary because the accepted full rebuild supplies automatic catch-up. Dropping active indexes before a rebuild creates avoidable unavailability; generation replacement preserves useful results. No long SQL snapshot, multiwriter coordination or global cross-resource freshness certificate is required.

**Limits**: Events waiting in memory are lost on a crash. A full run reads successive current SQL batches, not one business snapshot. The next run and queued current-state updates restore freshness; current restrictions remain enforced in reads. Local verification uses one serving backend writer; non-web operator invocations leave the index scheduler disabled. Native queueing and ordinary bounded I/O are used, without a custom queue manager. Unknown alias outcomes are reported as failures and retain the candidates until a later successful full run.

An alias read showing the old generation after a transport timeout does not prove that the submitted switch has finished: OpenSearch 3.9.0 [queues alias changes as cluster-state tasks](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/cluster/metadata/MetadataIndexAliasesService.java), while [alias reads inspect available state](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/action/admin/indices/alias/get/TransportGetAliasesAction.java). Therefore cleanup runs only after a confirmed complete publication. Failed or still-uncertain runs leave temporary indexes for the next confirmed full run, accepting temporary disk usage instead of adding polling, retry state or a rebuild ledger. No alternate completion detector rereads aliases to turn uncertainty into success. The typed SDK and `BulkResponse.errors()` own protocol consistency; local code retains safe counts, the requested native no-partial-results policy and the explicit timeout failure signal.

## Scoped V1 evidence

[F14 transition evidence](../014-v1-v2-transition/spec.md#v1-evidence) establishes no V2 worker architecture. Historical scheduling, startup/index replacement, delete-then-insert behavior, caches, broker and separate deployment are not retained requirements.

The [F04 requirements](spec.md#functional-requirements) define examples, complete pagination and explicit errors. V2 uses the same convenient page/example sizes while removing those completeness/error defects. V1 alias material associates known identities; it does not justify global lexical rewriting. Static source inspection proves neither production execution nor the new OpenSearch integration. Withdrawn technical dossiers were not inputs.

## Public contracts, choices and mobile state

**Decision**: Use ordinary public collection GETs and one resource-type-qualified search-options GET in the existing API. Reuse F03 summaries and F02 enums. PostgreSQL owns current filter catalogues and hydrated summaries. Every empty-text read selects at most five current deterministic examples; native TanStack Query owns cached responses, textual pagination, cancellation and safe read retry.

**Rationale**: Three collection resources retain actual sporting identities and open existing detail routes. A separate options representation has a distinct purpose and lifecycle. Empty text explicitly presents examples rather than a second exhaustive mode. Existing deterministic server selection and ordinary cache reuse satisfy discovery without freezing identities across HTTP, backend and mobile. Native [TanStack infinite queries](https://tanstack.com/query/latest/docs/framework/react/guides/infinite-queries) retain all textual pages under one context key and advance through `pageParam`; separate cursor-based cache keys would require unnecessary page assembly.

**Alternatives considered**: One generic mixed-type search union adds generated-model complexity and does not match the three independent tabs. A global filter/list endpoint, random sampling on refresh, a server search session or a persistent mobile cache supplies no needed behavior. Snapshot totals and custom transient-state protocols are not required. Existing errors/ordinary retry cover dependency loss without a new screen.

Search uses no pull-to-refresh or refresh button. Its native Query owner handles safe read retry, retained permitted data and pagination without a custom first-page refresh helper. Initial/new-read failures keep the illustrated card and pagination failures keep loaded authorized rows and use only the shared local error/Retry footer, without a toast; no background read or feedback effect is introduced. An exhausted traversal removes continuation without a terminal-list message.

**Current example integration**: One stable context key owns the generated example response, within F05's private Query client lifetime and the existing captured-account bypass prefix. Supported [Query defaults](https://tanstack.com/query/v5/docs/framework/react/guides/important-defaults) keep data stale immediately and collect an unused query after five minutes. The [`subscribed` option](https://tanstack.com/query/v5/docs/framework/react/reference/useQuery) limits observations to the active examples scene, as for text scenes; cancellation consumes the existing transport signal. Returning may display cached examples while an ordinary stale read runs. Successful current data replaces the page, including an earlier empty page. Keeping the exact IDs/order would require a request mode and visit/revision/exhaustion state for a guarantee FR-003 does not require. No second selection store, response transfer or cache subscription is justified. Detail refusals retain their own F03 sensitive-value purge; benign examples/text cards wait for their collection's current server read. Current hydration, exact filters and error semantics remain authoritative. Validate cache return, replacement, cancellation and failures in deterministic owner/consumer tests and qualify the changed native integration under [T048](tasks.md).

**Support boundary**: Search reuses F10's existing form/route and finite provenance mapping. The approved [header action](https://www.figma.com/design/rKu4xc8eJsx0f0Vu4E6U03/?node-id=916-2892) uses the existing plain `IconButton` and official Lucide Flag. Only `originScreen=search` crosses that entry; editable query/filter state remains in the public visit. A generic context object, second URL factory or query/error serialization would duplicate F10 ownership and violate minimization. F10 retains its existing UUID target and private-draft session rules; this integration adds no submission or provider operation.

**Native presentation**: Use F13's approved [shared `PagedTabs` composition](../003-shared-quality/plan.md#native-paging-and-scroll-composition) and [native paging research](../003-shared-quality/research.md#native-paging-and-navigation). Search retains its visit provider and RHF field above the three actual result scenes, with tabs/report first, query/filter next and count/clear heading last. The fixed host uses opaque canvas; content owns no blur target. Existing LegendList renders usable rows directly and PageScrollView hosts content-free feedback in the actual useful area. Native list identity resets changed criteria without RNCT commands or an application offset store. One stable Query observer per resource stays at the parent, with its current context and public `subscribed` selection option, while `enabled` criteria remain unchanged. The active heading/cards derive from the same deduplicated collection. Preserve active-scene/Router checks after delayed work; do not use a captured stale active boolean. These choices change no refresh trigger, Query freshness or replay policy. Validate active-scene behavior and native layout on iOS/Android.

**Contextual sheets**: Filter and choice routes adopt F13's [intrinsic sheet composition and installed-platform rationale](../003-shared-quality/research.md#account-readiness-basic-lists-and-intrinsic-sheets), including its shared Android viewport bound. `EntryGroup` and `SelectionRow` share row inset, separators and radio/check semantics, while Search's existing RHF visit remains the sole draft owner. Structural `(sheets)` leaves retain `/search/filters` and `/search/choice`, letting the app shell clear its floating capsule without a route registry or compensating padding. No second draft or dependency is introduced. The [mobile journey](quickstart.md#mobile-journey) defines short-content, overflow and enlarged-text checks.

**Generated binding**: The discovery operations use their own generator tag so the shared request boundary can be qualified without implementing unrelated sporting operations. The selected generators translate `maxLength` into UTF-16 length checks; the query schema instead expresses the same 200-code-point bound with a Unicode property pattern, including a strict end check. Java Pattern and Orval's generated Unicode RegExp enforce it natively. Spring query converters delegate exact wire values to the generated enums' `fromValue` methods. There is no handwritten transport schema or custom validation engine.

**Validation**: Use the [quickstart](quickstart.md#contracts-and-access) for Java/TypeScript, Unicode, query parameters, response-validation and session-boundary scenarios. Native journeys and accessibility require actual platform checks.

## Local engine security and diagnostics

**Decision**: Verify local engine TLS and scoped namespace permissions. Indexes are rebuildable derivatives. Use application diagnostics for update/rebuild failure and latest useful success; no query text, contact values or engine payloads in logs.

**Rationale**: Native OpenSearch [security configuration](https://docs.opensearch.org/latest/security/configuration/index/) supports trusted TLS and least-privilege client access. Disposable local fixtures verify these boundaries without selecting hosted networks, environments or infrastructure recovery.

**Alternatives considered**: A separate operator screen or another persistent index-recovery model adds no needed application behavior. Hosting, external alerting, infrastructure backup and restoration choices remain unselected.
