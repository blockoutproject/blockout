The canonical mobile and ingestion roots contain the authored domain operations referenced by their owning plans. ## Native health boundary

Use the [Spring Boot health group](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html#actuator.endpoints.health.groups) configuration directly: include only `readinessState,db` in the `readiness` group and set its `additional-path=server:/health`. Rely on Spring Boot 4.1.1 defaults for enabled probes, group-membership validation and hidden details/components. Order statuses `down,out-of-service,unknown,up` and explicitly map `down`, `out-of-service` and `unknown` to 503. The only healthy aggregate is `UP` (200). The response uses the native Actuator status representation, not a business DTO or Problem Details wrapper.

Allow anonymous GET only at the public probe path through the application's security and maintenance rules. Other Actuator paths are not public diagnostic routes. Bound database waiting with the selected pool/JDBC settings and the external probe timeout; a timeout or unreachable API fails the probe. No custom controller, health indicator or generated client is needed. Planned maintenance does not make a broken database healthy. Suppressing expected maintenance alerts must not convert absent telemetry into success.

## Source, composition and generated outputs

1. Author YAML using OpenAPI **3.0.4**, explicit schemas and `$ref`. Root security requirements are environment-appropriate; exceptional public operations explicitly declare their access. Root files declare routes, API metadata and security; referenced domain `paths.yaml` and `schemas.yaml` files own operations and models. Reusable parameters use named `$ref` definitions, not anonymous YAML anchors. Use unique operation IDs within the generated consumer namespace and owner-meaningful schema names; resolve collisions at the semantic owner before generation.
2. Redocly CLI **2.62.1** validates each root, then bundles with native `--dereferenced` output. Shared primitives are referenced, not copied. The expanded bundle avoids Orval 8.41.0’s missing reusable-response aliases. Query parameters used by the six affected list operations are declared on those operations, retaining their shared `$ref` owners and identical wire behavior. There is no extra join/assembly/export stage.
3. OpenAPI Generator **7.26.0** emits Spring interfaces and transport models for the backend, with supported Boot 4/Jackson 3/Bean Validation configuration. Object models and reusable enum schemas carry a stable `title` matching their canonical name, so dereferencing preserves semantic model names. Name nested model shapes at their owner; intentional maps remain maps. Native [`RESOLVE_INLINE_ENUMS`](https://openapi-generator.tech/docs/customization/#inline-schema-naming) reuses the titled enum models. Emit the collector client with `library=restclient`, Boot 4/Jackson 3. Compile through the owning Maven builds/BOM instead of accepting an unrelated generated project scaffold.
4. Orval **8.41.0** emits TanStack Query functions/hooks, transport types and Zod schemas from the same mobile bundle. Select React Query + Fetch, Zod schemas, runtime validation and `includeZodSchemaInArguments` for the custom mutator. Handwritten consumers use the named canonical schemas; Orval retains its native operation/status type and validator names in generated code. The mutator uses `expo/fetch` so native redirect refusal is supported, and owns the one validation call; turning on runtime validation alone does not validate custom transport responses.
5. Generate into ignored build directories and compile/test every affected actual consumer at the same source revision. Generated outputs, bundles and caches do not enter Git. No patched templates, manual generated edits or JPA-to-contract export.

The Java `disallowAdditionalPropertiesIfNotPresent=false` option lets explicit OAS policies govern instead of the generator's legacy restrictive default. Collector unknown-response-property tolerance does not waive required-field/type/enum constraints. Generated annotations/types prove neither invocation nor runtime validation. The collector uses Atlassian OpenAPI Request Validator 3.0.0’s native Spring client interceptor against the same bundled ingestion document before generated decoding: generated Bean Validation does not enforce required nullable field presence correctly. Validation failures expose no raw report. Apache HttpClient disables automatic retries/redirects and bounds connect, pool and response waits; no template or second schema is maintained.

For normal business JSON responses, use generated named object/array schemas whose validation path is qualified. Orval's inspected path skips primitive, void and NDJSON schema passing: 204/non-JSON are handled intentionally; any later required primitive/stream shape needs a supported qualified schema path before adoption. An unexpectedly absent success schema is a failing boundary qualification, never a cast. Do not invent wrapper objects solely to conceal unsupported domain semantics.

Collector model types use the generator's supported [`additionalModelTypeAnnotations`](https://github.com/OpenAPITools/openapi-generator/blob/v7.26.0/docs/generators/java.md) option with Jackson `@JsonInclude(NON_NULL)`: omitted optional non-nullable fields must not become forbidden nulls on the wire. Generated property-level `ALWAYS` annotations retain required nulls, while `JsonNullable` retains explicit nullable proposals. The consumer suites qualify these distinctions without a custom serializer or template patch.

## Shared HTTP behavior

Requiredness and nullability remain independent. The backend enables Jackson's native [`FAIL_ON_MISSING_CREATOR_PROPERTIES`](https://github.com/FasterXML/jackson-databind/blob/jackson-databind-3.1.5/src/main/java/tools/jackson/databind/DeserializationFeature.java) for generated required constructor arguments; optional properties remain optional and permitted explicit nulls remain valid. Current request collections have non-nullable elements/values: [native content-null handling](https://github.com/FasterXML/jackson-databind/blob/jackson-databind-3.1.5/src/main/java/tools/jackson/databind/cfg/MapperBuilder.java) rejects null entries independently of whole-field nulls. Mobile uses generated optional/nullable types and [standard JSON serialization](https://tc39.es/ecma262/multipage/structured-data.html#sec-json.stringify), without replacing omission or empty values with null. Nullable collection contents would require reconciling the backend setting with the source contract.

These are resource-oriented HTTP contracts for generated, known mobile/collector consumers. Clients use the agreed operation catalogue; no hypermedia-driven action discovery is selected, so full REST conformance is not claimed. Preserve existing route vocabulary; collections use plural nouns and compound literal segments use kebab-case. The owning operation selects GET for reading, PUT for replacement, PATCH for atomic changes and POST for creation or processing, without automatic CRUD or a generic batch protocol.

- Current account, administration and ingestion responses, including errors, declare `Cache-Control: no-store` through the shared [header definitions](../../../contracts/http/common/headers.yaml). HTTP caches must not retain private responses. The separately managed in-memory mobile query cache keeps its accepted session, authorization and expiry rules. This selects no persistent cache or new service.
- Missing or invalid credentials, including expiry or wrong issuer/audience, use 401 with a Bearer `WWW-Authenticate` challenge. An authenticated caller denied by client authorization, scope or business permissions receives 403. Preserve the [Bearer authentication/authorization distinction](https://www.rfc-editor.org/rfc/rfc6750.html#section-3.1) rather than translating invalid-token failures into 403.
- Request media types are explicit; unsupported types return 415 without effects. Successful PATCH responses and existing GET responses at the same resource URI advertise [`Accept-Patch`](https://www.rfc-editor.org/rfc/rfc5789.html#section-3.1) through the shared JSON/multipart header definitions; this project convention adds no discovery endpoint. Creation returns the created resource address in `Location` with 201 when a client-visible resource address exists. F10 support returns only its opaque request reference: no private GitHub URL or fictional mobile lookup route. HTTP preconditions, if later selected, retain their standard status semantics rather than reuse a domain revision conflict.
- Authenticate backend JWTs with expected issuer, environment audience, expiry, allowed client and necessary scopes. M2M has its own client/audience, never mobile credentials. Business authorization remains in the owning use case; a valid token alone is insufficient.
- The focused mobile transport preserves cancellation signals, bounds waiting and classifies safe network/HTTP/schema errors. It validates successful business JSON exactly once before Query success/cache. Parse non-success responses through their error profile, not the success schema. No raw sensitive response is logged on validation failure.
- RFC 9457 Problem Details uses `application/problem+json`, stable machine `type`, category `title`/`status` and safe details. Canonical OpenAPI response descriptions own HTTP problem identifiers and meanings; plans reference them rather than maintain a separate catalogue. Optional `instance` is an opaque URI reference; it and owner extensions must not leak private references. Known types map to accepted presentations; unknown types map to the existing generic error. Do not duplicate `type` with a separate generic code catalogue.
- Operation response keys remain HTTP status codes. Reusable response definitions use descriptive PascalCase names. Error responses live under their owning `problems.yaml#/responses/` section, with names such as `Unauthorized`, `Forbidden`, `ServiceUnavailable` and `AccessUnavailable`. Names identify reusable contract definitions, not wire fields or additional error codes; common errors continue to share `ProblemResponse`, with domain extensions only where needed.
- Each operation documents meaning, authorization, effects, units, bounds, examples, errors and uncertain-result behavior. Property names are camelCase; compound enum values use lowercase kebab-case. Use `get…` for a resource read and `list…` for a collection read. Preserve a concept’s name and wire constraints across its representations; intentional differences follow the owner’s meaning, not the plan that introduced them. The [shared scalars](../../../contracts/http/common/scalars.yaml) define sporting start years and collection read ordinals. Response descriptions explain returned state; request descriptions explain mutation effects. Owners select dates/time-zone meaning; formats must be validated in actual consumers rather than presumed from OpenAPI annotations.
- Backend resource links use `uri-reference`, resolved against the configured backend base URL through standard URL resolution; absolute links must remain on that backend origin. External destinations use absolute `uri` values and their owning allowlist/scheme rules. Do not forward backend credentials or bypass headers to external origins.
- Define requiredness separately from nullability (`nullable` in this dialect); empty is a third value. Reject unknown request properties, including nested objects, except intentional typed maps. Responses allow additional fields but require valid known fields. Do not silently strip an invalid request and accept it.
- Bound requests and waits for the actual owning operation, without a speculative global throughput programme. A cancelled/timeout mutation may already have committed. No ordinary automatic mobile retry or network-reconnect replay; token renewal grants no permission to replay an uncertain write. Owners choose safe reread/duplicate handling, including F10's accepted manual exceptional case.

## Compatibility and coordinated changes

Mobile and ingestion roots describe surfaces of one backend deployment. Several plans may change either root. Each change names the semantic owner, provider and real consumers, reuses existing operations when their meaning matches, and regenerates/compiles/tests those consumers together. Resolve a conflicting shared definition before either dependent plan relies on it. Cross-repository consumers, if later authorized, need an exact read-only revision rather than another editable authority.

Required fields, enum additions, changed null semantics, error meaning and authorization can break existing consumers even when a schema diff appears additive. All F12-admitted mobile versions remain supported. The V1-to-V2 rebuild follows [F14 retirement](../../014-v1-v2-transition/plan.md#cutover-and-recovery): after actual V2 availability in both stores, only the frozen V1 update-status read is retained, not the V1 business API. Plan a compatible provider transition through actual new-binary availability in both stores before any explicit minimum-version change; no immediate forced update is inferred from backend release. Keep OpenAPI dialect, product version and API compatibility separate. No URL versioning scheme is invented solely because two surfaces exist.
