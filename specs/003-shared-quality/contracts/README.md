The canonical mobile and ingestion roots contain the authored domain operations referenced by their owning plans. The separate [legacy-mobile root](../../../contracts/http/legacy-mobile/openapi.yaml) preserves the F14 historical wire contract. Plans extend these sources rather than create feature-local copies. ## Native health boundary

The selected [Spring Boot health group](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html#actuator.endpoints.health.groups) combines application readiness and database connectivity. Only aggregate `UP` returns 200; all other states return 503, using the native Actuator representation. [Application configuration](../../../apps/backend/src/main/resources/application.yaml) owns group membership, the public path, status mapping and pool/JDBC waits; the external probe supplies its own timeout. Framework defaults keep details and components hidden.

Allow anonymous GET only at the public probe path through the application's security and maintenance rules. Other Actuator paths are not public diagnostic routes. A timeout or unreachable API fails the probe. Planned maintenance does not make a broken database healthy. Suppressing expected maintenance alerts must not convert absent telemetry into success.

## Source, composition and generated outputs

The following decisions define Blockout's selected pipeline. The [OpenAPI skill](../../../.agents/skills/openapi-codegen/SKILL.md) and its [generation guidance](../../../.agents/skills/openapi-codegen/references/generation.md) supply reusable implementation conventions; changing a skill does not itself change these project decisions. Exact versions and qualification limits remain in the [plan](../plan.md#technical-context) and [research](../research.md).

1. Author OpenAPI **3.0.4** YAML. Root files declare routes, API metadata and security; domain `paths.yaml` and `schemas.yaml` files own operations and models. Reusable parameters use named `$ref` definitions rather than anonymous YAML anchors.
2. The [contracts target](../../../contracts/http/project.json) runs Redocly validation and native dereferenced bundling. Expanded bundles avoid the inspected Orval version's missing reusable-response aliases; affected list operations declare query parameter references at operation level. These generator constraints leave the shared parameter owners and wire behavior unchanged.
3. The [backend](../../../apps/backend/pom.xml) and [collector](../../../apps/collector/pom.xml) Maven builds generate Spring interfaces/models and a RestClient client with Boot 4/Jackson 3 support. Object models and reusable enum schemas carry a `title` matching their canonical name so dereferencing preserves those names. Native `RESOLVE_INLINE_ENUMS` reuses titled enum models.
4. [Orval configuration](../../../apps/mobile/orval.config.ts) selects TanStack Query/Fetch and Zod from the same mobile bundle. Orval retains native operation/status validator names alongside canonical model schemas. Its schema argument reaches [apiFetch](../../../apps/mobile/src/shared/api/api-fetch.ts), which validates successful business JSON once before Query success/cache and parses errors separately. Runtime validation alone does not validate custom-mutator responses. The adapter uses `expo/fetch` for native redirect refusal, cancellation and bounded waiting, with safe network/HTTP/schema errors.
5. Bundles and generated consumers stay in ignored `.generated/` and `target/generated-sources/` directories. The [README verification commands](../../../README.md#verification) compile and test the actual consumers together.

The Java generator's additional-property configuration follows explicit OpenAPI policies. The collector's [client configuration](../../../apps/collector/src/main/java/com/blockout/collector/ingestion/IngestionClientConfiguration.java) uses generated Spring RestClient/Jackson decoding directly. The [accepted collector response decision](../research.md#http-contracts-and-validation) replaces the former Atlassian response validator with this native boundary, without a replacement schema engine, Bean Validation invocation or handwritten field checks. The contract remains unchanged: an incorrect backend response may be coerced, misinterpreted, produce incomplete work or fail later. These limits are accepted for this owned internal API; request validation, authorization and domain integrity remain backend responsibilities. Apache HttpClient still disables automatic retries/redirects and bounds connect, pool and response waits. Binary bodies map to Spring `Resource` through supported type/import mappings and its native HTTP converter.

Current mobile business JSON responses use named object/array schemas with a qualified validation path. Orval's inspected path skips primitive, void and NDJSON schema passing: the adapter handles 204/non-JSON explicitly, while any later primitive/stream shape needs a qualified schema path before adoption. The [research evidence](../research.md) records this limit; it permits neither unchecked mobile success nor wrapper objects invented to hide unsupported semantics.

The collector's generator configuration adds Jackson `@JsonInclude(NON_NULL)` so omitted optional non-nullable fields do not become forbidden wire nulls. Generated property-level `ALWAYS` annotations retain required nulls, while `JsonNullable` retains explicit nullable proposals. This is a native serialization choice qualified by the consumer suites, not a custom serializer or template patch.

## Shared HTTP behavior

Blockout contracts distinguish required/absent/null/empty values, close request objects except typed maps, and allow additive responses with valid known fields. [HttpConfiguration](../../../apps/backend/src/main/java/com/blockout/backend/config/HttpConfiguration.java) applies native Jackson handling to generated required constructor arguments, unknown properties, coercion and null collection contents. Current request collection elements/values are non-nullable; introducing nullable contents requires reconciling that setting with the source contract. Mobile uses generated optional/nullable types and standard JSON serialization.

These resource-oriented contracts target known generated mobile/collector consumers. They adopt the skill's naming and HTTP conventions while preserving existing wire vocabulary. No hypermedia-driven action discovery is selected, so full REST conformance is not claimed. Blockout-specific decisions are:

- Current account, administration and ingestion responses, including errors, declare `Cache-Control: no-store` through the shared [header definitions](../../../contracts/http/common/headers.yaml). HTTP caches must not retain private responses. The separately managed in-memory mobile query cache keeps its accepted session, authorization and expiry rules. This selects no persistent cache or new service.
- Authentication follows the [identity plan](../plan.md#identity-session-and-mobile-lifecycle): environment-specific issuer/audience checks, separate mobile/M2M clients and current business authorization. Invalid credentials return 401 with a Bearer challenge; authenticated client/scope/permission refusals return 403.
- Request media types are explicit; unsupported types return 415 without effects. Successful PATCH responses and existing GET responses at the same resource URI advertise [`Accept-Patch`](https://www.rfc-editor.org/rfc/rfc5789.html#section-3.1) through the shared JSON/multipart header definitions; this project convention adds no discovery endpoint. Creation returns the created resource address in `Location` with 201 when a client-visible resource address exists. F10 support returns only its opaque request reference: no private GitHub URL or fictional mobile lookup route. HTTP preconditions, if later selected, retain their standard status semantics rather than reuse a domain revision conflict.
- RFC 9457 Problem Details uses `application/problem+json`, stable machine `type`, category `title`/`status` and safe details. Canonical OpenAPI response descriptions own HTTP problem identifiers and meanings; plans reference them rather than maintain a separate catalogue. Optional `instance` is an opaque URI reference; it and owner extensions must not leak private references. Known types map to accepted presentations; unknown types map to the existing generic error. Do not duplicate `type` with a separate generic code catalogue.
- Error responses live under their owning `problems.yaml#/responses/` section. Common errors share `ProblemResponse`, with domain extensions where needed. These definitions add no separate wire error-code catalogue.
- Compound enum values use lowercase kebab-case. The [shared scalars](../../../contracts/http/common/scalars.yaml) own sporting start years and collection read ordinals; domains own their date/time-zone meaning.
- Backend resource links use `uri-reference`, resolved against the configured backend base URL through standard URL resolution; absolute links must remain on that backend origin. External destinations use absolute `uri` values and their owning allowlist/scheme rules. Do not forward backend credentials or bypass headers to external origins.
- Bound requests and waits for the actual owning operation, without a speculative global throughput programme. A cancelled/timeout mutation may already have committed. No ordinary automatic mobile retry or network-reconnect replay; token renewal grants no permission to replay an uncertain write. Owners choose safe reread/duplicate handling, including F10's accepted manual exceptional case.

## Compatibility and coordinated changes

Mobile and ingestion roots describe surfaces of one backend deployment. Several plans may change either root under the skill's contract-ownership guidance. Cross-repository consumers, if later authorized, need an exact read-only revision rather than another editable authority.

Required fields, enum additions, changed null semantics, error meaning and authorization can break existing consumers even when a schema diff appears additive. All F12-admitted mobile versions remain supported. The V1-to-V2 rebuild follows [F14 retirement](../../014-v1-v2-transition/plan.md#cutover-and-recovery): after actual V2 availability in both stores, only the frozen V1 update-status read is retained, not the V1 business API. Plan a compatible provider transition through actual new-binary availability in both stores before any explicit minimum-version change; no immediate forced update is inferred from backend release. Keep OpenAPI dialect, product version and API compatibility separate. Multiple surfaces alone do not require a URL versioning scheme.
