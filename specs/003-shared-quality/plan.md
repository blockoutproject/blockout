## Runtime, data and consistency

The modular backend separates HTTP adapters, application use cases and domain-owned modules. JPA owns persistence; generated object DTOs remain at transport boundaries. Application use cases own transactions and current authorization, with database constraints enforcing structural uniqueness/references. MapStruct handles useful mechanical mappings. The [Java/Spring](../../.agents/skills/java-spring/SKILL.md) and [OpenAPI](../../.agents/skills/openapi-codegen/SKILL.md) skills supply implementation conventions for these choices.

The collector acquires/parses supplier material independently, then calls the ingestion API. It has no database credentials. PostgreSQL commits backend business changes atomically within the owning use case. Slow supplier/Auth0 calls occur outside SQL transactions; any result applied later must recheck the relevant current state and ownership. Domain plans choose concrete concurrency/version checks and duplicate semantics where required; F13 adds no universal operation ledger, lock service or recovery engine.

F01 owns immutable provider-page observations and the page-reading port in collector application code. Discovery, qualification and FFVB/LNV readers consume the same value; the HTTP adapter supplies actual supplier-read/cache provenance, final URI, timestamps and ordinal. Result recording resolves one authorized cycle target and reuses its source attribution; result and image admission share bounded multi-pool selection while preserving role-specific checks, runtime/season fences and initial reconstruction.

### Application use-case families

Classify each operation by its effects, not its HTTP verb or existing class name. Four families cover the implemented backend. A cohesive class may expose several operations with the same responsibility; a different caller or endpoint alone does not justify a new service. Separate read composition, local mutation and external orchestration when they require different dependencies or transaction lifetimes. Policies, immutable values, mappers and owner APIs support these families; they are not additional handler families.

Use concrete intent names (`Read…`, `Change…`, `Accept…`, `Establish…`, `Process…`, `Purge…`) and descriptive methods, not `Service`/`ServiceImpl`, generic `execute` contracts or one class per endpoint. Inject final dependencies through constructors. Inputs are explicit owner identities, immutable commands/observations and already prepared content; preserve omitted/null/value semantics. Return immutable views, meaningful domain values or explicit outcomes. Generated DTOs, servlet state, JPA entities and provider responses stay at their adapters. Expected rejection uses the owner's existing exception; ordinary absence uses its existing value/`Optional` contract. Do not introduce a command bus, handler registry, pipeline or generic result envelope.

### Persistence responsibilities and operation patterns

Application `XStore` ports express the owner's needed operations and detached values; `JpaXStore` adapters map those values and apply managed changes. Mutations and locking loads require the caller transaction through `MANDATORY`; they never create an isolated write boundary. Feature-owned `XRepository` interfaces own inherited/derived operations and explicit JPQL/HQL selections. Cross-owner application APIs and separate Spring proxies remain when they protect ownership or a distinct commit boundary; identical forwarding helpers and adapter-to-adapter presentation relays do not.

The existing [JPA skill](../../.agents/skills/java-spring/references/persistence.md) owns repository/query selection, bounded projections, entity contracts, dirty checking and database qualification. Eligibility precedes paging/counting; scalar identity probes avoid image BLOBs. Modification loads declare their actual optimistic/pessimistic lock (`…ForUpdate`), while shared fences use `…ForShare`. Assigned-ID insert-only state uses `persist`; flushes remain only for named-constraint translation, returned revisions or required SQL ordering.

These lifecycle/query needs remain within the same owner ports and adapters. No production JDBC/native-SQL persistence path is introduced.

### HTTP controller and error pattern

Handwritten `*Controller` classes implement their generated `*Api` interfaces with `@RestController`, constructor-injected final dependencies grouped before operations, and `@Override`/`{@inheritDoc}` methods named by the generated operation IDs. Use `@RequiredArgsConstructor` for assignment-only injection. Routes, parameter binding and Bean Validation remain on generated interfaces; do not repeat their annotations or add class-level `@Validated` alongside the selected native MVC validation.

Comparable operations follow the same sequence: capture the required caller/original-resource context; validate transport details not expressed by generation; map incoming intent; invoke the application owner; map its authorized result; build the contracted `ResponseEntity`. Inline simple delegation is sufficient. Feature request adapters own JWT/header extraction, multipart reads and strict query/cursor syntax; they must preserve refusal order and never redirect an original lifecycle. Application services and values own business decisions, current authorization, transactions and outcomes. Controllers neither inspect internal state to reconstruct an outcome nor translate common application/storage failures with local catch blocks.

Use `ResponseEntity.ok()`, `created(...)`, `accepted()` and `CacheControl.noStore()` consistently. A creation/current-state outcome selects a native `BodyBuilder` before common response construction. Preserve the authored status, body, Location, Accept-Patch and binary media semantics; these are not interchangeable for visual uniformity. Mechanical DTO mapping follows the existing mapping conventions; one-field generated wrappers need no extra mapper. Local response helpers may express a repeated resource-specific header policy, without a controller superclass, handler pipeline or response framework.

Feature `@RestControllerAdvice` classes translate only their owner's typed application failures, at order 0, independently of the calling controller. Shared exception types have one translation owner. `ApiExceptionHandler` alone extends Spring's `ResponseEntityExceptionHandler`, at lowest precedence: its `createResponseEntity` hook maps the final body while retaining native committed-response handling, server-error request attributes and protocol headers. It translates precise database-resource/transaction-acquisition outages to opaque 503 and unexpected failures to opaque 500. `HttpProblems` only constructs the common generated error representation and headers; it contains no exception registry or dispatch policy. Security retains its native entry point/denied handler and sanitized Bearer challenge before MVC. Filter failures use the native resolver with the original typed failure.
