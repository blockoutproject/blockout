## Summary

Provide a small shared foundation for the V2 mobile app, ingestion and backend: one modular backend owns business writes, a separately deployed collector uses its HTTPS ingestion surface, and a native Expo app consumes its mobile surface. PostgreSQL holds authoritative relational data and accepted images together. Standard identity, contract generation, manual delivery, diagnostics and backup mechanisms preserve domain integrity without a generic recovery platform.

This plan defines the common technical foundation. F05/F12 own identity and access behavior and its design approvals. The executable workspace provides launchers, generated HTTP boundaries, the mobile query foundation, readiness checks and prepared telemetry. The [README](../../README.md#verification) describes current checks; [tasks](tasks.md) track implementation and remaining domain, native/provider and operational qualifications.

## Runtime, data and consistency

The modular backend separates HTTP adapters, application use cases and domain-owned modules. JPA owns persistence; generated object DTOs remain at transport boundaries. Application use cases own transactions and current authorization, with database constraints enforcing structural uniqueness/references. MapStruct handles useful mechanical mappings. The [Java/Spring](../../.agents/skills/java-spring/SKILL.md) and [OpenAPI](../../.agents/skills/openapi-codegen/SKILL.md) skills supply implementation conventions for these choices.

The collector acquires/parses supplier material independently, then calls the ingestion API. It has no database credentials. PostgreSQL commits backend business changes atomically within the owning use case. Slow supplier/Auth0 calls occur outside SQL transactions; any result applied later must recheck the relevant current state and ownership. Domain plans choose concrete concurrency/version checks and duplicate semantics where required; F13 adds no universal operation ledger, lock service or recovery engine.

F01 owns immutable provider-page observations and the page-reading port in collector application code. Discovery, qualification and FFVB/LNV readers consume the same value; the HTTP adapter supplies actual supplier-read/cache provenance, final URI, timestamps and ordinal. Result recording resolves one authorized cycle target and reuses its source attribution; result and image admission share bounded multi-pool selection while preserving role-specific checks, runtime/season fences and initial reconstruction.

### Application use-case families

Classify each operation by its effects, not its HTTP verb or existing class name. Four families cover the implemented backend. A cohesive class may expose several operations with the same responsibility; a different caller or endpoint alone does not justify a new service. Separate read composition, local mutation and external orchestration when they require different dependencies or transaction lifetimes. Policies, immutable values, mappers and owner APIs support these families; they are not additional handler families.

Use concrete intent names (`Read…`, `Change…`, `Accept…`, `Establish…`, `Process…`, `Purge…`) and descriptive methods, not `Service`/`ServiceImpl`, generic `execute` contracts or one class per endpoint. Inject final dependencies through constructors. Inputs are explicit owner identities, immutable commands/observations and already prepared content; preserve omitted/null/value semantics. Return immutable views, meaningful domain values or explicit outcomes. Generated DTOs, servlet state, JPA entities and provider responses stay at their adapters. Expected rejection uses the owner's existing exception; ordinary absence uses its existing value/`Optional` contract. Do not introduce a command bus, handler registry, pipeline or generic result envelope.

Application composition owns resource availability, current visibility, aggregate projections and domain transformations. A persistence adapter owns query selection, locks and entity/value mapping; it must not become an application service hidden behind a forwarding port. A cross-feature caller uses the owner's explicit application API, never its private persistence port. Preserve a short API when it enforces this boundary or participates in a caller's atomic change; remove relays that add neither an owner contract nor a separate effect/transaction boundary. Shared knowledge has one narrow owner: current read-grant checks in F12, account identity/profile rules in F05, contribution eligibility in F08, announcement allocation in F07, and collection/sporting revision rules in their respective owners.

Necessary variations are explicit rather than additional families:

- A read needing `SELECT FOR UPDATE` uses a write-capable transaction without becoming a command, only where its owner requires that lock. F12 prepared-settings reads use the current read-grant guard and F06 follow-state reads use a read-only `REPEATABLE_READ` snapshot; neither acquires the original-account command lock. Their writes and erasure retain that lock. Multi-query consultation and eligibility retain their accepted `REPEATABLE_READ` snapshot. F12 internal maintenance admission retains its fresh `REQUIRES_NEW` read so an already hydrated caller context cannot authorize a push from old settings.
- `ActionAuthorization`, `AccountAccess`, sporting lifecycle APIs and announcement/collection participants remain narrow owner APIs. Their `MANDATORY` methods hold the same lock/commit boundary as the actual mutation; they never independently commit an effect.
- Calendar acceptance and moderated-submission response composition are local counterparts of external orchestration. The latter reads original-author attribution after the command has committed, preserving concurrent rename/erasure outcomes. For the calendar, begin, each match and finish are independent local transactions. It deliberately has no outer transaction, preserving partial acceptance and final absence rules from [F02](../002-sporting-data/plan.md#acceptance-and-concurrency).
- F05 establishment retains its bounded uniqueness collision handling only after rollback; no generic retry is introduced. F07 purge performs one bulk delete in one effective transaction and logs completion/count only after commit. A definite transaction failure rolls back that entire pass; lost commit confirmation leaves an atomic but unconfirmed outcome and publishes no completion/count. The next ordinary daily or explicit manual attempt retries the idempotent deletion. Its strict logical 29-day exclusion remains independent. After-commit handoff failure cannot turn an already committed business outcome into a failed response.
- `JpaSportingStore` registers only sporting identities for derivative invalidation when its managed write actually changes persisted state. This technical notification belongs beside dirty/no-op detection: it runs through `SportingProjectionChanges.submit` with `MANDATORY`, performs no cross-feature read or external work, and resolves current dependents only after commit. Moving it to every command would duplicate change detection or expand write-port results. This exception does not move required F07 announcement policy or atomic allocation into persistence.
- Image preparation remains outside mutation transactions, between transport preflight and locked revalidation. Profile re-encoding, sporting original validation and private support originals have different accepted size/metadata/lifetime contracts; their owner-specific policies are not interchangeable helpers.

### Mapping and conversion boundaries

The existing [Java mapping skill](../../.agents/skills/java-spring/references/mapping.md) owns mechanical mapper placement, naming, injection and nested reuse; [React feature architecture](../../.agents/skills/react-feature-architecture/SKILL.md#forms-contracts-and-mapping) owns mobile editing/transport distinctions. Blockout uses MapStruct 1.6.3 at Java persistence, application-value and API/client boundaries, with typed feature functions for mobile presentation/requests. Application composition, current visibility, authorization and domain decisions remain outside mechanical mappers; persistence adapters retain bounded query selection and detached entity mapping.

Both executable Java modules have their own `MappingConfiguration`: Spring components, constructor injection, `NullValueCheckStrategy.ALWAYS`, unmapped destinations and lossy implicit numeric conversions as errors. This keeps the collector executable independent of backend code. The concrete presence and conversion choices are:

- Required-null response fields use [RequiredNullableMapping](../../apps/backend/src/main/java/com/blockout/backend/shared/api/RequiredNullableMapping.java) with field-level `ON_IMPLICIT_CONVERSION`; optional responses retain omission. Incoming nested values use native `JsonNullable.map`; collector `_JsonNullable` accessors preserve omitted/null/empty/supplied values.
- Complete supplied-state updates clear explicit null while excluding owner-managed identity/revision and unrelated fields. Sparse mobile requests use editing values and relevant RHF dirty flags; an empty editing string alone does not submit a clear. Coherent revision and validation stay with the form owner.
- Native typed enum mappings retain declared vocabulary exceptions and refuse unsupported values. Domain constructors establish invariants; pure domain code remains independent of generated transport objects. Single-field wrappers and HTTP status/Location construction need no mapper layer.
- MapStruct's installed conversion catalogue covers enum, UUID and numeric copies but lacks `Instant` ↔ `OffsetDateTime` and `String` ↔ `URI`. The focused [temporal](../../apps/backend/src/main/java/com/blockout/backend/shared/mapping/TemporalMapping.java) and [URI](../../apps/backend/src/main/java/com/blockout/backend/shared/mapping/UriMapping.java) owners cover those gaps; the collector owns its temporal counterpart. Absolute instants serialize at UTC, offsets are consumed once at ingress, and local dates/times remain local until their domain owner can establish an instant. URI literals and UUID identity are not normalized; narrowing is exact or guarded by an existing bound.

[Research](research.md#mapping-and-presence) retains the installed-library rationale; [qualification](quickstart.md#mapping-and-conversion) defines meaningful presence, precision, privacy and refusal cases rather than a duplicate file inventory.

### Persistence responsibilities and operation patterns

Application services own authorization, transaction lifetime and lock ordering. Application `XStore` ports express the owner's needed operations and detached values; `JpaXStore` adapters map those values and apply managed changes. Mutations and locking loads require the caller transaction through `MANDATORY`; they never create an isolated write boundary. Feature-owned `XRepository` interfaces own inherited/derived operations and explicit JPQL/HQL selections. A scalar identity read before a lock and a managed load after that lock have different responsibilities: merging them can reuse stale state. Cross-owner application APIs and separate Spring proxies remain when they protect ownership or a distinct commit boundary; identical forwarding helpers and adapter-to-adapter presentation relays do not.

The existing [JPA skill](../../.agents/skills/java-spring/references/persistence.md) owns repository/query selection, bounded projections, entity contracts, dirty checking and database qualification. Blockout's current choices retain native `Slice`, projected keyset `Window` or bounded ID traversal according to the owning navigation contract. Eligibility precedes paging/counting; scalar identity probes avoid image BLOBs. Modification loads declare their actual optimistic/pessimistic lock (`…ForUpdate`), while shared fences use `…ForShare`. Assigned-ID insert-only state uses `persist`; flushes remain only for named-constraint translation, returned revisions or required SQL ordering.

Narrow JPA exceptions carry explicit responsibilities: assigned-ID match state/allowances are loaded and persisted directly rather than adding empty CRUD interfaces; inbox Criteria aggregation reuses the same current selection as its keyset/member reads; the [F03 scalar Criteria boundary](../011-notifications-delivery/research.md#bounded-inbox-construction) composes visibility before consumer pagination without exposing sporting entities. Operational collection freshness uses targeted bulk updates outside the operator editing revision, with its columns excluded from ordinary entity updates so stale managed state cannot overwrite it. These lifecycle/query needs remain within the same owner ports and adapters. No production JDBC/native-SQL persistence path is introduced.

The [persistence rationale](research.md#persistence-and-scalar-reads) records installed mechanisms and preserved exceptions. PostgreSQL qualification covers actual constraints, SQL projections and independent commit/rollback/concurrent outcomes; application startup or repository mocks are insufficient evidence.

### HTTP controller and error pattern

Handwritten `*Controller` classes implement their generated `*Api` interfaces with `@RestController`, constructor-injected final dependencies grouped before operations, and `@Override`/`{@inheritDoc}` methods named by the generated operation IDs. Use `@RequiredArgsConstructor` for assignment-only injection. Routes, parameter binding and Bean Validation remain on generated interfaces; do not repeat their annotations or add class-level `@Validated` alongside the selected native MVC validation.

Comparable operations follow the same sequence: capture the required caller/original-resource context; validate transport details not expressed by generation; map incoming intent; invoke the application owner; map its authorized result; build the contracted `ResponseEntity`. Inline simple delegation is sufficient. Feature request adapters own JWT/header extraction, multipart reads and strict query/cursor syntax; they must preserve refusal order and never redirect an original lifecycle. Application services and values own business decisions, current authorization, transactions and outcomes. Controllers neither inspect internal state to reconstruct an outcome nor translate common application/storage failures with local catch blocks.

Use `ResponseEntity.ok()`, `created(...)`, `accepted()` and `CacheControl.noStore()` consistently. A creation/current-state outcome selects a native `BodyBuilder` before common response construction. Preserve the authored status, body, Location, Accept-Patch and binary media semantics; these are not interchangeable for visual uniformity. Mechanical DTO mapping follows the existing mapping conventions; one-field generated wrappers need no extra mapper. Local response helpers may express a repeated resource-specific header policy, without a controller superclass, handler pipeline or response framework.

Feature `@RestControllerAdvice` classes translate only their owner's typed application failures, at order 0, independently of the calling controller. Shared exception types have one translation owner. `ApiExceptionHandler` alone extends Spring's `ResponseEntityExceptionHandler`, at lowest precedence: its `createResponseEntity` hook maps the final body while retaining native committed-response handling, server-error request attributes and protocol headers. It translates precise database-resource/transaction-acquisition outages to opaque 503 and unexpected failures to opaque 500. `HttpProblems` only constructs the common generated error representation and headers; it contains no exception registry or dispatch policy. Security retains its native entry point/denied handler and sanitized Bearer challenge before MVC. Filter failures use the native resolver with the original typed failure.

HTTP query enums use Spring’s per-request binder and generated `fromValue` methods, with explicit concrete contract type registration. Java constant-name fallback cannot expand the wire vocabulary. Feature request owners retain their distinct parameter/cursor shapes and refusal semantics.

Exceptions retain their actual owners and reasons:

- [F12 settings](../013-administration-app-configuration/plan.md) has a controller-scoped advice because its existing fail-closed semantics intentionally translate broader data/transaction failures to 503; optimistic/stale conflicts remain 409. This does not make programming failures retryable in other features.
- [F02 image editing](../002-sporting-data/plan.md) checks current permission/source before expensive decoding, then rechecks authoritative state under the mutation lock. Native byte-read failures remain transport-specific validation errors. No servlet object or callback is passed into the transaction to hide this ordering.
- Account maintenance admission retains the original lifecycle; following hides absent owners with 404, whereas inbox absent-account refusal retains 403. Typed maintenance and authorized sporting-conflict extensions remain distinct from the opaque common problem.
- Frozen [legacy status](../014-v1-v2-transition/plan.md) is a small configuration-backed compatibility adapter, with native configuration registration and a 503 when publication settings are absent. It needs no mutable business use case. Actuator `/health` retains the separately approved native contract. Search cursor/position adaptation is transport mapping to an application-owned port value.
- Generated interfaces/placeholders without a production implementation remain incomplete under their owning feature tasks; their presence does not establish contract coverage.
