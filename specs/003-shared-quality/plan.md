## Summary

Provide a small shared foundation for the V2 mobile app, ingestion and backend: one modular backend owns business writes, a separately deployed collector uses its HTTPS ingestion surface, and a native Expo app consumes its mobile surface. PostgreSQL holds authoritative relational data and accepted images together. Standard identity, contract generation, manual delivery, diagnostics and backup mechanisms preserve domain integrity without a generic recovery platform.

This plan defines the common technical foundation. F05/F12 own the reconciled identity and access behavior and its design approvals. The executable workspace provides launchers, generated HTTP boundaries, the mobile query foundation, readiness checks and prepared telemetry. The [README](../../README.md#verification) describes current checks; [tasks](tasks.md) track implementation and remaining domain, native/provider and operational qualifications.

## Runtime, data and consistency

The modular backend separates HTTP adapters, application use cases and domain-owned modules. JPA owns persistence; generated object DTOs remain at transport boundaries. Application use cases own transactions and current authorization, with database constraints enforcing structural uniqueness/references. MapStruct handles useful mechanical mappings. The [Java/Spring](../../.agents/skills/java-spring/SKILL.md) and [OpenAPI](../../.agents/skills/openapi-codegen/SKILL.md) skills supply implementation conventions for these choices.

The collector acquires/parses supplier material independently, then calls the ingestion API. It has no database credentials. PostgreSQL commits backend business changes atomically within the owning use case. Slow supplier/Auth0 calls occur outside SQL transactions; any result applied later must recheck the relevant current state and ownership. Domain plans choose concrete concurrency/version checks and duplicate semantics where required; F13 adds no universal operation ledger, lock service or recovery engine.

### Application use-case families

Classify each operation by its effects, not its HTTP verb or existing class name. Four families cover the implemented backend. A cohesive class may expose several operations with the same responsibility; a different caller or endpoint alone does not justify a new service. Separate read composition, local mutation and external orchestration when they require different dependencies or transaction lifetimes. Policies, immutable values, mappers and owner APIs support these families; they are not additional handler families.

Use concrete intent names (`Read…`, `Change…`, `Accept…`, `Establish…`, `Process…`, `Purge…`) and descriptive methods, not `Service`/`ServiceImpl`, generic `execute` contracts or one class per endpoint. Inject final dependencies through constructors. Inputs are explicit owner identities, immutable commands/observations and already prepared content; preserve omitted/null/value semantics. Return immutable views, meaningful domain values or explicit outcomes. Generated DTOs, servlet state, JPA entities and provider responses stay at their adapters. Expected rejection uses the owner's existing exception; ordinary absence uses its existing value/`Optional` contract. Do not introduce a command bus, handler registry, pipeline or generic result envelope.

### Persistence responsibilities and operation patterns

Application services own authorization, transaction lifetime and lock ordering. Application `XStore` ports express the owner's needed operations and detached values; `JpaXStore` adapters map those values and apply managed changes. Mutations and locking loads require the caller transaction through `MANDATORY`; they never create an isolated write boundary. Feature-owned `XRepository` interfaces own inherited/derived operations and explicit JPQL/HQL selections. A scalar identity read before a lock and a managed load after that lock have different responsibilities: merging them can reuse stale state. Cross-owner application APIs and separate Spring proxies remain when they protect ownership or a distinct commit boundary; identical forwarding helpers and adapter-to-adapter presentation relays do not.

| Operation             | Implemented pattern                                                                                                                                                                                                                                                                            |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Simple read           | Inherited or derived lookup, then a typed scalar projection/JPQL query when the shape requires it. Map inside the owning transaction; avoid binary columns and mutable entity hydration for identity/eligibility probes.                                                                       |
| Paged search          | Stable owner ordering with bounded `Slice`, projected keyset `Window`, or bounded ID traversal according to the accepted navigation contract. Apply eligibility before paging/counting; fetch selected presentation in bounded queries.                                                        |
| Load for modification | `findBy…ForUpdate` identifies mutation intent; its declared optimistic or pessimistic lock supplies the actual guarantee. Shared fences use `…ForShare`. Acquire roots in the owning plan's order, then read current managed state.                                                            |
| Write                 | Persist a new generated-ID entity through Spring Data; update a loaded entity through dirty checking. Assigned-ID insert-only state uses JPA `persist`, never implicit `merge`. Flush only for immediate named-constraint translation, a returned generated revision or required SQL ordering. |
| Concurrent operation  | Keep schema constraints, owner lock order, version/no-op checks and commit boundaries together. A retry begins only after rollback; bounded purge batches commit independently; external work follows commit. No universal repository or generic retry/locking layer.                          |

Narrow JPA exceptions carry explicit responsibilities: assigned-ID match state/allowances are loaded and persisted directly rather than adding empty CRUD interfaces; inbox Criteria aggregation reuses the same current selection as its keyset/member reads; the [F03 scalar Criteria boundary](../011-notifications-delivery/research.md#bounded-inbox-construction--250) composes visibility before consumer pagination without exposing sporting entities. Operational collection freshness uses targeted bulk updates outside the operator editing revision, with its columns excluded from ordinary entity updates so stale managed state cannot overwrite it. These lifecycle/query needs remain within the same owner ports and adapters. No production JDBC/native-SQL persistence path is introduced.

The [persistence rationale](research.md#persistence-normalization) records installed mechanisms and preserved exceptions. PostgreSQL qualification covers actual constraints, SQL projections and independent commit/rollback/concurrent outcomes; application startup or repository mocks are insufficient evidence.

Store accepted PNG/JPEG image bytes, metadata and associations in PostgreSQL, with the accepted 5 MiB bound and owner access/erasure rules. Preserve previous usable projections until their replacement completes. Current restrictions still filter retained results; stale or interrupted work cannot overwrite a newer accepted state. Keep useful partial success and use ordinary next runs/manual corrections. No broker, distributed cache, exact-step checkpoint engine or generic job framework. The accepted [F04 search plan](../008-search-discovery/plan.md#projection-lifecycle) uses native OpenSearch generations and a single Spring scheduler for after-commit indexing plus startup/hourly catch-up. It adds no durable recovery queue; one backend instance per environment owns those writes. Search infrastructure is private with verified TLS and native scoped permissions, and is rebuilt from PostgreSQL after restoration rather than independently backed up.

Liquibase XML runs once as a dedicated release job with separate schema credentials. Backend startup uses Hibernate validation and disables SQL initialization; Liquibase is confined to the migration plugin and integration tests, outside the application runtime. While every database is disposable and no version has run in preproduction or production, maintain an evolving initial creation baseline, without an incremental migration file per edit. The first version in either environment freezes it. Subsequent changes are immutable migrations preserving retained data. Editing an already applied baseline does not magically update that database: this task authorizes no reset, volume erasure or checksum clearing.

## HTTP generation, errors and compatibility

The backend provides mobile and ingestion surfaces from canonical OpenAPI YAML 3.0.4 roots. Redocly validates/bundles them; OpenAPI Generator produces Java interfaces, DTOs and the collector client; Orval produces mobile Query functions/types and Zod schemas. A focused Fetch adapter validates mobile business responses before cache admission. The collector uses generated RestClient/Jackson decoding directly with the explicitly accepted internal-response limits in the interface decisions.

[Interface decisions](contracts/README.md) define the source locations, generation configuration, RFC 9457 errors, request/response validation and compatibility policy. [Research](research.md) explains the selected tools and their concrete limits; [quickstart](quickstart.md#contract-boundary) defines the integrated proof required before adoption.

### HTTP controller and error pattern

Handwritten `*Controller` classes implement their generated `*Api` interfaces with `@RestController`, constructor-injected final dependencies grouped before operations, and `@Override`/`{@inheritDoc}` methods named by the generated operation IDs. Use `@RequiredArgsConstructor` for assignment-only injection. Routes, parameter binding and Bean Validation remain on generated interfaces; do not repeat their annotations or add class-level `@Validated` alongside the selected native MVC validation.

Comparable operations follow the same sequence: capture the required caller/original-resource context; validate transport details not expressed by generation; map incoming intent; invoke the application owner; map its authorized result; build the contracted `ResponseEntity`. Inline simple delegation is sufficient. Feature request adapters own JWT/header extraction, multipart reads and strict query/cursor syntax; they must preserve refusal order and never redirect an original lifecycle.
