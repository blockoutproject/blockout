# Research: F13 shared technical foundation

**Date**: 2026-10-16 | **Plan**: [plan.md](plan.md)

The decisions below define the shared application stack, responsibilities and relevant tradeoffs. Official documentation and bounded implementation evidence establish their named boundaries, not native/provider qualification. Executable contract qualification is owned by the [boundary suites](../../README.md#verification). Server hosting and release tooling, external monitoring and backup policy are outside this research scope; existing native build and store qualification remains applicable.

[Quickstart](quickstart.md) defines the required validation. A failed qualification blocks affected adoption rather than weakening an invariant. Rejected alternatives are not a roadmap; no load/capacity or monthly-availability programme is introduced.

## Backend, collector and workspace

**Decision**: One modular Java backend; separate Java collector through HTTPS.

**Rationale**: One writer owns transactions and permissions; acquisition has its own execution lifecycle. Standard Spring/JPA mechanisms meet the need.

**Alternatives and tradeoffs**: Collector SQL access removes an HTTP call but duplicates write ownership and bypasses backend invariants. Services per feature add deployment and contract coordination without a current requirement.

**Evidence and limits**:

- **Java / Spring**: Spring Boot's current documentation identifies **4.1.1**, requires Java 17+, supports Java through 26 and Maven 3.6.3+. Java 25 is within its documented range. [Spring requirements](https://docs.spring.io/spring-boot/system-requirements.html). Temurin 25 is published and categorized as LTS; no patch/image digest was selected by this research. [Temurin releases](https://adoptium.net/temurin/releases/?arch=any&mode=filter&version=25).

- **Managed persistence dependencies**: the Boot 4.1.1 dependency table currently lists Hibernate ORM **7.4.5.Final**, PostgreSQL JDBC **42.7.13**, Liquibase **5.0.3**. These selected dependencies are managed by the Boot BOM; the build and lockfiles own their resolved graph. [Managed coordinates](https://docs.spring.io/spring-boot/appendix/dependency-versions/coordinates.html).

- **PostgreSQL 18.6** is an official release dated August 13, 2026; its notes mention security-related configuration/data cleanup considerations for upgrades. This foundation has no retained database to upgrade. The release's existence does not prove the driver or mappings used by this application. [Release notes](https://www.postgresql.org/docs/release/18.6/).

## Persistence and scalar reads

**Decision.** The SQL boundary uses the [operation patterns](plan.md#persistence-responsibilities-and-operation-patterns) consistently across accounts, access, collection, sporting, following, contributions and notifications. Repositories own query definitions, stores own boundary conversion and managed writes, and application services own complete transactions. OpenSearch remains a derived external projection; the collector has no SQL persistence. Consultation selection and presentation use one sporting owner and its scalar inter-owner Criteria contract.

**Rationale and exceptions.** Generated-ID insertion uses Spring Data new-state detection; assigned-ID insert-only rows retain `EntityManager.persist` to reject identity reuse. Existing managed entities need no repeated `save`. Flushes remain for constraint translation, returned `@Version` values and contribution replacement ordering against partial unique indexes. Account creation translates its two expected immediate uniqueness conflicts in the adapter; the application retries only after the failed transaction has rolled back. Source creation and collection result replacement need no extra flush. Freshness bulk updates intentionally leave operator revisions unchanged; excluding their columns from ordinary managed updates prevents stale overwrites. Owner-required constraints and locks remain intact; previously applied changeSets are preserved.

**Alternatives.** A universal repository or generic insert fragment would add forwarding types without a new responsibility. Merging account retry attempts or per-match announcement transactions would change required failure ownership. F07 instead accepts a single bulk-delete transaction: a definite failure rolls back that pass rather than preserving completed batches, and the next ordinary attempt retries it. Lost commit confirmation may mean the entire deletion committed; it remains unconfirmed, with no successful count announced. This removes batch selection and nested transaction orchestration while keeping logical expiry; one pass may hold more locks and produce more WAL. Materializing all public match IDs before inbox paging, or duplicating sporting visibility in notifications, would break bounded reads or owner authority.

**Mechanisms checked.** The resolved Boot 4.1.1 graph uses Spring Data JPA 4.1.1, Hibernate ORM 7.4.5.Final and Spring Framework 7.0.9. Exact local source artifacts confirm `SimpleJpaRepository.save` chooses persist/merge, Hibernate's action queue orders inserts before updates, and transaction callbacks cannot extend an already committed transaction. Official references: [entity state detection](https://docs.spring.io/spring-data/jpa/reference/jpa/entity-persistence.html), [repository transaction ownership](https://docs.spring.io/spring-data/jpa/reference/jpa/transactions.html), [Hibernate flush ordering](https://docs.hibernate.org/orm/7.4/userguide/html_single/#flushing-order), [Spring 7.0.9 transaction semantics](https://docs.spring.io/spring-framework/docs/7.0.9/javadoc-api/org/springframework/transaction/annotation/Transactional.html), [after-commit lifecycle](https://docs.spring.io/spring-framework/docs/7.0.9/javadoc-api/org/springframework/transaction/support/TransactionSynchronization.html), and [PostgreSQL 18 locking](https://www.postgresql.org/docs/18/explicit-locking.html). Rolling guides may show later patch releases; the exact installed source inspection and PostgreSQL regressions establish this implementation's evidence boundary.

**Scalar read rationale.** Sporting seasonal Criteria, detached summary batches and current owner hydration keep eligibility before consumer pagination without foreign entities, image-bearing entity loads or a cache. Match context supplies its pool presentation once. Database tests measure bounded query behavior; a persistence context can suppress repeated finds, so static repetition alone is not an N+1 measurement. [Spring Data query derivation](https://github.com/spring-projects/spring-data-jpa/blob/4.1.1/src/main/antora/modules/ROOT/pages/jpa/query-methods.adoc) and [transaction ownership](https://github.com/spring-projects/spring-data-jpa/blob/4.1.1/src/main/antora/modules/ROOT/pages/jpa/transactions.adoc) support these native boundaries. F12 settings reads use an unlocked current grant; effects require the original-account command lock. F01 uses one admitted target/source attribution with bounded multi-pool selection.

## Application transactions

The [four application families](plan.md#application-use-case-families) express read, local change, external orchestration and bounded asynchronous processing. The owner service performs authorization, composition and effects; persistence adapters retain query/lock/mapping mechanics. Cohesive operations share a class, while different transaction lifetimes and unrelated responsibilities have distinct owners. A generic handler interface or pipeline would add a new dispatch model without satisfying any unmet requirement.

Spring Boot 4.1.1 resolves Spring Framework 7.0.9 in the installed Maven BOM. The native [propagation contracts](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-tx/src/main/java/org/springframework/transaction/annotation/Propagation.java) distinguish joining/owning a transaction, requiring a caller transaction, suspending it and refusing it. Public proxied application operations own these declarations; self-invocation does not create a new transaction. Use ordinary constructor injection and `@Transactional`, retaining [TransactionTemplate](https://docs.spring.io/spring-framework/reference/data-access/transaction/programmatic.html) for variable/per-item boundaries or an exception translation that must also catch commit failure. Replacing these templates with private annotated helpers would lose their actual boundary.

Native [transaction-bound events in 7.0.9](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-tx/src/main/java/org/springframework/transaction/event/TransactionalEventListener.java) supply the after-commit phase and discard events without a transaction unless fallback is explicitly enabled. Resources may remain bound during the callback: dependent database work must retain its explicit new transaction rather than assume another `REQUIRED` operation will commit. Native listener ordering preserves announcement handoff before derivative invalidation. Downstream transient handoff failures stay isolated from the committed result. These mechanisms add no durability, automatic retry or provider success guarantee.

The simpler alternative of one surrounding transaction is rejected for calendar item acceptance and account provider orchestration: it changes required partial-commit or provider-call ownership. F07's [retention owner](../011-notifications-delivery/plan.md) accepts one purge transaction and completion only after its commit; no independently committed purge batches remain. A separate class per endpoint or an API wrapper around each port adds no responsibility. Retained owner APIs and required transaction/lock boundaries are documented in the plan and exercised through real Spring proxies and PostgreSQL where those boundaries are the behavior.

## Mapping and presence

**Decision.** Keep the [selected conversion boundaries](plan.md#mapping-and-conversion-boundaries) and use installed MapStruct 1.6.3 for mechanical Java copies, native `JsonNullable.map` for presence-preserving nested values, and ordinary typed feature functions on mobile. Module-local MapStruct configuration rejects unmapped destinations and lossy implicit conversions. UTC/URI scalar helpers and required-nullable response wrappers cover repeated concrete gaps only; none dispatches arbitrary types or chooses business policy.

**Rationale and alternatives.** Repeated expressions invoking a single helper hide mappings from MapStruct's type checking. Named sources and qualifiers retain null checks and generated nested reuse. A shared registry or base mapper would couple unrelated ownership and erase partial-update semantics. Conversely, forcing validated settings construction, notification allowance transitions, provider parsing or a one-field response through a new abstraction would obscure their actual responsibility. These remain explicit. Mobile reuses generated DTOs directly where their meaning fits; editing snapshots and presentation views exist only for different semantics. Native TanStack `hashKey` supplies query identity instead of manual serialization.

**Mechanisms and limits.** The [MapStruct 1.6.3 reference](https://mapstruct.org/documentation/1.6/reference/html/#datatype-conversions) documents built-in conversion, enum mapping, qualifiers, constructor mapping and null policies; the installed processor's conversion catalogue confirms the temporal/URI gaps. [Null property handling](https://mapstruct.org/documentation/1.6/reference/html/#controlling-mapping-result-for-null-properties-in-bean-mappings) applies to update methods and cannot represent PATCH presence by itself. Generated collector presence accessors and the installed Jackson nullable `map` operation preserve omitted/null/value. Compilation and the [behavioral inventory](quickstart.md#mapping-and-conversion) qualify the actual implementation; this refactor changes no contract, provider setting, UI design or native SDK.

## Authoritative images

**Decision**: PostgreSQL stores accepted image bytes and associations together.

**Rationale**: A database transaction preserves bytes and their association together. PNG/JPEG and 5 MiB limits bound individual accepted uploads.

**Alternatives and tradeoffs**: External image storage requires additional consistency and deletion coordination. Keeping bytes in PostgreSQL increases database size; no speculative capacity programme is required. Private F10 GitHub attachments retain their own authority.

## Schema lifecycle

**Decision**: Preserve applied Liquibase XML changesets and append data-preserving schema evolution. Execute migrations explicitly through the Maven target with separate credentials; the application validates its schema at startup.

**Rationale**: Current local databases and repeatable qualification rely on a consistent applied chain. Neither a change of development scope nor removal of hosted resources authorizes rewriting checksums, resetting databases or erasing volumes.

**Alternatives and tradeoffs**: Hibernate schema updates surrender controlled changes. Editing an applied definition does not update its database and can fail checksum validation. Disposable test fixtures remain separate from retained development data.

**Evidence and limits**: `spring.jpa.hibernate.ddl-auto=validate` and `spring.sql.init.mode=never` prevent application schema initialization; the Maven plugin owns explicit XML migration and integration tests use test-scoped `liquibase-core`. [Spring database initialization](https://docs.spring.io/spring-boot/how-to/data-initialization.html) and [Liquibase changesets](https://docs.liquibase.com/concepts/changelogs/changeset.html) document these mechanisms. Actual startup/role and PostgreSQL tests qualify the application boundary.

## HTTP contracts and validation

**Decision**: YAML OpenAPI 3.0.4, Redocly, OpenAPI Generator and Orval.

**Rationale**: A direct authored format feeds the actual Java and mobile consumers and their validators. The mobile, ingestion and legacy-mobile roots belong to one backend and reference shared primitives.

**Alternatives and tradeoffs**: A schema-language export or custom assembly stage adds an additional authority/transform without an accepted need. No editable per-plan contract copies or template forks.

**Server adapter mechanism**: The [controller/error pattern](plan.md#http-controller-and-error-pattern) uses the installed generator's [native Spring validation option](https://github.com/OpenAPITools/openapi-generator/blob/v7.26.0/docs/generators/spring.md) and Spring's [final response customization hook](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-webmvc/src/main/java/org/springframework/web/servlet/mvc/method/annotation/ResponseEntityExceptionHandler.java). Feature advices compose the shared generated problem representation without inheriting the application's global advice. This avoids duplicating Spring's exception dispatch and lifecycle. Image adapters share native `[MultipartFile.getResource()](<https://docs.spring.io/spring-framework/docs/7.0.9/javadoc-api/org/springframework/web/multipart/MultipartFile.html#getResource()>)` when reading multipart and binary content; application validation remains with its owner. No controller base class, generated-source patch or framework upgrade is needed.

**Decision**: One targeted Fetch adapter with generated Zod validation.

**Rationale**: Validate business JSON once before Query success/cache; centralize credentials, cancellation, bounded waiting and safe errors.

**Alternatives and tradeoffs**: Unchecked casts do not satisfy integrity. Validation in every screen duplicates logic; a universal middleware framework is unnecessary. Actual supported response shapes must pass integrated qualification.

**Evidence and limits**:

- [OpenAPI 3.0.4](https://spec.openapis.org/oas/v3.0.4.html) defines YAML/JSON descriptions, references and the selected schema subset. Do not write 3.1 JSON Schema syntax into this dialect. Nullability uses `nullable` with explicit `type`; requiredness remains separate. Extra object properties default to allowed. Formats are not universally validated by tools; date/time acceptance must be exercised.

- [Redocly CLI 2.62.1 release](https://github.com/Redocly/redocly-cli/releases/tag/@redocly%2Fcli@2.62.1) is published. Its [official lint-then-bundle guide](https://redocly.com/docs/cli/guides/lint-and-bundle) explicitly supports failing validation before resolving references into a single downstream input. Each root is independently bundled with its shared technical references; no custom join stage is needed.

- [OpenAPI Generator 7.26.0 release](https://github.com/OpenAPITools/openapi-generator/releases/tag/v7.26.0) is published. Version-pinned [Spring documentation](https://raw.githubusercontent.com/OpenAPITools/openapi-generator/v7.26.0/docs/generators/spring.md) includes `interfaceOnly`, model package configuration, `useSpringBoot4`, Jakarta, `useJackson3`, `useBeanValidation`, and explicit null setter controls. Choose interface/model output; do not treat a generated server project, SpringDoc export or generated persistence model as the contract authority. `disallowAdditionalPropertiesIfNotPresent` defaults to legacy restrictive behavior; set it false so explicit contract request/response policies govern. Supported options are not proof that unknown request fields are rejected at runtime.

- Version-pinned [Java client documentation](https://raw.githubusercontent.com/OpenAPITools/openapi-generator/v7.26.0/docs/generators/java.md) includes `library=restclient`, Spring 7 with `useSpringBoot4`, and Jackson 3 with `useJackson3`. `failOnUnknownProperties=false` supports additive-response tolerance; known-field validity still needs actual decoding tests. Unknown enum fallback is opt-in and must not be enabled merely to claim compatibility. Client Bean Validation defaults false; generated constraints do not establish invocation. Use the selected Boot dependency management rather than assuming a generated standalone POM matches the application.

- [Orval 8.41.0 release](https://github.com/orval-labs/orval/releases/tag/v8.41.0) is published. The [official output configuration](https://orval.dev/docs/reference/configuration/output/) documents `client: 'react-query'`, `httpClient: 'fetch'`, `schemas: {type: 'zod'}`, `override.fetch.runtimeValidation: true`, a custom mutator and `override.includeZodSchemaInArguments: true`. The native validation call is skipped when a mutator owns transport; the passed schema lets that mutator parse once. Simply turning on runtimeValidation without the schema argument does not validate custom-mutator responses. Do not use its logging validation mode for private payloads.

- The option also exists in the [8.41.0 configuration types](https://raw.githubusercontent.com/orval-labs/orval/v8.41.0/packages/core/src/types.ts), not merely unversioned documentation. Configurations expose optional-vs-null handling, schema output and status-envelope switches. A custom mutator must match the selected return shape; do not assume generated status/header wrapping is executed inside a handwritten transport.

The [8.41.0 fetch implementation](https://raw.githubusercontent.com/orval-labs/orval/v8.41.0/packages/fetch/src/index.ts) passes the schema only for eligible generated response shapes. Primitive/void responses and NDJSON streams skip the generated parse/schema path; named schema objects and eligible arrays use it. Query clients reuse this fetch path. Therefore the accepted statement means consumed JSON business object responses with a generated schema; it must not claim blanket coverage for every possible OpenAPI shape. If a feature actually needs primitive JSON, streams, or complex unions, it must qualify an appropriate generated schema invocation before adoption, not silently bypass validation. No current F13 operation requires those shapes. Preserve explicit 204/non-JSON handling and safe error parsing in the small transport adapter. A missing schema on an expected business JSON response is a qualification failure, never a successful unchecked cast.

The [7.26.0 Spring implementation](https://raw.githubusercontent.com/OpenAPITools/openapi-generator/v7.26.0/modules/openapi-generator/src/main/java/org/openapitools/codegen/languages/SpringCodegen.java) has explicit Boot 4/Jackson 3 branches; enabling Boot 4 disables Boot 3 generation. Its null-annotation path warns about defaults and does not universally reject optional non-null fields under defaults. Explicit supported configuration and actual boundary tests must establish absent/null/empty distinctions. This is not evidence for a custom template fork.

The integrated generators require native dereferenced bundles and operation-level query parameter references to avoid Orval 8.41.0’s missing aliases/parameter schemas. Orval 8.43.0 reproduces these errors and is not adopted. The source HTTP semantics remain unchanged; [interface decisions](contracts/README.md#source-composition-and-generated-outputs) own the resulting configuration.

The five profile/presentation image writes use one [image FormData owner](../../apps/mobile/src/shared/api/image-form-data.ts), selected directly by Orval's operation-level `formData` overrides in [its existing configuration](../../apps/mobile/orval.config.ts). It appends JSON metadata as an `application/json` Blob and the optional image once; native Fetch supplies encoding and the multipart boundary. F10's support adapter remains separate because its contract sends repeated attachment parts. This is a shared concrete envelope, not a multipart registry or generic serializer; operation metadata and image intent remain generated/domain-owned. Use the [contract scenarios](quickstart.md#contract-boundary) to validate integrated generation and actual multipart requests.

**Collector response boundary**: Use the generated RestClient/Jackson path directly for the owned backend API, with the explicitly accepted decoding limits below. Exhaustive response-schema enforcement does not justify a second runtime parser, bundled contract and interceptor when its stronger guarantee is not required. The [7.26.0 RestClient template](https://raw.githubusercontent.com/OpenAPITools/openapi-generator/v7.26.0/modules/openapi-generator/src/main/resources/Java/libraries/restclient/ApiClient.mustache) owns native decoding; generated Bean Validation annotations alone do not invoke validation.

A controlled HTTP probe with the actual generated client, Spring Web 7.0.9, Jackson 3.1.5 and application mappers observed missing required fields, numeric coercion and out-of-range values reaching application code. Missing revision/count/continuation fields can become primitive defaults; missing collections can fail during mapping. Consequently incorrect backend responses may be misinterpreted, truncate work, appear successful or fail late. These consequences are explicitly accepted without relaxing the OpenAPI contract. Native decoding still rejects malformed JSON and invalid UUID/enum/date values in the exercised cases. The probe does not establish exhaustive rejection or require these limitations to persist after an upstream fix.

Do not substitute manual field checks or a Bean Validation pass: the generated nullable runtime field also carries `@NotNull`, which rejects a valid explicit null when invoked directly. Keep tests of real producer serialization, valid consumer data, native decoding errors and downstream partial outcomes. Request validation, OAuth, domain controls, bounded waits and no automatic replay retain their existing guarantees.

[Expo Fetch](https://docs.expo.dev/versions/v58.0.0/sdk/expo/#expofetch-api) supplies redirect handling and cancellation, including response-body reads. The adapter passes native AbortSignals and translates failures. The Fetch adapter passes the request signal and reports aborted failures as cancellation; F05’s private-client lifetime supplies identity isolation. Cancellation cannot retract a completed body read or prove that a mutation was rolled back. The named import avoids React Native's XHR Fetch polyfill. Native networking requires device qualification separately from the adapter's controlled tests.

**Query enum binding.** Spring Framework 7.0.9's [TypeConverterDelegate](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-beans/src/main/java/org/springframework/beans/TypeConverterDelegate.java) can fall back to Java constant names after converter rejection. The selected per-request editor delegates to each generated `fromValue`, preserving exact contract vocabulary without duplicating values. Qualify omission, defaults and refusal through actual MVC binding; feature cursor/query shapes remain distinct.

### Native request-policy qualification

HttpConfiguration is a small centralized Jackson configuration, not a second validator. An installed Boot/Jackson probe against generated DTOs and Bean Validation distinguishes its responsibilities: default binding accepts unknown fields/string booleans, truncates a fractional revision and admits a null Set member; a missing required-nullable gradient can become present null. JsonNullable presence, missing-creator checks, non-null collection contents and integer fidelity preserve actual write meaning. Unknown/coercion refusal remains optional grammar policy, with only a few native settings; retaining those settings does not establish that stronger spelling is essential to authorization. No new validation middleware, request ledger or parser framework is selected. A wider grammar change is not required merely to remove native library configuration.

## Proportionate qualification

**Decision**: Use deterministic owner and consumer tests for delayed responses, cancellation, original targets, account isolation and distinct side effects, followed by ordinary native transitions and representative shared compositions. Native coverage retains FR-029's declared runtime matrix and the relevant platform differences; it does not repeat every mutation or schedule across every theme, font size and OS. Each changed UI mechanism receives an applicable native composition with ordinary focus, labels/roles/states, enlarged text, reduced motion and reachable actions under FR-030. Dedicated VoiceOver/TalkBack campaigns remain excluded. The [plan](plan.md#proportionate-qualification) owns the execution boundary and the existing [quickstart](quickstart.md#native-ui-and-approved-design) supplies runnable cases.

**Rationale and alternatives**: Precisely timed manual races repeat controlled ordering checks without reliably isolating their cause. The existing [private-client isolation test](../../apps/mobile/src/shared/query/__tests__/session-isolation.test.tsx) and [late native-identity test](../../apps/mobile/src/features/accounts/__tests__/account-session-provider.test.tsx) control deferred completion at the actual Query/session owner; they establish those tested boundaries, not a live provider result. Repeating every equivalent shared visual state on every consumer adds no distinct mechanism proof. Automated checks alone are also insufficient: SDK-owned storage, serialized global identity effects, purchases/restoration, push, native permissions and signing/upgrade continuity retain focused real-boundary checks at their owners.

**Evidence reuse and limits**: Reuse generation/reproducibility and native composition evidence only when the relevant source, dependencies, configuration and integration remain applicable to the exercised scope. A changed wire contract, permission, consumer effect or native mechanism needs its own useful check; a JavaScript-only change may use an already compatible client, while a changed native graph needs the affected rebuild and runtime evidence. Record passed, failed and unavailable outcomes in delivery evidence. Absorbed tracker scope, retired scenarios, local exports and approved design supply no missing runtime pass. T077 retains live iOS text-resize requalification, the accepted Android crop-intermediate defect retains its official-correction/native-cleanup boundary, and T058 retains the exact production-identity binary; none is completed by this shared policy.
