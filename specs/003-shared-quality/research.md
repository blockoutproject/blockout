# Research: F13 shared technical foundation

**Date**: 2026-10-16 | **Plan**: [plan.md](plan.md)

The decisions below preserve the accepted direction and explain the relevant alternatives. Evidence comes from official documentation, bounded upstream source inspection and the authorized read-only Auth0 account inspection. Documented support and observed source behavior do not establish integrated Blockout runtime compatibility. Executable contract qualification is owned by the [boundary suites](../../README.md#verification); provider, deployment and restoration evidence remains separate.

[Quickstart](quickstart.md) defines the required validation. A failed qualification blocks affected adoption rather than weakening an invariant. Rejected alternatives are not a roadmap; no load/capacity or monthly-availability programme is introduced.

## Backend, collector and workspace

**Decision**: One modular Java backend; separate Java collector through HTTPS.

**Rationale**: One writer owns transactions and permissions; acquisition has its own execution lifecycle. Standard Spring/JPA mechanisms meet the need.

**Alternatives and tradeoffs**: Collector SQL access removes an HTTP call but duplicates write ownership and bypasses backend invariants. Services per feature add deployment and contract coordination without a current requirement.

**Evidence and limits**:

- **Java / Spring**: Spring Boot's current documentation identifies **4.1.1**, requires Java 17+, supports Java through 26 and Maven 3.6.3+. Java 25 is within its documented range. [Spring requirements](https://docs.spring.io/spring-boot/system-requirements.html). Temurin 25 is published and categorized as LTS; no patch/image digest was selected by this research. [Temurin releases](https://adoptium.net/temurin/releases/?arch=any&mode=filter&version=25).

- **Managed persistence dependencies**: the Boot 4.1.1 dependency table currently lists Hibernate ORM **7.4.5.Final**, PostgreSQL JDBC **42.7.13**, Liquibase **5.0.3**. These are observed BOM values, not independently approved overrides. Prefer the selected Boot BOM; lock the actual resolved graph when executable work is authorized. [Managed coordinates](https://docs.spring.io/spring-boot/appendix/dependency-versions/coordinates.html).

- **PostgreSQL 18.6** is an official release dated August 13, 2026; its notes mention security-related configuration/data cleanup considerations for upgrades. This foundation has no retained database to upgrade. The release's existence does not prove the planned image, driver, mappings or backup integration. [Release notes](https://www.postgresql.org/docs/release/18.6/).

[Nx ordinary targets](https://nx.dev/docs/kb/executors-and-configurations) can run shell commands with `nx:run-commands`, supporting the accepted orchestration of npm/Maven without new platform plugins. The [Nx 23.3.0 release](https://github.com/nrwl/nx/releases/tag/23.3.0) is published (2026-10-07); the [official Node compatibility matrix](https://nx.dev/docs/technologies/node/introduction) lists Node 24 for Nx 23. This establishes release availability and supported major pairing, not a qualified Blockout workspace.

## Persistence normalization

**Decision.** The implemented SQL boundary uses the [operation patterns](plan.md#persistence-responsibilities-and-operation-patterns) consistently across accounts, access, collection, sporting, following, contributions and notifications. Repositories own query definitions, stores own boundary conversion and managed writes, and application services own complete transactions. OpenSearch remains a derived external projection; the collector has no SQL persistence. Consolidating consultation selection and presentation removes the forwarding adapter while preserving its scalar inter-owner Criteria contract.

**Rationale and exceptions.** Generated-ID insertion uses Spring Data new-state detection; assigned-ID insert-only rows retain `EntityManager.persist` to reject identity reuse. Existing managed entities need no repeated `save`. Flushes remain for constraint translation, returned `@Version` values and contribution replacement ordering against partial unique indexes. Account creation translates its two expected immediate uniqueness conflicts in the adapter; the application retries only after the failed transaction has rolled back. Source creation and collection result replacement need no extra flush. Freshness bulk updates intentionally leave operator revisions unchanged; excluding their columns from ordinary managed updates prevents stale overwrites. No constraint, lock or schema migration is removed.

**Alternatives.** A universal repository or generic insert fragment would add forwarding types without a new responsibility. Merging account retry attempts, notification purge batches or per-match announcement transactions would change failure ownership. Materializing all public match IDs before inbox paging, or duplicating sporting visibility in notifications, would break bounded reads or owner authority. These boundaries therefore remain explicit.

**Mechanisms checked.** The resolved Boot 4.1.1 graph uses Spring Data JPA 4.1.1, Hibernate ORM 7.4.5.Final and Spring Framework 7.0.9. Their exact local source artifacts confirm `SimpleJpaRepository.save` chooses persist/merge, Hibernate's action queue orders inserts before updates, and transaction callbacks cannot extend an already committed transaction. Official references: [entity state detection](https://docs.spring.io/spring-data/jpa/reference/jpa/entity-persistence.html), [repository transaction ownership](https://docs.spring.io/spring-data/jpa/reference/jpa/transactions.html), [Hibernate flush ordering](https://docs.hibernate.org/orm/7.4/userguide/html_single/#flushing-order), [Spring 7.0.9 transaction semantics](https://docs.spring.io/spring-framework/docs/7.0.9/javadoc-api/org/springframework/transaction/annotation/Transactional.html), [after-commit lifecycle](https://docs.spring.io/spring-framework/docs/7.0.9/javadoc-api/org/springframework/transaction/support/TransactionSynchronization.html), and [PostgreSQL 18 locking](https://www.postgresql.org/docs/18/explicit-locking.html). Rolling guides may show later patch releases; the exact installed source inspection and PostgreSQL regressions establish this implementation's evidence boundary.

## Application use-case normalization

The [four application families](plan.md#application-use-case-families) classify implemented behavior without adding an execution framework. The owner service performs authorization, composition and effects; persistence adapters retain query/lock/mapping mechanics. Cohesive operations share a class, while different transaction lifetimes and unrelated responsibilities have distinct owners. This corrects adapter-owned consultation composition, copied eligibility/authorization rules and mixed read/command services at their source. A generic handler interface or pipeline would add a new dispatch model without satisfying any unmet requirement.

Spring Boot 4.1.1 resolves Spring Framework 7.0.9 in the installed Maven BOM. The native [propagation contracts](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-tx/src/main/java/org/springframework/transaction/annotation/Propagation.java) distinguish joining/owning a transaction, requiring a caller transaction, suspending it and refusing it. Public proxied application operations own these declarations; self-invocation does not create a new transaction. Use ordinary constructor injection and `@Transactional`, retaining [TransactionTemplate](https://docs.spring.io/spring-framework/reference/data-access/transaction/programmatic.html) for variable/per-item boundaries or an exception translation that must also catch commit failure. Replacing these templates with private annotated helpers would lose their actual boundary.

Native [transaction-bound events in 7.0.9](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-tx/src/main/java/org/springframework/transaction/event/TransactionalEventListener.java) supply the after-commit phase and discard events without a transaction unless fallback is explicitly enabled. They replace hand-written synchronization callbacks where the same owner event already exists. Resources may remain bound during the callback: dependent database work must retain its explicit new transaction rather than assume another `REQUIRED` operation will commit. Native listener ordering preserves announcement handoff before derivative invalidation, as with the former synchronization callback. Downstream transient handoff failures stay isolated from the committed result. These mechanisms add no durability, automatic retry or provider success guarantee.

The simpler alternative of one surrounding transaction is rejected for calendar item acceptance, account provider orchestration and independent purge batches: it changes partial-commit, lock duration or failure behavior. Conversely, a separate class per endpoint or an API wrapper around each port adds no responsibility. Retained owner APIs, locked reads and independently committed batches are documented in the plan and exercised through real Spring proxies and PostgreSQL where those boundaries are the behavior.

## Mapping normalization

**Decision.** Keep the [five actual conversion families](plan.md#mapping-and-conversion-boundaries) and use installed MapStruct 1.6.3 for mechanical Java copies, native `JsonNullable.map` for presence-preserving nested values, and ordinary typed feature functions on mobile. Module-local MapStruct configuration rejects unmapped destinations and lossy implicit conversions. UTC/URI scalar helpers and required-nullable response wrappers cover repeated concrete gaps only; none dispatches arbitrary types or chooses business policy.

**Rationale and alternatives.** Repeated expressions invoking a single helper hide mappings from MapStruct's type checking. Named sources and qualifiers retain null checks and generated nested reuse. A shared registry or base mapper would couple unrelated ownership and erase partial-update semantics. Conversely, forcing validated settings construction, notification allowance transitions, provider parsing or a one-field response through a new abstraction would obscure their actual responsibility. These remain explicit. Mobile reuses generated DTOs directly where their meaning fits; editing snapshots and presentation views exist only for different semantics. Native TanStack `hashKey` supplies query identity instead of manual serialization.

**Mechanisms and limits.** The [MapStruct 1.6.3 reference](https://mapstruct.org/documentation/1.6/reference/html/#datatype-conversions) documents built-in conversion, enum mapping, qualifiers, constructor mapping and null policies; the installed processor's conversion catalogue confirms the temporal/URI gaps. [Null property handling](https://mapstruct.org/documentation/1.6/reference/html/#controlling-mapping-result-for-null-properties-in-bean-mappings) applies to update methods and cannot represent PATCH presence by itself. Generated collector presence accessors and the installed Jackson nullable `map` operation preserve omitted/null/value. Compilation and the [behavioral inventory](quickstart.md#mapping-and-conversion-inventory) qualify the actual implementation; this refactor changes no contract, provider setting, UI design or native SDK.

## Authoritative images

**Decision**: PostgreSQL stores accepted image bytes and associations together.

**Rationale**: A database transaction and a single logical backup preserve the association. PNG/JPEG and 5 MiB limits bound individual accepted uploads.

**Alternatives and tradeoffs**: External image storage requires consistency, deletion and restore coordination. Keeping bytes in PostgreSQL increases backup size; accepted without a speculative capacity programme. Private F10 GitHub attachments retain their own authority.

## Schema lifecycle

**Decision**: Mutable initial XML baseline, then immutable migrations at first preproduction/production version.

**Rationale**: Keep few files while every database is disposable; preserve data once an environment has a real release. Separate migration credentials keep the application from altering its schema.

**Alternatives and tradeoffs**: Incremental migrations before any retained version add history with no current preservation benefit. Hibernate schema updates surrender controlled delivery. No reset or checksum clearing is authorized.

**Evidence and limits**:

- **Schema execution**: Use `spring.jpa.hibernate.ddl-auto=validate` and `spring.sql.init.mode=never`, with no Liquibase starter in the application runtime. The Maven plugin owns explicit XML migration; integration tests use test-scoped `liquibase-core`. Omitting the startup integration avoids carrying and disabling an unused mechanism. [Database initialization](https://docs.spring.io/spring-boot/how-to/data-initialization.html).

- **Liquibase baseline**: changesets carry execution history/checksums and normally run once; changing an applied definition can stop validation. The mutable disposable baseline is a project posture, not a provider feature that updates an existing retained schema. Initial creation changesets can remain in one evolving baseline before the first preproduction/production version; this never authorizes reset or checksum clearing. Freeze the baseline at that first version, then append immutable evolution. [Changesets](https://docs.liquibase.com/concepts/changelogs/changeset.html), [checksum behavior](https://docs.liquibase.com/secure/user-guide-5-2/what-is-a-changeset-checksum). The latter documentation is labeled Secure 5.2: it supports the conceptual explanation, not qualification of the precise chosen CLI edition/version.

## HTTP contracts and validation

**Decision**: YAML OpenAPI 3.0.4, Redocly, OpenAPI Generator and Orval.

**Rationale**: A direct authored format feeds the actual Java and mobile consumers and their validators. The mobile, ingestion and legacy-mobile roots belong to one backend and reference shared primitives.

**Alternatives and tradeoffs**: A schema-language export or custom assembly stage adds an additional authority/transform without an accepted need. No editable per-plan contract copies or template forks.

**Server adapter mechanism**: The [controller/error pattern](plan.md#http-controller-and-error-pattern) uses the installed generator's [native Spring validation option](https://github.com/OpenAPITools/openapi-generator/blob/v7.26.0/docs/generators/spring.md) and Spring's [final response customization hook](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-webmvc/src/main/java/org/springframework/web/servlet/mvc/method/annotation/ResponseEntityExceptionHandler.java). Feature advices compose the shared generated problem representation without inheriting the application's global advice. This avoids duplicating Spring's exception dispatch and lifecycle. Image adapters share native `[MultipartFile.getResource()](<https://docs.spring.io/spring-framework/docs/7.0.9/javadoc-api/org/springframework/web/multipart/MultipartFile.html#getResource()>)` when reading multipart and binary content; application validation remains with its owner. No controller base class, generated-source patch or framework upgrade is needed.

**Decision**: One targeted Fetch adapter with generated Zod validation.

**Rationale**: Validate business JSON once before Query success/cache; centralize credentials, cancellation, bounded waiting and safe errors.

**Alternatives and tradeoffs**: Unchecked casts do not satisfy integrity. Validation in every screen duplicates logic; a universal middleware framework is unnecessary. Actual supported response shapes must pass integrated qualification.

**Evidence and limits**:

- [OpenAPI 3.0.4](https://spec.openapis.org/oas/v3.0.4.html) defines YAML/JSON descriptions, references and the selected schema subset. Do not write 3.1 JSON Schema syntax into this dialect. Nullability uses `nullable` with explicit `type`; requiredness remains separate. Extra object properties default to allowed. Formats are not universally validated by tools; date/time acceptance must be exercised.

- [Redocly CLI 2.62.1 release](https://github.com/Redocly/redocly-cli/releases/tag/@redocly%2Fcli@2.62.1) is published. Its [official lint-then-bundle guide](https://redocly.com/docs/cli/guides/lint-and-bundle) explicitly supports failing validation before resolving references into a single downstream input. Each root is independently bundled with its shared technical references; no custom join stage is needed.

- [OpenAPI Generator 7.26.0 release](https://github.com/OpenAPITools/openapi-generator/releases/tag/v7.26.0) is published. Version-pinned [Spring documentation](https://raw.githubusercontent.com/OpenAPITools/openapi-generator/v7.26.0/docs/generators/spring.md) includes `interfaceOnly`, model package configuration, `useSpringBoot4`, Jakarta, `useJackson3`, `useBeanValidation`, and explicit null setter controls. Choose interface/model output; do not treat a generated server project, SpringDoc export or generated persistence model as the contract authority. `disallowAdditionalPropertiesIfNotPresent` defaults to legacy restrictive behavior; set it false so explicit contract request/response policies govern. Supported options are not proof that unknown request fields are rejected at runtime.

- Version-pinned [Java client documentation](https://raw.githubusercontent.com/OpenAPITools/openapi-generator/v7.26.0/docs/generators/java.md) includes `library=restclient`, Spring 7 with `useSpringBoot4`, and Jackson 3 with `useJackson3`. `failOnUnknownProperties=false` supports additive-response tolerance; known-field validity still needs actual decoding tests. Unknown enum fallback is opt-in and must not be enabled merely to claim compatibility. Client Bean Validation defaults false; generated constraints do not establish invocation. Use the selected Boot dependency management rather than assuming a generated standalone POM matches the application.

- [Orval 8.41.0 release](https://github.com/orval-labs/orval/releases/tag/v8.41.0) is published. The [official output configuration](https://orval.dev/docs/reference/configuration/output/) documents `client: 'react-query'`, `httpClient: 'fetch'`, `schemas: {type: 'zod'}`, `override.fetch.runtimeValidation: true`, a custom mutator and `override.includeZodSchemaInArguments: true`. The native validation call is skipped when a mutator owns transport; the passed schema lets that mutator parse once. Simply turning on runtimeValidation without the schema argument does not validate custom-mutator responses. Do not use its logging validation mode for private payloads.

- The option also exists in the [8.41.0 configuration types](https://raw.githubusercontent.com/orval-labs/orval/v8.41.0/packages/core/src/types.ts), not merely unversioned documentation. Configurations expose optional-vs-null handling, schema output and status-envelope switches. A custom mutator must match the selected return shape; do not assume generated status/header wrapping is executed inside a handwritten transport.

The [8.41.0 fetch implementation](https://raw.githubusercontent.com/orval-labs/orval/v8.41.0/packages/fetch/src/index.ts) passes the schema only for eligible generated response shapes. Primitive/void responses and NDJSON streams skip the generated parse/schema path; named schema objects and eligible arrays use it. Query clients reuse this fetch path. Therefore the accepted statement means consumed JSON business object responses with a generated schema; it must not claim blanket coverage for every possible OpenAPI shape. If a feature actually needs primitive JSON, streams, or complex unions, it must qualify an appropriate generated schema invocation before adoption, not silently bypass validation. No current F13 operation requires those shapes. Preserve explicit 204/non-JSON handling and safe error parsing in the small transport adapter. A missing schema on an expected business JSON response is a qualification failure, never a successful unchecked cast.

The [7.26.0 Spring implementation](https://raw.githubusercontent.com/OpenAPITools/openapi-generator/v7.26.0/modules/openapi-generator/src/main/java/org/openapitools/codegen/languages/SpringCodegen.java) has explicit Boot 4/Jackson 3 branches; enabling Boot 4 disables Boot 3 generation. Its null-annotation path warns about defaults and does not universally reject optional non-null fields under defaults. Explicit supported configuration and actual boundary tests must establish absent/null/empty distinctions. This is not evidence for a custom template fork.

The integrated generators require native dereferenced bundles and operation-level query parameter references to avoid Orval 8.41.0’s missing aliases/parameter schemas. Orval 8.43.0 reproduces these errors and is not adopted. The source HTTP semantics remain unchanged; [interface decisions](contracts/README.md#source-composition-and-generated-outputs) own the resulting configuration.

The five profile/presentation image writes use one [image FormData owner](../../apps/mobile/src/shared/api/image-form-data.ts), selected directly by Orval's operation-level `formData` overrides in [its existing configuration](../../apps/mobile/orval.config.ts). It appends JSON metadata as an `application/json` Blob and the optional image once; native Fetch supplies encoding and the multipart boundary. The two identical feature adapters are removed. F10's support adapter remains separate because its contract sends repeated attachment parts. This is a shared concrete envelope, not a multipart registry or generic serializer; operation metadata and image intent remain generated/domain-owned. Integrated generation and request tests are qualified in the [composition results](quickstart.md#shared-composition-qualification).

**Collector response boundary**: The accepted native decoding boundary supersedes the former Atlassian response-validator decision. Use the generated RestClient/Jackson path directly for this owned backend API. Exhaustive response-schema enforcement does not justify a second runtime parser, bundled contract and interceptor when its stronger guarantee is not required. The [7.26.0 RestClient template](https://raw.githubusercontent.com/OpenAPITools/openapi-generator/v7.26.0/modules/openapi-generator/src/main/resources/Java/libraries/restclient/ApiClient.mustache) owns native decoding; generated Bean Validation annotations alone do not invoke validation.

A controlled HTTP probe with the actual generated client, Spring Web 7.0.9, Jackson 3.1.5 and application mappers observed missing required fields, numeric coercion and out-of-range values reaching application code. Missing revision/count/continuation fields can become primitive defaults; missing collections can fail during mapping. Consequently incorrect backend responses may be misinterpreted, truncate work, appear successful or fail late. These consequences are explicitly accepted without relaxing the OpenAPI contract. Native decoding still rejects malformed JSON and invalid UUID/enum/date values in the exercised cases. The probe does not establish exhaustive rejection or require these limitations to persist after an upstream fix.

Do not substitute manual field checks or a Bean Validation pass: the generated nullable runtime field also carries `@NotNull`, which rejects a valid explicit null when invoked directly. Keep tests of real producer serialization, valid consumer data, native decoding errors and downstream partial outcomes. Request validation, OAuth, domain controls, bounded waits and no automatic replay retain their existing guarantees.

[Expo Fetch](https://docs.expo.dev/versions/v58.0.0/sdk/expo/#expofetch-api) supplies redirect handling and cancellation, including response-body reads. The adapter passes native AbortSignals and translates failures. Before admitting a result, it checks the final signal and captured session generation; these guards cannot retract a completed body read or prove that a mutation was rolled back. The named import avoids React Native's XHR Fetch polyfill. Jest exercises the adapter; native networking still requires device evidence.

## Native UI projection and system appearance

**Decision**: Use a small typed projection of the approved Figma variables/styles with React Native `StyleSheet`, native system appearance and bundled Outfit. The [plan](plan.md#native-ui-and-approved-design) owns module responsibilities and dependencies; this adds no UI HTTP contract or persisted model.

**Rationale**: The live [UI Library Color guidance](https://www.figma.com/design/l8EIQApzbfM24FwR0WKyAC/?node-id=7-3) separates semantic light/dark, sporting context and membership. Its Context Color modes are representative fixtures; production uses the approved derivation from effective sporting inputs, not a hard-coded palette per division. Separate Core, Typography, Motion and Platform collections supply other values. [Product Design Patterns](https://www.figma.com/design/rKu4xc8eJsx0f0Vu4E6U03/?node-id=253-2) composes library instances. Existing light/dark modes are observed; automatic system following is the explicit requirement in [FR-035](spec.md#platforms-accessibility-and-bounded-continuity), not an inferred prior implementation.

React Native's [useColorScheme](https://reactnative.dev/docs/usecolorscheme) subscribes to appearance changes; [Expo color themes](https://docs.expo.dev/develop/user-interface/color-themes/) requires automatic native appearance and `expo-system-ui` for Android development builds. [StyleSheet](https://reactnative.dev/docs/stylesheet) retains typed native style properties without another styling runtime. [Expo SDK 58 fonts](https://docs.expo.dev/versions/v58.0.0/sdk/font/) supports bundled font configuration; native family/weight resolution must be checked on each platform rather than assuming a Figma label maps directly to an installed face.

**Native limits**: [React Native text styles](https://reactnative.dev/docs/text-style-props) documents Android font padding and closest-weight substitution when a face is absent; bundle the actual Outfit faces rather than compensating with arbitrary spacing. The primary Button's outward `boxShadow` is available on the supported Android 10 floor through React Native's [native shadow API](https://reactnative.dev/docs/view-style-props#boxshadow). The [native qualification scenarios](quickstart.md#native-mobile-and-approved-design) cover font resolution, effects and host behavior.

**Android support**: Blockout requires Android 10 / API 29. This floor permits the [currently supported Chrome](https://support.google.com/chrome/answer/95414?co=GENIE.Platform%3DAndroid&hl=en) used for hosted authentication, with ordinary system certificate validation. The installed [Expo BuildProperties](https://docs.expo.dev/versions/v58.0.0/sdk/build-properties/) plugin declares `android.minSdkVersion: 29` for every build variant. The application uses platform Java-time APIs directly and adds no certificate resource, custom trust manager or compatibility library for this boundary. Qualify the generated APK and the complete authentication/form journey on an unmodified API 29 image and the latest stable Android runtime.

**Font faces**: Register the four static Outfit files through the shared `expo-font` file list and select their exact names in semantic typography, as documented by the [font guide](https://docs.expo.dev/develop/user-interface/fonts/). Their filenames match their PostScript names: `Outfit-Regular` (400), `Outfit-Medium` (500), `Outfit-SemiBold` (600) and `Outfit-Bold` (700). Selecting each bundled face directly preserves the intended distinction across platforms without numeric-weight overrides or platform branches. Retain the five semantic styles and their dimensions; native face resolution and enlarged-text rendering require platform qualification.

The [native qualification gallery](https://github.com/blockoutproject/product-prototype/blob/39f7b231a70264e2de9a6c798a0628c318985eb1/evidence/standard-presentations-2026-10-22/README.md) reproduced stale live Dynamic Type layout on iPhone 18 Pro / iOS 27 / RN 0.86.3: after keyboard dismissal, a later layout truncated unchanged field labels and the confirmation button; cold launch at enlarged text rendered correctly. This observation is consistent with the upstream report, not a causal bisect. The [Fabric correction](https://github.com/react/react-native/commit/45904c866882f136edde55df2fe453327057d387) is included in the newly selected React Native 0.88 baseline. Requalify the actual upgraded iOS build through [T077](tasks.md#phase-9-user-story-6--use-the-application-with-the-phones-capabilities-priority-p2) before declaring the defect resolved; a dependency upgrade alone is not passing evidence. The [scoped adoption boundary](spec.md#initial-control-adoption-boundary) remains applicable until that result. Add no font-scale remount, manual font calculation or dependency patch.

**Presentation selection**: The 2026-10-22 owner decision limits sheets to brief contextual choices, invitations and previews, moves text-entry and extended confirmation journeys to ordinary screens, and uses native dialogs for simple confirmations. It preserves the existing content and domain rules. The former short/intermediate/long form-sheet comparison is no longer the product contract. [Expo Router modals](https://docs.expo.dev/router/advanced/modals/) supplies native `formSheet` presentation; its iOS UIKit and Android Material hosts may have different interactions.

The short-sheet candidate registers `presentation: "formSheet"`, `headerShown: false` and `sheetGrabberVisible: true` before navigation, with one `[0.5]` detent in the qualification route. The grabber is iOS-only. The route uses `contentStyle: { backgroundColor: colors.surface }`, to keep the native sheet surface continuous when its content is shorter than the detent, without computing content geometry; dimming retains the native default. [React Navigation’s platform considerations](https://reactnavigation.org/docs/native-stack-navigator/#platform-considerations) require Android nested scrolling and describe its short-content limitation; a single position avoids coordinating multiple heights. Numeric detents support bounded content in Expo SDK 55 and later; This qualification example does not use `fitToContents` or automatic height switching. The compact, non-scrolling [F05 guest invitation](../005-accounts-identity/plan.md#profile-photo-and-concurrent-changes) uses the owner-selected content-fitting exception with a natural-height `View`; retain the documented Android restriction against `flex: 1` at that root. For the scrolling default, keep a first-child `ScrollView` with `nestedScrollEnabled`, then one [SafeAreaView bottom edge](https://docs.expo.dev/versions/v58.0.0/sdk/safe-area-context/) around its content. Title, close control and actions scroll together if enlarged text overflows. Sheets contain no keyboard-driven form or keyboard compensation.

Ordinary form routes use one documented keyboard mechanism per platform, with `keyboardShouldPersistTaps="handled"`. iOS uses React Native [ScrollView](https://reactnative.dev/docs/scrollview#automaticallyadjustkeyboardinsets) with `automaticallyAdjustKeyboardInsets`. Android uses the default [KeyboardAwareScrollView](https://kirillzyusko.github.io/react-native-keyboard-controller/docs/1.21.0/api/components/keyboard-aware-scroll-view), under [KeyboardProvider](https://kirillzyusko.github.io/react-native-keyboard-controller/docs/1.21.0/api/keyboard-provider), from the third-party `react-native-keyboard-controller` 1.22.7 supported by [Expo SDK 58](https://docs.expo.dev/versions/v58.0.0/sdk/keyboard-controller/). This adds a native dependency and provider prerequisite; it is not a React Native core-only solution. Reanimated is already installed. No manual offsets, header-height calculations or stacked avoidance are selected.

The bounded native trials justify this split: on Android API 37, Expo’s default `resize` alone left the final field/action covered; the tested stock [KeyboardAvoidingView](https://reactnative.dev/docs/keyboardavoidingview) with `behavior="height"` and zero offset exposed the last field but not the action. Default KeyboardAwareScrollView exposed both in the tested Android compositions. Applying that library on iOS instead left the final caret/text overlapping the keyboard in the small-screen trial, so iOS retains its native inset API. These are observed compositions, not a general claim that the alternatives cannot work. The [native evidence gallery](https://github.com/blockoutproject/product-prototype/blob/39f7b231a70264e2de9a6c798a0628c318985eb1/evidence/standard-presentations-2026-10-22/README.md) retains exact builds and interactions; [quickstart](quickstart.md#native-presentation-qualification) owns qualification scenarios and limits. Sheets themselves contain no text-entry form or keyboard compensation.

[Alert.alert](https://reactnative.dev/docs/alert) supplies simple confirmations with explicit cancel/confirm callbacks; the business owner issues the command only from confirmation. Android supports at most three buttons and platform styling differs. Do not put typed confirmation, checkbox safeguards or long forms into an alert. The Figma Dialog component documents content and action semantics, not a Blockout skin to reproduce over the system dialog. The SubmitBar describes ordinary actions within scrolling content, not a sticky-footer requirement. Provider-owned Auth0 and RevenueCat content remains excluded from app-owned rendering; [F05](../005-accounts-identity/plan.md) and [F09](../006-pro-subscriptions/plan.md) own their integration and lifecycle.

These documented mechanisms form the candidate for [native presentation qualification](quickstart.md#native-presentation-qualification); source/docs inspection is not runtime acceptance. FR-029 governs the minimum/latest runtime selection, and the accepted live Dynamic Type limitation remains separately tracked. No framework upgrade, dependency patch or custom modal focus repair is selected.

## Frontend mutation inventory

The [canonical responsibilities](plan.md#frontend-mutation-conventions) apply to the only implemented frontend, `apps/mobile`. The audit covers **23 generated HTTP write operations**, all their mounted and exposed consumers, and **19 local/native/memory families** below. It excludes generated declarations without runtime consumers: account erasure, notification mutation, contribution/moderation and support submission are not implemented UI commands yet. Their existing owning tasks remain incomplete.

**Why these changes:** the same resource could be submitted twice through stale render flags or retained native callbacks; RHF submission state was combined with Query pending; a draft-local recovery flag disappeared when the draft was discarded; acknowledgement/cache logic and invalidations were repeated among comparable commands. Login establishment and discovery completion additionally depended on an effect consuming an action flag. The solution keeps native Query records, removes those obsolete paths, and treats the existing session and native owners as separate contracts. It adds no operation ledger, offline queue, compatibility layer or generic command bus.

## Application observability

The scoped [F05 cleanup decision](../005-accounts-identity/research.md#synchronous-business-deletion-and-manual-external-cleanup) uses native log alerting and private original-target references for manual handling. It accepts interruption before logging without a durable recovery record; the exception does not broaden other telemetry.

**Decision**: Native Grafana alerts and manual investigation.

**Rationale**: Scope, latest successful stages and partial outcomes support intervention without a custom incident system.

**Alternatives and tradeoffs**: An incident ledger/custom notifier adds state and maintenance. Native closure only means the condition stopped; the operator still assesses business recovery.

**Evidence and limits**:

[Alloy Docker logging](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.source.docker/) supports ordinary Docker discovery/log consumption and preserves read offsets. An Alloy healthy-component flag is not proof of current incoming telemetry. [Synthetic monitoring](https://grafana.com/docs/grafana-cloud/observe-and-act/testing/synthetic-monitoring/introduction/) executes each probe independently outside the monitored host. Public API health must test the DB and return minimal state while private diagnostics retain detail.

Server telemetry uses the existing [Boot ECS encoder and native JSON member filtering](https://docs.spring.io/spring-boot/reference/features/logging.html#features.logging.structured). Its explicit permitted fields exclude free-form messages, raw throwables and arbitrary MDC; native error types and authored operational fields retain safe diagnosis. Only the backend permits the owning F05 `account_cleanup` original-target fields. This intentionally reduces framework prose instead of attempting heuristic redaction or introducing another encoder/logging facade. Callers still own the meaning and safety of permitted field values.

Use BOM-managed Micrometer OTLP plus Boot's OpenTelemetry support module for [native metrics export](https://docs.spring.io/spring-boot/reference/actuator/metrics.html#actuator.metrics.export.otlp); no tracing bridge/exporter or OpenTelemetry logging appender is added. This preserves the collector's non-web launcher; a Prometheus scrape would require another HTTP listener and security boundary there. The existing generated RestClient receives the native observation registry. Export is opt-in through standard properties, with application identity supplied by Boot and environment through native `OTEL_RESOURCE_ATTRIBUTES`.

[Alloy 1.20.1](https://github.com/grafana/alloy/releases/tag/v1.20.1) is pinned for Docker log collection and OTLP forwarding. Native relabel/JSON stages restrict application/environment selection and log labels; native OTTL `keep_keys` restricts metric attributes before forwarding. Keep original cleanup targets solely in private log bodies. The Docker socket grants engine access despite a read-only mount and requires target-host authorization. Grafana's retention does not expire Docker's local source storage: confirm the host's privacy lifetime before admitting private cleanup references; size rotation is not an age guarantee. Shared-host logging changes and actual activation are not implied by this configuration.

[Spring Boot 4.1 health groups](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html#actuator.endpoints.health.groups) support native readiness and database contributors, aggregate-only output and an additional path on the main application port. Use this native boundary rather than add a generated controller that delegates to the same check: the latter adds a duplicate representation and wiring without a business consumer. The approved generation exception is limited to `/health`. Explicitly map unknown health to failure and retain DOWN/OUT_OF_SERVICE mappings when overriding defaults; native defaults otherwise map unknown to 200. The [MVC and PostgreSQL health suites](../../apps/backend/src/test/java/com/blockout/backend/config/) qualify native main-port routing, security, bounded database failure and diagnostic non-disclosure with controlled inputs. External probes and the implemented F12 maintenance exception still require their owning integrated qualifications.

Rely on Spring Boot 4.1.1 defaults for health-only web exposure, enabled probes, group-membership validation and hidden details/components. Keep only the group, path and non-UP status overrides in application configuration; the health suites protect the resulting behavior.

Use [Hikari's native connection/validation timeouts](https://github.com/brettwooldridge/HikariCP#configuration-knobs-baby) (3/1 seconds) and the [PostgreSQL socket read timeout](https://jdbc.postgresql.org/documentation/use/) (5 seconds). Actuator's [native JDBC check](https://github.com/spring-projects/spring-boot/blob/v4.1.1/module/spring-boot-jdbc/src/main/java/org/springframework/boot/jdbc/health/DataSourceHealthIndicator.java) calls `isValid(0)`, so pool timeouts alone cannot bound a borrowed connection's check. Retain the driver's default connect timeout: Hikari already bounds callers waiting for a connection. This supersedes the initial additional 3-second JDBC connect override. The retained limits apply to all application database calls, including long silent SQL operations; they are operational bounds, not a latency SLA. The operational security chain permits only `GET /health`, denies diagnostic aliases/components and introduces no local user/password login; business JWT authentication remains with T038.

[Grafana pricing](https://grafana.com/pricing/), rechecked on 2026-10-17, gives Free 14-day logs retention, 50 GB monthly log ingest, 10k active metric series and 100k API test executions/month. Using [documented calculation](https://grafana.com/docs/grafana-cloud/platform/pricing-and-usage/synthetic-monitoring/), two checks at the retained frequencies and one probe each consume approximately 51,840 executions/30 days (53,568/31 days). This arithmetic is a provider-quota check, not a capacity programme; other account use and emitted telemetry consume shared allowances. No automatic paid upgrade is authorized.

[Notification grouping](https://grafana.com/docs/grafana-cloud/observe-and-act/alert-and-measure-reliability/alerting/fundamentals/notifications/group-alert-notifications/) supports a repeat interval up to five days, aligned to group interval; choose a divisor such as native five minutes. Group changes can notify between reminders, so five days is not a universal suppression interval. [Discord contact point](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/configure-discord/) natively emits firing/resolved notifications. Resolution establishes only rule-condition change, not F01 observation/acquisition/integration/projection recovery. Missing data needs an explicit non-healthy treatment. Group by useful low-cardinality operational scope; domain owners supply latest useful success and partial outcomes.

**Decision:** Sentry Free for JS errors/native crashes and source maps; no replay, tracing or profiling. [Expo Sentry integration](https://docs.expo.dev/guides/using-sentry/) documents `@sentry/react-native`, EAS source-map support and an actual release test. [Sentry Free pricing](https://sentry.io/pricing/) documents a single-user Developer plan; do not promise paid third-party integrations. [Filtering](https://docs.sentry.io/platforms/react-native/configuration/filtering/) supplies `beforeSend` and breadcrumb hooks. [Collected data](https://docs.sentry.io/platforms/react-native/data-management/data-collected/) explicitly warns that outgoing URLs/query strings and console breadcrumbs can contain PII; disabling default PII alone is insufficient. Native event filtering, symbol/source-map upload and representative redaction must be qualified in native builds, with intentionally harmless fixtures.

Follow the [Expo/Sentry setup](https://docs.sentry.io/platforms/react-native/guides/expo/) with the Expo-compatible Sentry React Native version selected in [mobile dependencies](../../apps/mobile/package.json), its Metro/config plugins and one JavaScript `Sentry.init()`. Keep automatic native initialization and native crash handling at their SDK defaults, including Android NDK; no application-owned Swift/Kotlin initialization or crash parser is retained. The T024/T030 activation boundary keeps `enabled: false` in every build, including releases with a DSN, until separately authorized T033 qualification and an explicit activation decision. The JavaScript `beforeSend` hook removes free-form context and attachment hints while preserving standard JS error categories (unknown/custom names become `Error`), handled status, packaged source coordinates and UUID-shaped source-map Debug IDs. SDK name/version and build/event metadata remain technical inputs, never a channel for user/provider content. `maxBreadcrumbs: 0` disables JavaScript breadcrumbs before scope storage/synchronization and bounds the separate native capture surface; the event filter also excludes any supplied breadcrumbs. No additional breadcrumb hook is needed.

**Qualification limit:** JavaScript `beforeSend` does not process native events. Sentry officially supports [server-side scrubbing](https://docs.sentry.io/security-legal-pii/scrubbing/server-side-scrubbing/) and [attachment/minidump scrubbing](https://docs.sentry.io/security-legal-pii/scrubbing/attachment-scrubbing/). These operate after transmission and do not prove that sensitive data never reaches Sentry. Default rules are not an exhaustive guarantee; the documentation warns against scrubbing stack memory because it is needed to reconstruct useful stacks. Before activation, T033 must qualify the actual project's available controls, retained event fields and crash-file retention against FR-013 with harmless fixtures. T024/T030 cover local filtering/configuration only; T033 owns actual native privacy and symbolication evidence. Keep sending disabled if the standard controls cannot satisfy that requirement; no custom Relay, binary scrubber, paid capability or weakening of FR-013 is authorized by choosing the standard integration.

The inspected [8.28.0 options](https://github.com/getsentry/sentry-react-native/blob/8.28.0/packages/core/src/js/options.ts) and [native bridge](https://github.com/getsentry/sentry-react-native/blob/8.28.0/packages/core/src/js/wrapper.ts) support disabled sending, default PII, session tracking, screenshots/view hierarchy, failed-request capture and iOS app-hang/watchdog controls. Those optional capture surfaces are disabled. Replay/tracing/profiling sampling stays absent, and client reports/Sentry Logs are disabled. This version also exposes native breadcrumb controls and iOS `enableMemoryIntrospection`, which defaults to false and omits memory contents near a crash; `attachAllThreads`, MetricKit/raw-payload capture and Android tombstone capture also default to false. ANR profiling is disabled when `anrProfilingSampleRate` is absent, but the React Native options still expose no independent general Android ANR switch. T033 must verify these supported controls and the actual native payload rather than infer that preserving crash handling guarantees crash-only events or removes all exception text, memory and private paths. Keep the existing activation gate; these controls authorize neither sending nor custom interceptors.

## Backups and restoration

**Decision**: Native Dokploy logical backups, S3 lifecycle, one initial isolated restore.

**Rationale**: Protect authoritative data/images with supported scheduling and retention; ordinary manual inspection matches the accepted requirement.

**Alternatives and tradeoffs**: No recurring verification, backup alerts, count purge, versioning, replication or cleanup service. Failures may remain unnoticed; one successful drill does not prove every future dump.

**Evidence and limits**:

[Dokploy database backup](https://docs.dokploy.com/docs/core/databases/backups) supports S3 destination, database, cron, prefix and enablement. [Restore](https://docs.dokploy.com/docs/core/databases/restore) documents its PostgreSQL `pg_dump -Fc --no-acl --no-owner` format and restoring its own backups. This is a database logical backup, not Dokploy's whole-server backup and not a live-volume copy. The missing owners/ACLs imply explicit recreation of intended identities/grants from configuration during recovery; no preservation of grants may be inferred. All application image bytes stored in ordinary PostgreSQL values are included in that database dump; qualification must prove their associations and integrity.

[Dokploy API](https://docs.dokploy.com/docs/api/reference-backup) exposes nullable `keepLatestCount`; qualify disabled/null count cleanup in the retained release and leave retention to S3. [S3 lifecycle expiration](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html) is asynchronous; a 30-day rule is not physical deletion exactly at 720 hours. [SSE-S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingServerSideEncryption.html) encrypts stored objects with S3-managed keys; this does not encrypt a downloaded dump or remove access-control obligations. Schedule activity or file existence is not successful restoration.

**Known activation blocker, statically reconfirmed:** [v0.30.8 backup utility](https://github.com/Dokploy/dokploy/blob/v0.30.8/packages/server/src/utils/backups/utils.ts#L66-L85) generates S3 flags with shell-quote, whereas [redactor](https://github.com/Dokploy/dokploy/blob/v0.30.8/packages/server/src/utils/backups/redact.ts) matches only double-quoted flag values. [Execution wrapper](https://github.com/Dokploy/dokploy/blob/v0.30.8/packages/server/src/utils/process/execAsync.ts#L23-L47) retains raw command/error details; [PostgreSQL runner](https://github.com/Dokploy/dokploy/blob/v0.30.8/packages/server/src/utils/backups/postgres.ts) forwards error messages and rethrows errors. Disabling backup notifications does not fix the command/log path. Preserve the accepted requirement to select and verify a release fixing all relevant paths before using real V2 S3 credentials. This research neither identifies a qualified fixed release nor reproduces exposure with credentials. No fork or workaround selected. This condition blocks activation, not documentation finalization.

## Manual delivery and promotion

**Decision**: Manual release qualification and promotion of identical artefacts.

**Rationale**: Human-controlled production and store release; digests/build IDs avoid a different reconstruction after qualification.

**Alternatives and tradeoffs**: Automatic deployment on merge is outside accepted control. A custom release ledger or orchestrator duplicates native tool records. Server/mobile promotion is not atomic and requires compatibility.

**Evidence and limits**:

**Documented:** [Dokploy Compose](https://docs.dokploy.com/docs/core/docker-compose) permits replacing its complete deployment command (Dokploy prepends `docker`). It documents queued-deployment cancellation but not cancellation of a running deployment. [Dokploy v0.30.8 builder](https://github.com/Dokploy/dokploy/blob/v0.30.8/packages/server/src/utils/builders/compose.ts#L72-L118) statically permits `&&` chains, requiring subsequent members to start with `docker compose` or `docker-compose`, and rejects shell substitution, pipes, semicolons and newlines. Therefore use explicit literal Compose arguments for each member, including the same project, env-file and compose-file arguments; do not assume defaults are appended. The accepted pull → stop writers → one-off migration → start/wait chain fits that mechanism. A failed member prevents the following member through ordinary shell `&&`. The exact assembled command still needs the isolated deployment qualification.

[Compose run](https://docs.docker.com/reference/cli/docker/compose/run/) supports a one-off `--rm --no-deps` migration container; [Compose up](https://docs.docker.com/reference/cli/docker/compose/up/) supports `--wait` and a bounded wait timeout. The future Compose file must actually declare service health checks; a running process alone is not application health. Explicitly select backend and collector when stopping/starting so PostgreSQL is not included. There is no evidence that Dokploy coordinates business maintenance, SQL compatibility or cross-store delivery; those remain operator/application responsibilities.

[GHCR](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry) supports digest-addressed pulls. Source revision plus image digests and native CI/deployment records suffice; no editable release ledger or rebuild for promotion is needed. A source-matching candidate is a project gate, not a guarantee GHCR provides.

[Expo TestFlight](https://docs.expo.dev/submit/testflight/) documents submitting an existing production/store build without rebuilding and a separate explicit App Store release. Internal distribution is not TestFlight internal testing. [Expo submission](https://docs.expo.dev/deploy/submit-to-app-stores/) distinguishes uploaded binaries, testing tracks and store release. Preserve build IDs through qualification and publication; Blockout Preprod is a separate variant and cannot substitute for qualification of the production binary. No EAS Update/OTA follows from these capabilities.

The executable packaging uses ordinary multi-stage Dockerfiles and the committed Maven wrapper; the minimal JDK builder needs `unzip` to retain the configured ZIP/checksum rather than the wrapper's automatic tarball fallback. The dedicated publisher Liquibase 5.0.3 image receives authored changelogs and the PostgreSQL driver resolved from Boot's BOM through Maven's native dependency plugin. No Maven runtime or schema credentials enter the application images. [Liquibase JDBC/classpath integration](https://docs.liquibase.com/community/integration-guide-5-0-3/connect-liquibase-with-postgresql).

Manual preparation reuses CI and the official Docker/Expo actions. Native GitHub artifacts retain digest outputs and minimal EAS build identifiers; workflow source revision and environment approvals provide the handoff, with no release ledger. Promotion compares Git trees, requires the production approval and hands the same references to the operator. Dokploy executes its native command/queue, and the native store consoles own explicit binary release. A custom Dokploy API client/poller would add orchestration without eliminating these accepted manual qualifications; it is omitted. [Build variants](https://docs.expo.dev/build-reference/variants/), [EAS lifecycle hooks](https://docs.expo.dev/build-reference/npm-hooks/), [GitHub environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments). Actual setup and commands belong in the [delivery guide](../../infra/dokploy/README.md); external execution remains pending its owning tasks.

## Common backend responsibility decisions

**Decision**: Keep the existing use-case, error, authorization, transaction and persistence-port grammar; unify only the concrete responsibilities identified in the [plan](plan.md#common-backend-composition). Independent inspection covered accounts/access, sporting/consultation, search, following, contributions, notifications, collection/collector, images and prepared support. No backend Pro/privacy provider implementation is present to migrate.

**Rationale**: Query enum handling split one wire rule across converters, a local formatter and manual reparse. Spring Framework 7.0.9's [TypeConverterDelegate](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-beans/src/main/java/org/springframework/beans/TypeConverterDelegate.java) can fall back to Java enum names after a converter rejection; a native per-request editor with generated `fromValue` preserves the exact contract vocabulary. Three image consumers repeated native decoder lifetime and detection while legitimately owning different budgets/transforms. Collector application imported an infrastructure response solely for the same page observation. Follow season reads referred to sporting private entities/predicates. Search rehydrated each already-selected sporting candidate through separate read paths, repeating visibility and scalar projections and loading image bytes just to establish logo presence. Read and publication adapters duplicated resource alias names.

**Alternatives retained or rejected**: Keep domain advice and account read/command guards because their status, lifecycle and locking semantics differ. Keep distinct cursor/page shapes and generated/application/domain models where their meanings differ. Reuse existing scalar Criteria composition rather than materializing an unbounded ID list or moving foreign entities across features. Batch existing summaries with JPA projections rather than introducing a cache or generic query engine. A single decoded-image policy would break profile/support/sporting guarantees; only ImageIO mechanics are common. Existing transaction templates, after-commit listeners, OAuth clients and provider confirmation limits already have concrete responsibilities. No generic result, HTTP-client, validation, command, event or recovery framework is warranted.

**Season selection ownership**: `JpaSportingReadStore` implements `SportingSeasonSelection` alongside its read port, following the existing `JpaConsultationStore`/`ConsultationMatchSelection` arrangement. This supersedes the separate stateless selection bean: composing the same seasonal visibility has no independent lifecycle or dependencies. Keep the narrow selection interface because F06 needs scalar Criteria expressions, not the broader sporting read port. It is a query-composition contract, not another persistence store. Existing handwritten `Jpa*Store` adapters retain `@Repository`; Spring Data creates the `*Repository` interface implementations through its repository factory. Renaming or annotating both roles identically would obscure their different responsibilities.

**Remaining-consumer decisions**: Match composition extends the already selected scalar team presentation batches instead of retaining a second entity-graph/presentation path. It reuses the pool presentation already mapped with the required season/classification context rather than querying that pool again. A persistence context may suppress repeated `findById` statements, so no N+1 improvement is claimed without measurement; removal is justified by one composition owner and avoiding team/club image loads. F01 reuses the admitted `Target` instead of checking existence and resolving it again; native Spring Data first-result selection preserves bounded multi-pool admission for both result recording and image capability checks. The latter retains its additional direct-logo current-parent check. F12 reads use the existing unlocked read guard, while effects keep the command lock. Optional principal resolution removes exception-based ordinary absence without changing the feature-owned refusal status. No schema, wire model, dependency or external effect changes. [Spring Data query derivation](https://github.com/spring-projects/spring-data-jpa/blob/4.1.1/src/main/antora/modules/ROOT/pages/jpa/query-methods.adoc) and [transaction ownership](https://github.com/spring-projects/spring-data-jpa/blob/4.1.1/src/main/antora/modules/ROOT/pages/jpa/transactions.adoc) support these ordinary mechanisms; executable tests qualify the installed BOM-managed versions.

**Verification**: The [qualification](quickstart.md#common-backend-composition) distinguishes controlled MVC/ImageIO/HTTP tests, real PostgreSQL/OpenSearch tests and started-application evidence. Static inference of repeated queries is not a runtime measurement; the batched hydration decision requires database query-count evidence.
