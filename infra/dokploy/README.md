# Manual application delivery

[F13](../../specs/003-shared-quality/plan.md#manual-delivery-and-operations) owns delivery policy. This guide describes the executable configuration; it grants no deployment, signing, store-publication or provider permission. Native environment qualification remains under F13 T053/T058, with the actual Actions→Dokploy handoff pending T213. The database backup redaction prerequisite remains separate under T047/T054/T055; do not supply real V2 S3 credentials before it passes.

## Images and configuration

Build from the repository root. The application Dockerfiles regenerate canonical contracts, then use the committed Maven wrapper and dependency management. `unzip` is a build prerequisite for the wrapper's checksum-verified ZIP. Application runtimes contain the executable JAR and Temurin 25 JRE, run as UID 10001 and receive termination signals directly. The migration image contains Liquibase 5.0.3, authored changelogs and the Boot-managed PostgreSQL JDBC driver; it retains the publisher's non-root user and entrypoint.

```sh
docker build -f apps/backend/Dockerfile -t blockout-backend:local .
docker build -f apps/collector/Dockerfile -t blockout-collector:local .
docker build -f apps/backend/Dockerfile.migration -t blockout-migration:local .
docker compose --env-file infra/dokploy/.env.example -f infra/dokploy/compose.yaml config --quiet
```

Local application development still runs on the host. Release Compose contains no PostgreSQL service or database volume. Configure independent production/preproduction PostgreSQL instances, volumes and networks in Dokploy. Use the existing [role boundary](../postgres/init-roles.sql) as a disposable test example, not as a command to reset an existing environment. Backend receives only the application role; the one-off migration receives schema-owner credentials. Collector receives neither database credentials nor the database network.

### Fresh durable preproduction

Use the Dokploy project **Blockout pré-production**, environment `preproduction`, native PostgreSQL resource `postgres` and independent Raw Compose resource `release`. Keep private database/release inputs and the credential replacement inventory under ignored `local/preproduction/`, with credentials readable only by their owner. Copy only each resource's required inputs into Dokploy.

1. Create [native PostgreSQL](https://docs.dokploy.com/docs/core/databases) with image `postgres:18.6`, a fresh dedicated volume, bootstrap database `postgres` and a separate administrator login. Keep **External Port** empty (`externalPort: null`); no PostgreSQL port is published. Verify that the native volume covers `PGDATA=/var/lib/postgresql/18/docker`: its leaf mount differs from a Compose volume mounted at `/var/lib/postgresql`. This is fresh initialization, not a volume migration; see the [PostgreSQL 18 image layout](https://hub.docker.com/_/postgres).
2. Create `blockout-preproduction-database` as an internal [attachable overlay network](https://docs.docker.com/engine/network/drivers/overlay/) so the native Swarm database and standalone Compose containers can join it: `docker network create --driver overlay --attachable --internal blockout-preproduction-database`. In Dokploy's native network form, select driver **Overlay** and enable **Attachable** and **Internal**; in the PostgreSQL resource's **Networks** settings, select only this network and detach the shared `dokploy-network`. This selector does not configure an alias. Verify the effective service networks and absence of published ports after deployment and every native database redeployment.
3. Through the authorized administrator connection, create `blockout_migration` and `blockout_app` with distinct private passwords, and business database `blockout` owned by `blockout_migration`. Apply the ownership, `PUBLIC` revocations, application DML grants and migration-owner default privileges from the [existing role boundary](../postgres/init-roles.sql), adapted to this fresh native bootstrap. Neither runtime role receives administrator flags; the application role receives no schema creation or migration-role membership. Never inject the administrator credentials into release Compose.
4. Set `BLOCKOUT_ENVIRONMENT=preproduction` and `BLOCKOUT_DATABASE_NETWORK=blockout-preproduction-database` in the private release inputs. Set `SPRING_DATASOURCE_URL=jdbc:postgresql://<Internal Host>:5432/blockout`, replacing `<Internal Host>` with the hostname Dokploy provides under PostgreSQL **General → Internal Credentials**. The example's `postgres` hostname is a placeholder; use it only if that network alias was deliberately configured. The existing Compose database network connects only backend and migration. Use application credentials for backend and migration credentials only for the one-off Liquibase service. Supply exact private GHCR digests and verify authenticated server pulls before starting the release.

Configure PostgreSQL's native Swarm mode as **Replicated** with one replica and a `pg_isready` **HealthCheck**. For both **Update Config** and **Rollback Config**, use parallelism `1`, order `stop-first` and failure action `pause`. Follow **Save** with **Deploy** to apply these settings, then verify the new task retains the same volume and data. The destructive **Rebuild** action is not a persistence test.

Retain the native volume across application deployments and verify the actual mounts, role boundaries, migration result and backend/database health before accepting setup. These instructions do not establish runtime success. Backup activation and restoration qualification remain with [#140](https://github.com/blockoutproject/blockout/issues/140) and [#350](https://github.com/blockoutproject/blockout/issues/350).

### Application configuration

Before application startup, provision the environment's external telemetry network using the [observability setup](../observability/README.md), even if Alloy activation remains pending. Both applications carry Alloy's admission labels and join this private network; migration does neither. Once the receiver and its privacy prerequisites are qualified, set `MANAGEMENT_OTLP_METRICS_EXPORT_ENABLED=true` in the private environment configuration. It defaults to `false`. Starting the authorized Alloy stack admits labelled application logs independently of this metrics switch. No OTLP port is published by application Compose.

For each environment, create a native Dokploy Docker Compose application with **Raw** source. Copy [compose.yaml](compose.yaml) from the exact candidate revision and retain its native deployment record. Enable creation of Dokploy's `.env` file and supply private values using [.env.example](.env.example) as the field list. Set the three image references to qualified `ghcr.io/...@sha256:...` digests. Do not print resolved environment values. Configure the backend domain/HTTPS and port 8080 through Dokploy's native domain UI; collector uses that environment's HTTPS API origin. Keep automatic deployments and image-update hooks disabled.

For private GHCR packages, verify registry access on the actual deployment server before delivery. Dokploy v0.31.0 uses the Docker login already present on that machine for Raw Compose custom commands; it does not log in to every saved registry before each deployment. Use [Settings → Registry](https://docs.dokploy.com/docs/core/registry) to test the authorized existing GHCR entry against that server, then verify pulls of all three exact digests. A successful login alone does not prove package access. [GHCR](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry) requires an authorized account and a classic PAT with `read:packages` for private pulls; the GitHub CLI's ordinary repository token may lack this scope. Registry login is shared by host/registry, not isolated by Compose environment: do not replace or remove historical credentials as part of an isolated qualification.

Keep the backend, collector and migration packages private. New GHCR packages are private by default; publishing a new version preserves the existing package visibility. Verify package visibility and repository Actions access after creation. A public package cannot be switched back to private: an authorized replacement requires deletion/republication or new private package paths, with newly verified digest references. See [GitHub package visibility](https://docs.github.com/en/packages/learn-github-packages/configuring-a-packages-access-control-and-visibility) and [deletion/restoration](https://docs.github.com/en/packages/learn-github-packages/deleting-and-restoring-a-package).

### First account and operator access

Release Compose explicitly injects the Auth0 Management registration needed for account establishment into **backend only**, using the private inputs listed in [.env.example](.env.example). Its OAuth grant and authentication method are fixed in Compose. Account establishment needs the existing authorized Management client's `read:users`; provider deletion and cleanup remain subject to their separate F05 prerequisites and must stay disabled for a read-only qualification. The [backend environment example](../../apps/backend/.env.example) retains those separate activation inputs.

Putting values in `.env` alone does not inject them into Spring; Compose's explicit `environment` entries do. Do not load the complete release `.env` into backend or collector: it also contains credentials belonging to other services.

Follow [F12 preparation](../../specs/013-administration-app-configuration/plan.md#production-preparation): sign in normally, establish the account, grant its required action permission through the owner's authorized database connection, then activate maintenance through F12 with the usable session. Auth0/Dokploy dashboard sessions are not application operator sessions. `maintenance.manage` and ordinary-access `maintenance.bypass` remain separate; maintenance does not stop collector writes.

Backend health uses native Actuator readiness, including PostgreSQL. Collector starts only after backend health passes; it remains a non-web process. Compose reports its process start, which does not establish successful acquisition or integration. Those outcomes remain with F01's observations. The migration profile is excluded from ordinary service startup.

## Private search infrastructure

F04's [OpenSearch Compose](opensearch.compose.yaml) owns the OpenSearch 3.9.0 service in an independent Dokploy **Raw** Compose resource. Merge only the [backend connection overlay](opensearch.backend.compose.yaml) with the application release Compose. Use each resource's actual Dokploy **App Name** as its own Docker project name. Ordinary application delivery leaves the engine and its volume running. Each environment has its own private internal network shared by these projects, named volume, private configuration directory, CA/certificates and backend password. No engine port is published; collector and migration do not join the search network. Both instances still share the VPS host-failure boundary. There is no Dashboards, replica/HA promise or independent index backup chain. PostgreSQL remains authoritative.

Use [the input names](opensearch/.env.example) in each private Dokploy environment. The engine needs its environment, TLS/security directories and certificate DNs; the application release needs the environment, backend password and TLS directory for its CA file, alongside its existing inputs. The backend mounts only `ca.pem`, never the node/operator private keys or security directory. Compose loads interpolation only through Dokploy's generated `.env` or explicit `--env-file` arguments; Spring receives the overlay's `environment` keys. Search remains disabled without this opt-in overlay. Boot's native PEM SSL bundle supplies CA trust. The full-run delay defaults to `1h`, overridable through `BLOCKOUT_SEARCH_PROJECTION_FULL_REBUILD_DELAY`. Only a web backend schedules writes. Preserve stop-before-start delivery: serving writers must never overlap within an environment.

Before any separately authorized deployment:

1. Confirm [official Docker prerequisites](https://docs.opensearch.org/latest/install-and-configure/install-opensearch/docker/), including `vm.max_map_count=262144`, resources and readable mount ownership. The declared 512 MiB heap is initial configuration, not capacity qualification. This task changes no host settings.
2. Before either Compose project starts, create its shared private network: `docker network create --internal blockout-search-preproduction` for preproduction, and a separate `blockout-search-production` for production. Both Compose files reference this network as external; neither owns its deletion. Standard [cross-project Compose networking](https://docs.docker.com/compose/how-tos/networking/#use-an-existing-external-network) exposes service DNS `opensearch` to the attached backend.
3. Supply a separate CA, node certificate/private PKCS#8 key and distinct operator certificate/key per environment. The node certificate must cover DNS `opensearch` for verified TLS. Set exact node/operator DNs from those certificates. Set `BLOCKOUT_SEARCH_TLS_DIRECTORY=../files/search/tls` and create engine-native **File Mounts** with **File Path** `search/tls/ca.pem`, `search/tls/node.pem` and `search/tls/node-key.pem`. In the separate release resource, create only `search/tls/ca.pem` with the same environment CA. Keep operator keys in a separate private directory. Never reuse test certificates or disable trust/hostname verification.
4. Set `BLOCKOUT_SEARCH_SECURITY_DIRECTORY=../files/search/security` and populate engine-native File Mounts under **File Path** `search/security/<filename>` with [config.yml](opensearch/config.yml), [roles_mapping.yml](opensearch/roles_mapping.yml), [action_groups.yml](opensearch/action_groups.yml), [tenants.yml](opensearch/tenants.yml), [nodes_dn.yml](opensearch/nodes_dn.yml) and that environment's [production roles](opensearch/production/roles.yml) or [preproduction roles](opensearch/preproduction/roles.yml) as `roles.yml`. The native directory import requires `nodes_dn.yml`; it retains only the [upstream 3.9 metadata](https://github.com/opensearch-project/security/blob/3.9.0.0/config/nodes_dn.yml), without adding dynamic node DNs. Generate private `internal_users.yml` with OpenSearch's native `hash.sh`: `_meta: {type: internalusers, config_version: 2}` and `blockout_search.hash` holding the BCrypt password hash. Keep hashes/passwords outside Git. Roles grant only required search/bulk, generation, refresh and alias operations within the selected namespace, without security-admin permission.
5. Validate the engine with `docker compose --env-file <private-search-inputs> --project-name <search-app-name> -f infra/dokploy/opensearch.compose.yaml config --quiet`. Validate the application separately with `docker compose --env-file <private-release-inputs> --env-file <private-backend-search-inputs> --project-name <release-app-name> -f infra/dokploy/compose.yaml -f infra/dokploy/opensearch.backend.compose.yaml config --quiet`. Replace each project placeholder with that resource's actual App Name, including its generated suffix. Do not print resolved values. In the engine resource, create a native File Mount with **File Path** `search/opensearch.yml` containing [opensearch.yml](opensearch/opensearch.yml) from the same revision. Dokploy writes File Mounts under the resource's `files/` directory beside its Raw Compose `code/` directory; the engine bind therefore uses `../files/search/opensearch.yml`. Pasting Compose YAML alone does not create these files. Supply the merged application configuration to `release`; its custom delivery command still targets only backend, collector and migration.
6. Demo installation/default security initialization are disabled. After environment authorization, deploy only the independent engine resource. Initialize its fresh security index in that engine project with the image's native `plugins/opensearch-security/tools/securityadmin.sh`, using one-off Compose `run --rm --no-deps`, that entrypoint and a read-only operator directory mounted at `/run/operator`. Pass `-h opensearch -p 9200 -cn blockout-<environment>-search -cd /usr/share/opensearch/config/opensearch-security -cacert /run/operator/ca.pem -cert /run/operator/admin.pem -key /run/operator/admin-key.pem`. Keep trust/hostname checks enabled. On an existing instance, inspect and back up native security configuration first: `-cd` overwrites it. Follow [official security-admin guidance](https://docs.opensearch.org/latest/security/configuration/security-admin/). The long-running service never mounts the operator key.
7. Deploy the serving backend with its connection overlay after security initialization. Its startup full run creates generations and aliases. F04 T041/#351 retains actual namespace permissions, cross-environment rejection and reconstruction qualification. Static validation establishes no deployment evidence.

## Preparation and qualification

GitHub only exposes `workflow_dispatch` after the workflow exists on the default branch. Deliver the workflow configuration through the ordinary authorized develop-to-main PR before first use; that merge starts no deployment/build.

Configure the GitHub `preproduction` and `production` environments with the owner's **required review** and appropriate branch policies (`develop` and `main`, respectively) before running the workflows. Referencing an environment in YAML does not configure its protection. The preproduction deployment job needs human approval before runtime operations; this approval permits delivery and is separate from qualification after actual tests.

Set these four values once in the GitHub `preproduction` environment; do not duplicate application/database/provider secrets in GitHub settings:

| Type     | Name                    | Value                                                          |
| -------- | ----------------------- | -------------------------------------------------------------- |
| Variable | `DOKPLOY_URL`           | HTTPS origin of the existing Dokploy instance.                 |
| Variable | `DOKPLOY_COMPOSE_ID`    | Native ID of the preproduction `release` Raw Compose resource. |
| Variable | `PREPRODUCTION_API_URL` | Public HTTPS origin of the preproduction API.                  |
| Secret   | `DOKPLOY_TOKEN`         | API key of the dedicated preproduction Member account.         |

Use a dedicated Member with access to the preproduction project and `release` service, plus native API/deployment access. In [Dokploy v0.31.0](https://github.com/Dokploy/dokploy/blob/v0.31.0/apps/dokploy/server/api/routers/compose.ts#L194), `compose.update` also requires `canCreateServices`. This permits new services in any environment of an assigned project, so assign only the dedicated preproduction project, never a historical/production project. Native queue inspection exposes global job metadata. These are broader rights than updating three image fields, and Raw Compose execution on the shared host is not a host-isolation boundary. Review the account's actual permissions before supplying it. API responses can contain private environment configuration: the [deployment helper](../../.github/scripts/deploy-preproduction.sh) discards update responses and filters queue metadata without printing response bodies or uploading them as artifacts. Do not enable shell tracing or dump API errors.

Run **Prepare release** from `develop`, selecting Server, Mobile or Both and supplying its exact current SHA. A moved/different ref is refused. The workflow reuses existing CI. Server preparation publishes three images with the native Docker actions and retains their complete image references pinned by digest as GitHub artifacts. For Server/Both, enable F12 maintenance with an already usable operator session before approving the deployment job. It downloads those exact artifacts, waits for ongoing native operations and requires public `/application-access` to report `maintenance.active == true` before updating the candidate Raw Compose using [compose.yaml](compose.yaml) plus the existing [OpenSearch backend overlay](opensearch.backend.compose.yaml) and invoking the saved native command below. It waits for its matching native deployment's terminal success and checks external `/health`. No additional service, host SSH or custom deployment queue is introduced.

Mobile preparation runs EAS for `preview` and `production` on both platforms and retains only native build IDs/platforms, excluding download URLs and credentials. GitHub's normal artifact retention applies; an expired candidate cannot be promoted through this workflow.

After actual deployment, complete the [prepared qualification](../../specs/003-shared-quality/quickstart.md#delivery-and-operations) before approving the existing manual qualification job. Qualify the native mobile candidates when Mobile/Both is selected; the production-identity binary needs its own store-test proof. Record results in the native Dokploy/EAS/store tools and the owning delivery evidence. This later qualification records actual tests; the earlier deployment permission and automated health check do not establish it. Both jobs use the existing `preproduction` environment. Lift F12 maintenance manually only after qualification; CI has no F12 administration rights.

EAS uses standard [build-time variants](https://docs.expo.dev/build-reference/variants/) and [remote build versions](https://docs.expo.dev/build-reference/app-versions/). `preview` is **Blockout Preprod**, with its own package/bundle identifier. `production` retains F14's `com.blockoutproject.blockout` and existing EAS project. Set `EXPO_PROJECT_SLUG` to that project's actual slug both as a GitHub repository variable (for initial CLI resolution) and as a plain-text variable in the EAS environments used by the profiles. Supply private `EXPO_TOKEN` for the authorized build account. F14 must replace the local-only `0.0.0` marketing version in `app.config.ts` with its approved version in the candidate source before a store build, and verify the existing remote counters/signing associations against the latest submitted builds; do not initialize/reset them from stale local values. Configure API/provider inputs in EAS's `preview` and `production` environments, keeping private upload/signing credentials private. No provider SDK or secret is added here.

The [EAS lifecycle hooks](https://docs.expo.dev/build-reference/npm-hooks/) install the workspace's npm version and regenerate ignored mobile consumers after dependency installation. There is no generated-source upload or second build pipeline. Native development builds remain available locally; no EAS Update/OTA is configured.

## Promotion and native deployment

After explicit human promotion from `develop` to `main`, run **Promote release** from `main` with the successful, approved preparation run ID. It checks the native workflow's identity/result and compares the complete candidate/main source content, allowing a different merge-commit SHA only when the trees match. The `production` environment approval then releases the **same** digest/build-ID handoff to the operator. It rebuilds nothing and publishes nothing to stores.

Production deployment remains manual: the operator enables F12 maintenance with an already usable authorized session, waits for any active Dokploy delivery to finish, sets the exact approved digest references and uses Dokploy's native deployment queue. Keep one delivery in flight per environment and do not cancel a migration. Preproduction's entire preparation/qualification workflow uses `cancel-in-progress: false`, retaining its candidate until the human tests are recorded; its helper also waits for native operations before updating live configuration. Manual operators must coordinate with that same release resource and wait too. Do not replace a candidate while its tests are in progress.

In [Dokploy v0.31.0](https://github.com/Dokploy/dokploy/blob/v0.31.0/apps/dokploy/server/queues/in-memory-queue.ts), native queue groups use the Compose resource ID, not its environment or Docker project name. Two different resources targeting the same project do not provide an environment lock. A [queued job](https://github.com/Dokploy/dokploy/blob/v0.31.0/apps/dokploy/server/queues/queue-types.ts) contains no candidate snapshot; the worker reads current Raw Compose/environment configuration when it runs. Use one release resource per environment, wait before applying the next candidate and qualify this behavior against the actual deployment records. Static/API fixture checks alone do not close T213.

For **Raw** source, Dokploy writes `docker-compose.yml` and `.env` in its application directory. Before saving this **custom Command**, replace **every** `REPLACE_WITH_DOKPLOY_APP_NAME` with the release resource's exact generated **App Name**, including its suffix. Use that same value for every `--project-name`: Dokploy's [container discovery](https://github.com/Dokploy/dokploy/blob/v0.31.0/packages/server/src/services/docker.ts#L106-L122) and [native stop/delete commands](https://github.com/Dokploy/dokploy/blob/v0.31.0/packages/server/src/services/compose.ts#L442-L536) use `compose.appName`, not the display name or environment name. A different project name leaves containers outside those native operations. Dokploy prepends the first `docker`:

```text
compose --project-name REPLACE_WITH_DOKPLOY_APP_NAME --env-file .env --file docker-compose.yml pull backend collector migration && docker compose --project-name REPLACE_WITH_DOKPLOY_APP_NAME --env-file .env --file docker-compose.yml stop backend collector && docker compose --project-name REPLACE_WITH_DOKPLOY_APP_NAME --env-file .env --file docker-compose.yml run --rm --no-deps migration && docker compose --project-name REPLACE_WITH_DOKPLOY_APP_NAME --env-file .env --file docker-compose.yml up --detach --wait --wait-timeout 180 backend collector
```

For production, use the same command with **every** project argument set to that production release resource's exact **App Name**, with production's separate configuration. The complete command replaces Dokploy's default; retain explicit project/file/env arguments on every member. Native `&&` stops after a failed pull, stop, migration or startup. The command never stops PostgreSQL, removes volumes, invokes a Liquibase rollback or repairs a failed migration automatically; native changeset transactions retain their ordinary behavior.

Wait for the native Dokploy result and actual backend/database health, then check owner outcomes before lifting maintenance. A GitHub handoff, container start or green infrastructure probe is not business acceptance. After a failed/uncertain delivery, inspect its native record before another explicit attempt. Use an older application image only after checking compatibility with the current schema/data; otherwise follow the owning repair/restore procedure. Store release is a separate explicit action in the native store consoles using the qualified production build IDs; preproduction is not a substitute. Server/store publication remains non-atomic.
